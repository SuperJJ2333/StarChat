# 好友系统专项重构实施计划

## 现状结论（探索已完成）

- **BUG 1 根因**：通讯录数据来自 `ChatIdentityCache`（SharedPreferences 快照），仅在好友申请变化/自己头像更新时 `refresh()`；好友改头像后无任何触发器重拉，头像缓存键也未失效。朋友圈还会自建独立 `ChatIdentityCache`（违反单一数据源）。
- **BUG 2 现状**：搜索行尾部有"快捷添加"按钮直接发请求（违反流程）；行点击已有申请页（greeting/remark/tags 已存在）；"新的朋友"在列表内联接受/拒绝，无"通过朋友验证"详情页。
- **BUG 3 现状**：accept 后靠整表网络刷新；无本地乐观插入、无 revision、无好友系统消息；`friend.accepted` 仅为后端审计字符串。
- **BUG 4 现状**：`MatrixDirectChatBackend.createEncryptedDirectRoom` 用 `createRoom(invite, isDirect:true)`+`addToDirectChat`，但 m.direct 写入与本地同步的时序在部分设备（API 28）上导致房间被缓存为群聊。SDK 0.34 已有 `client.startDirectChat(mxid, waitForSync: true)`（内部完成查重/加入邀请/isDirect 创建/等同步/写 m.direct），但默认加密条件依赖对方已上传密钥——必须显式 `enableEncryption: true`。
- **后端**：无 `direct_conversations` 表；Matrix 房间创建 100% 在客户端（服务端无法正确设置双方 m.direct，维持客户端创建）。

## Phase A — ProfileRepository（BUG 1）

`ChatIdentityCache` 重构为 `ProfileRepository`（保留 ChangeNotifier 与现有公开 API：`profile/contacts/contactsByMatrixId/preload/refresh/applyUpdatedContact/precacheAvatarImages`，页面接入面最小化）：

1. `FriendProfile {userId, nickname, avatarUrl, avatarVersion, updatedAt}`——`avatarVersion` 从 avatar_url 的 `?v=` 提取（无则用规范化 URL 哈希，与 `avatar_cache.dart` 现有版本键对齐）；缓存键统一 `avatar:{userId}:{avatarVersion}`。
2. 持久化 SharedPreferences → **SQLite**（复用 sqflite_common_ffi + 既有加密缓存仓库模式 `lib/core/cache/`），保存 profile + contacts + `contactsRevision`。
3. 好友头像更新链路（收到 `/friends` 数据 diff 出 avatarUrl/avatarVersion 变化时）：写 SQLite → `AvatarCache.invalidateUser`（旧头像逐出）→ `notifyListeners()`（通讯录/消息页/朋友圈同为监听者，实时重绘）。
4. 刷新触发器：① App 回前台（节流）；② `FriendRequestWatch` 60s 轮询同期拉取 `/friends`（快照 diff，有变化才 notify）；③ 打开通讯录 tab 时。收到任何 contact 变更 → `contactsRevision++`。
5. 朋友圈不再自建缓存：`MomentsPage.identityCache` 必传（AppHome 注入），删除回退自建逻辑。
6. 测试（先行红）：SQLite 持久化/恢复、avatarVersion 变更触发 invalidate+notify、revision 递增、refresh 失败保留快照（迁移既有 `chat_identity_cache_test`）。

## Phase B — 好友申请流程（BUG 2）

1. 删除搜索行"快捷添加"按钮（禁止直接发送）。
2. 新增 `AddFriendProfilePage`（用户资料页：头像/昵称/畅聊号/签名）→「添加到通讯录」→ 进入既有 `RequestFriendPage`（greeting/remark/tags 编辑，保留）→ 发送才 `POST /friends/requests`。
3. 新增 `FriendRequestReviewPage`（通过朋友验证页）：列表点击请求 → 展示头像/昵称/greeting/remark/tags → 「通过验证」「拒绝」→ 仅通过时调 `/friends/requests/{id}/accept`；替换现有列表内联按钮。
4. 状态机 `FriendRequestStatus {PENDING, ACCEPTED, REJECTED, EXPIRED, CANCELLED}`：后端补 `DELETE /friends/requests/{id}`（申请人撤销 PENDING→CANCELLED）；列表按状态渲染（既支持 EXPIRED）。
5. 测试：申请页既有测试迁移 + 新用户资料页/验证页 Widget 测试 + 后端 cancel 端点测试。

## Phase C — 好友接受即时同步（BUG 3）

accept 成功后（客户端本地编排，对应领域事件 friend.accepted）：

1. **乐观本地插入**：用请求行数据构造 `ContactDetails` → `ProfileRepository.applyUpdatedContact`（SQLite 持久化 + revision++ + notify）——无需等待网络整表刷新，UI 立即出现好友。
2. **建立/取得 Direct Room**（Phase D 修正后的路径，失败不阻断好友显示）。
3. **系统招呼消息**：新 Matrix 自定义事件 `com.changliao.friend_accepted`（内容 `{friend_user_id, friend_display_name}`，E2EE，发送到该私聊房间）；时间线适配器映射为 `RoomMessageKind.system`，渲染为居中灰字 **"你已添加了 XXX，现在可以开始聊天了。"**——绝不作为对方名义的普通气泡消息（与 nudge 系统消息同一渲染管线，`room_page.dart` 既有 system 分支）。
4. **会话列表更新**：房间建立后触发首页刷新（既有 onSync 监听自然生效，补一次显式 setState 通知）。
5. 对端（申请人）视角：加入房间后收到同一事件，同样渲染系统消息。
6. 测试：accept 编排单测（乐观插入/revision/房间失败不回滚好友）、`friend_accepted` 事件解析→system 渲染。

## Phase D — Direct Chat Android 修正（BUG 4）

`MatrixDirectChatBackend.createEncryptedDirectRoom` 重写：

1. `client.startDirectChat(matrixUserId, enableEncryption: true, waitForSync: true)`（显式加密，绕过"对方无密钥则明文"默认）。
2. 建房后校验：`room.isDirectChat == true && room.directChatMatrixID == target`；不满足 → `addToDirectChat` + 等待 m.direct account data 同步（`waitForSync` + 本地校验循环），仍失败则**不缓存房间**并抛错重试（禁止把未同步房间永久缓存为群聊）。
3. 结构化日志（一次性 debug 级）：`sdkInt, roomId, targetUserId, isDirect请求值, m.direct前/后, room.isDirectChat, directChatMatrixID, encrypted, waitForSync, db持久化结果`。
4. 既有 `DirectChatService._requireSafe`（加密+双人+含目标）保留为最终防线。
5. 测试：SDK 假件集成测试——复用已有房间/邀约加入/新建/isDirect 校验失败回退/m.direct 等待；`direct_chat_controller_test` 扩展。

## Phase E — Canonical Direct Conversation（后端）

1. 新表 `direct_conversations(id, user_low_id, user_high_id, matrix_room_id, created_at, UNIQUE(user_low_id,user_high_id))`——Alembic 迁移（纯新增，非破坏）。
2. 端点（鉴权 + 幂等键）：
   - `GET /direct-conversations?peer_user_id=` → `{matrix_room_id | null}`（创建前先查，存在复用）；
   - `POST /direct-conversations {peer_user_id, matrix_room_id}` → 注册；UNIQUE 冲突（并发双开）返回既有行（200 + existing），客户端弃用自己的房间采用规范房间。
3. 客户端 `DirectChatController` 接入：open 时先查规范房间 → 无则 `startDirectChat` 创建后注册。OpenAPI 再生 + 后端测试（复用/冲突/鉴权/自对）。
4. 说明：Matrix 房间仍由客户端创建（服务端无法设置双方 m.direct 语义），后端只做规范化登记与复用。

## 顺序与风险

A（数据基座）→ B/C（流程，依赖 A 的乐观插入）→ D（建房修正，C 依赖）→ E（canonical，D 之上）→ F。全程测试先行；不触碰财务/账本边界；后端仅新增表与端点（无破坏性变更）。本计划不包含发版——验收通过后另行走既有发布流程。
