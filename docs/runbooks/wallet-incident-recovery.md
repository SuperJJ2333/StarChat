## 管理后台步骤

### 简化界面（2026-09-08 已批准）

1. 进入「USDT 钱包」，点击「检查当前状态」或页面右上角刷新；只读检查无需操作密码，仍需有效管理员登录。对照“上次完整资金核验”与“当前链上/业务扫描检查”，不要把历史异常标记当作当前监控结果。只读检查不会结案或恢复资金。
2. 选择阻断事故的「查看事故」，阅读中文原因、发生时间和影响范围。勾选接手确认，输入独立操作密码，点击「检查并处理事故」。系统根据当前状态完成确认、实时复核、结案；原因代码自动填写。
3. 检查未完成会显示具体原因，例如“等待业务流水同步”或“链上快照刚发生变化”。稍后刷新并再次检查。断网或未知结果时流程停止，原步骤请求编号保留，下一次显式操作先核实原请求；不会自动恢复资金。

2026-09-09 同步修复：正式复核前先通过现有流水服务同步发现进度（禁止入账），短暂检查点变化最多自动尝试三次。新流水尚待完整核验时仍会停止，不允许靠重试跳过真实缺口。刚过期的有效快照在金融事务外等待 200ms 后重新读取一次；180 秒健康上限及完整性检查保持不变。只读诊断与后台任务可能仍显示不同采样时点，实际恢复以授权复核为准。
4. 所有阻断事故处理后，在「资金启停」勾选独立恢复确认并输入操作密码，点击「核验并恢复资金」。完整检查通过后才恢复。确切匹配的 manual_liquidity 储备 P1 提醒会注明“不阻止恢复”，无需为恢复而强制结案。
5. 当前部署为操作密码模式，一次确认可完成事故内的多个步骤；TOTP 模式每次只能完成一个步骤，需要下一组动态验证码，不能重复使用同一组六位码。

提交期间点击刷新，会提示等待，并在操作结束后统一刷新，不重复提交命令。查看操作结果区分成功与未知结果。暂停资金使用中文确认，系统记录原因代码；不需要手填英文。未确认旧请求保留原参数。页面刷新图标只更新数据；仍看到旧版分步按钮时，待当前请求结束后使用浏览器重新加载以获取新版程序。

以下是旧界面/接口排障流程，简化界面无需手填原因代码或选择三个内部步骤。

### 旧界面与接口排障

1. 使用配置的官方钱包拥有者管理员登录后台，进入「USDT 钱包」。如果提示 RECENT_LOGIN_REQUIRED，重新登录。使用页面要求的独立操作密码；部署处于 TOTP 模式时使用该模式的动态验证码。凭据只输入后台，不交给运维或聊天。
2. 在「监控与事故」点击「刷新监控和事故」，找到 MANUAL_SOURCE_UNHEALTHY，点击「查看事故」，核对事故 ID。邮件事件编号与事故编号不同。
3. 对 OPEN 事故执行「确认事故」。操作原因代码可填写 MANUAL_SOURCE_INVESTIGATED。确认只表示有人接手，不解除异常或暂停。
4. 执行「复核人工监控证据」，操作原因代码可填写 MANUAL_SOURCE_RECHECKED。服务端重新核验来源、流水覆盖、储备与告警状态。刷新后必须看到「异常仍存在：否」并有复核摘要。失败时保留暂停，按错误码排查。
5. 执行「结案并保留暂停」，操作原因代码可填写 MANUAL_SOURCE_RECOVERED。此操作再次核验当前证据。确认事故变为 RESOLVED；若仍有其他阻断事故，分别处理。
6. 到「资金启停」点击「刷新资金控制状态」。未结事故为 0 后，执行「核验并恢复人工钱包」，操作原因代码可填写 MANUAL_SOURCE_RECOVERY_VERIFIED。服务端会再次检查新鲜证据、储备、限制来源和在途付款，成功后才解除本人工钱包暂停。
7. 再刷新资金状态，核对 RUNNING、提现暂停解除、未结阻断事故为 0，并等待一个监控周期确认没有新告警。恢复动作不自动处理需人工签名的付款，也不改变服务器配置的资金开关。

原因代码为人工说明值，格式为大写字母开头、后续大写字母/数字/下划线，总长度 3–100；上述值是建议填写内容，不是新增业务原因枚举。

## 常见阻断

### 后台快照有界重采样（ADR-0061）

部署包含此修复的 worker 后，`BUSINESS_WALLET_MANUAL_STALE_RESAMPLE_BUDGET_SECONDS` 控制后台重采样预算，整数范围 0–60，默认 60；设为 0 并重建 worker 可恢复原有 200ms 单次重采样。同步管理接口仍使用原有短重采样，不等待 60 秒。

仅当快照除了过期之外均有效、业务保护检查通过且储备可以失效时，后台才进入 `MANUAL_SOURCE_WAITING`。等待前先提交储备失效，使新出款执行、兑换及依赖储备的入账无法使用旧证据。等待不占用资金事务，告警发送继续运行。新快照必须具有更大的 observation_id，并通过完整检查；180 秒固化头期限不变。等待超时或发现其他异常仍阻断，不自动结案或恢复已有暂停。

排障查看结构化事件 `reserve_cut_expired_wait`：STARTED、RECOVERED、REJECTED、TIMED_OUT，以及 waited_ms、poll_count 和 observation_id。频繁等待说明源扫描或固化头滞后挤压了可用窗口，应结合已有扫描耗时和块头年龄日志检查供应商。此日志不能作为解除提现暂停的依据，已有事故仍按上方人工流程处理。

- WALLET_MONITOR_UNAVAILABLE / MANUAL_CONTROL_EVIDENCE_UNAVAILABLE：当前证据尚未通过；刷新并检查具体等待/失败原因后重试。
- WALLET_UNRESOLVED_INCIDENTS：仍有阻断事故未结案。
- MANUAL_CONTROL_UNRESOLVED_PAYOUT：存在已领取或状态未知的付款，先核对原付款与链上记录。
- MANUAL_CONTROL_PAUSE_SOURCE_UNKNOWN / MANUAL_CONTROL_SAFETY_SOURCE_UNKNOWN / MANUAL_CONTROL_OTHER_SAFETY_RESTRICTION：有其他来源或归属不明的限制，按对应事故处置。
- MANUAL_CONTROL_SNAPSHOT_CONFLICT：控制状态已变化；刷新后核对新状态，再确认操作。
- 网络中断或请求结果未知：先刷新状态，页面保留原请求参数和幂等键；不要通过换键重复提交来猜测结果。

事故结案与资金恢复是两个独立动作。不要直接改数据库标志或清空事故记录，也不要重建观察库来恢复；这些操作无法完成现有恢复核验。

接口对应关系位于 /api/v1/admin/wallet/manual/operations：事故操作为 /incidents/{incident_id}/ack、/review、/resolve；资金状态为 GET /control，恢复为 POST /control/resume。正常使用后台，由页面管理版本、摘要和幂等键。
