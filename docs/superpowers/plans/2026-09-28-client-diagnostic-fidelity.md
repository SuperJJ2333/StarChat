# 客户端诊断保真与定位计划

**授权：** 用户在 2026-09-28 要求根据真实日志检查修复网络超时、同步、媒体和局部卡顿的记录，包含 version/platform 等定位信息。本计划限定于诊断保真与可证明的失败分类；不凭日志猜测网络根因，也不改变聊天加密、业务鉴权或财务流程。

**已观察到的问题：** 生产形状的网络请求批次因采集器漏列外层 version/platform 被拒；升级恢复的旧操作可能被标成新版本；媒体失败常被记成 unknown；帧只有全局聚合且后台慢事件可能误记为前台；有界队列驱逐缺少覆盖计数。

**设计选择：** 延续既有认证接收端和有界客户端 spool，使用封闭枚举、随机请求/窗口 ID、UTC 时间和非负性能数值。新接收字段只做可选扩展，先发布兼容接收端，再纳入客户端。比较过单独新建遥测服务的方案；现有端点已有鉴权、限流和隐私过滤，当前问题可在这条路径修复。严格逐条远端留存还需要独立的耐久回执/容量设计，本批明确报告本地队列与日志轮转限制。

## 验收项目

1. **N1 网络：** 生产形状的 version/platform 批次被闭合采集器接受，敏感/未知字段仍拒绝；详细失败入队后触发已有 1 秒 spool 调度，请求 ID、阶段、错误类、版本/平台可关联，换号隔离与 422 旧接收兼容保持。
2. **S1 同步：** SDK 等待响应起点写入现有闭合阶段；升级前持久化的操作从原版本/平台批次上传，503 重试/再次恢复不重标、不重复。看门狗的实测停跳与恢复动作失败经独立闭合事件记录，不把动作调用返回冒充 SDK 同步成功。
3. **M1 媒体：** 能以异常类型/HTTP 状态证明的失败归入现有闭合网络类别；不能证明的仍为 unknown。取消与缓存未命中不伪报失败，不读取或上传附件明文、URL、房间 ID、异常文本。
4. **J1 卡顿：** 后台或无效时钟回调不产生前台慢事件；保留旧全局帧计数，并以有界分钟窗口记录安全主标签、刷新预算、慢 build/raster 与最大值。主标签不等于具体子页面；无可靠上下文时记 unknown。每条窗口沿用批次 version/platform、随机 ID 与 UTC 起止以便去重。
5. **C1 覆盖：** 异常操作、事件、帧/窗口在本地容量驱逐或拒绝时有闭合丢失计数；采样成功记录、禁用的帧采集和离线未观测事件不得算作丢失。202 才确认清除，422 仅剥不被旧端支持的可选扩展。离线、进程终止、队列满和服务端日志轮转下不能承诺 100% 远端送达。
6. **T1 排查：** 服务器侧仅输出 version/platform、闭合操作阶段/原因、主标签帧慢率与丢失覆盖的去重汇总；任何原始日志、随机记录 ID、账号/路径/内容不得导出。冲突的重试 ID 要显式计数，不能默默重复累加。

## 顺序与文件归属

1. `network` 子任务：`scripts/collect_network_request_diagnostics.py`、`scripts/collect_network_diagnostics.py`、必要报告脚本及 `tests/infra` 对应测试；先合成生产信封 RED 后修正。
2. `sync-media` 子任务：`apps/mobile_flutter/lib/features/matrix/media_cache.dart`、`matrix_sync_phase_metrics.dart`、必要 watchdog 与相关 Flutter 测试；先证明旧分类缺失再实现。
3. `frame-spool` 子任务：`apps/mobile_flutter/lib/core/chat_diagnostics.dart`、`chat_diagnostics_scope.dart`、`network_diagnostics.dart`、服务端可选诊断模型、OpenAPI 和相关测试；测试升级恢复、丢失覆盖、前台判定、旧接收兼容。
4. `triage` 子任务：新 `scripts/client_diagnostics_triage.py` 及定向 `tests/infra`；在服务器侧处理原始日志，输出有界聚合，不将原始内容下载到工作站。
5. 集成负责人：`apps/mobile_flutter/lib/app_home.dart` 安全 tab 上下文接线及文档/生产发布。先合并协议/接收端、规格复核、质量安全复核；冻结生产当前镜像与配置，仅最小差异发布；再依 Android 固定签名重建及 iOS 交接流程纳入客户端更新。

## 验证与回退

每个代码子任务先 RED/GREEN，再跑聚焦测试、Flutter analyze 或 Python 接口/采集器测试；最终执行适用 `scripts/verify.ps1`，按移动交付工作流记录既有失败与复用边界。服务端扩展无 schema 破坏性迁移；旧接收端 422 可降级到旧字段。发布后的匿名健康/未授权拒绝、版本/平台真实形状、日志接收与无敏感字段验证必须成立。客户端和接收端可独立回退，旧帧/操作信封继续可收。

## 2026-09-28 发布后日志完整性补充

15:38+08 的服务器内聚合发现一行 Android 2188 诊断日志被拒；只在服务器内检查结构后确认，06:57:18 UTC 的同一物理行包含完整、可通过现行 DTO 的诊断 JSON（20 个操作），后面紧接非 JSON 文本。它发生在 Android 2190 发布前，是服务端日志行边界问题，不是新版客户端协议错误。为了满足本计划 T1 的可定位性，追加两个有界步骤：

1. 接收端先用测试证明 `print(..., flush=True)` 的写入边界风险，再以最小更改将单个脱敏诊断 JSON 与换行作为一次写入；验证隐私过滤、限制、鉴权与兼容 DTO 不变。基于当前线上接收端镜像准备仅一文件候选，发布前再次比对容器配置和当前镜像。
2. 服务器私有 triage 对“完整且现行 DTO 有效的 JSON 前缀 + 行尾污染”进行有界恢复，仍将覆盖标记为不完整并计数；不把 malformed 前缀或未验证片段当有效批次，不输出原文。先 RED/GREEN 再复跑已知日志，验证 20 个操作能恢复，并确认新日志无该类问题。若同一行包含多个完整对象，必须有清楚的处理或显式丢失计数。

这两项不改变客户端发布物、API 契约或数据库。远端日志轮转和客户端离线等边界仍不能保证绝对留存。
