# 钱包告警原因与敏感度：已批准并发布

日期：2026-10-05。用户明确回复“同意这套阈值和邮件方案”；实现、评审和生产发布完成。关联[任务记录](../../workflow/tasks/2026-10-05-wallet-alert-sensitivity.md)与[验证报告](../../verification/2026-10-05-wallet-alert-sensitivity.md)。

## 范围与策略

1. 沿用已批准的“监控只记录事故和发送告警、管理员手动暂停”政策。验证所有定时监控入口均不改变全局暂停或限制所有权。保留管理员权限、近期验证、审计与幂等，不自动解除已有暂停。资金操作仍须独立通过新鲜观察、覆盖、对账与余额等证据门槛；通知等待不等于资金操作可以继续。
2. 将可确认的暂时数据过期、源访问失败和没有余额差额的采样不稳定/对账等待分类为短暂观察问题。第一次失败保留诊断；同类异常连续达到 10 分钟才发 P1。恢复使用连续三轮有效健康观察确认，避免一轮好一轮坏反复重开邮件。连续异常只发一次首次通知；仍保留事故时间线与状态变化。计时与去抖状态持久化，worker 重启不重置已累计异常时长；诊断状态不可用时不能无限静默。
3. 不按 MANUAL_SOURCE_UNHEALTHY 名称一刀切降级。真实 BALANCE_DISCREPANCY、源身份/格式异常、时钟异常、覆盖/账本异常、未知出款与邮件送达失败保留即时通知。baseline 未达到及原因无法确认的故障不得冒充短暂网络问题。不增加资金证据的新鲜度窗口。
4. 邮件标题包含等级、中文问题摘要与事件码；正文含事件 ID、事故 ID、北京时间、实际触发原因、连续时长、采样/时效等脱敏证据、操作影响及处理建议。明确“此告警不会自动暂停钱包；暂停由管理员操作”，并说明证据不足的具体资金动作仍会被拒绝。网络错误只有实际证据支持才写；无法确认的底层起因标为未确认。
5. 原因上下文在事件发生时保存，发送/重试使用同一不可变上下文，不拿当前已恢复的状态改写历史。旧事件无原因数据时明确标注历史事件未记录详细原因。仅允许枚举原因与有界数值，不带异常原文、钱包完整地址、余额、凭据。保留原 Outbox 不可变 payload 和 SMTP 回执的重放兼容性，不重写或重发已投递事件。

## 执行与验收

1. 确认具体策略，建立独立干净工作区，冻结相关源码与锁文件哈希，复核现行生产镜像/Compose/schema。
2. 先红测：短暂故障不邮件、10 分钟边界触发、持续故障去重、三轮恢复与重新恶化、进程重启、不同原因切换、并发更新、诊断状态不可用；严重异常立即通知；等待期间资金证据仍拒绝；任何监控分支不自动暂停、已有暂停不解除。
3. 最小实现原因分类与持久状态，邮件上下文及模板；旧事件/回执/重放兼容测试。新增状态若需迁移仅作非财务 expand，核对唯一迁移 head，留恢复证据。
4. 专项红绿后运行受影响 wallet/worker/邮件测试、OpenAPI/迁移兼容检查；环境预检后运行 scripts/verify.ps1。按现行工作流记录无关基线失败与阻断，不导出生产秘密来补环境。
5. 依次规格符合性、领域及质量/安全审查；若使用独立审查代理，先遵守代理使用授权规则。
6. 基于当次线上镜像精确增量构建，核对 worker 实际 site-packages 导入路径；隔离 PostgreSQL 与最终镜像门禁、兼容回退后按 refresh-release-guards 发布。只切换 manifest 内服务，不用整个脏工作区覆盖其他任务。
7. 验证生产源码/hash/健康/未授权拒绝/监控控制不变/实际诊断行为。以隔离邮件捕获验证完整格式，不额外给真实收件人发送测试邮件；后续实际业务通知按现有邮箱配置投递。完成后逐项报告 A1–A3 的实际发布状态。
