# MI 6 Phone Login OTP Replay Guard and Matrix Session Diagnosis Plan

**Authorization:** User reported the Debug2174 failure after the production configuration restore and asked for a working Debug build on MI 6. This is an authentication change under ADR-0075, so domain and quality/security review are required before device installation. Root owns client code, tests, device and documentation; production remains read-only for this plan.

**Evidence:** Three phone-login 200 responses and five subsequent phone-login 400 responses in the 01:58–02:04 UTC read-only production window; three login OTP rows were consumed once. Matrix grant/login returned 200 in the same window. No failed `/auth/matrix-session` response followed the successful phone submissions. Client `LoginPage` labels the same `_submit` handler “重试”, and `DualDomainLoginService.loginPhone` invokes `phoneLogin` again. Backend `verify_code` rejects consumed OTP by design. The first Matrix-session error remains at an unobserved device boundary.

**Goal:** Once phone OTP has been accepted, a failed downstream Matrix/session confirmation must never make the page resubmit that consumed OTP. Keep the existing failure compensation and logout semantics. Emit only a closed, local Debug diagnostic category for an unclassified Matrix-session failure. Do not relax OTP consumption, single-device checks, E2EE, or server auth policy.

**Security review correction:** A proposed in-memory continuation was rejected before implementation. The Business token is persisted before Matrix-session confirmation; on process restart, an in-memory pending flag disappears and `SessionBootstrapController` may show old cached chat and accept a locally logged-in Matrix client without repeating the server confirmation. A safe continuation would require a family-scoped persistent pending gate before cached rendering. That broader authentication change is outside this incident fix.

## Work

1. Write a failing login-page test: once a syntactically valid phone code is submitted, treat every failure or lost response as potentially consumed. Clear the entered code and require a user-initiated request for a new code; the generic “重试” button must never silently submit the previous six digits. This includes `OTP_INVALID`, `PHONE_PROVISIONING_PENDING`, Matrix/business errors, account selection, cancellation and startup callbacks. The existing 60-second resend cooldown still applies. A request's generic 202 response does not prove SMS delivery; unlock only if the phone number has not changed during that request.
2. Add an explicit, closed classification for the `matrix_session` callback boundaries: local credential read and Business confirmation request. In Debug only, record a fixed category and stage code without exception text, IDs, tokens, URLs or stacks. Write focused unit tests for the classifier; retain existing production error/compensation behavior.
3. Run focused Flutter tests, `flutter analyze lib test`, Matrix test suite, full Flutter test suite and applicable `verify.ps1` change-impact gates. Complete ADR-0075 domain review, then quality/security review.
4. Build a higher Debug version using the required source → conventional DEX/resource/Manifest rebuild → alignment → stable test signer path. Preserve MI 6 data, install with `adb install -r`, verify package/signature/SHA, start the app, and observe only safe local diagnostics. Real OTP/login requires user input; do not send a code or enter credentials on their behalf. Record remaining blockers precisely.

**Stop condition:** If the actual first `matrix_session` cause cannot be established without a fresh user login, finish the safe retry fix and instrumentation, install the verified Debug candidate when MI 6 is online, then wait for user-driven reproduction. Do not guess a Matrix/E2EE fix or claim full login success. The existing session-bootstrap recovery boundary is separate and remains open.
