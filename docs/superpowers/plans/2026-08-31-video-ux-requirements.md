# 视频 UX 精准化产品需求（图片页视频展示/压缩发送/播放/气泡样式）

> 版本基线：0.3.20+ 已具备"相册视频条目展示 + 默认压缩发送 + 原图≤20MB"
> 能力；本需求针对用户反馈的四个缺口精准化。
> **前置说明（验收范围）**：相册列出视频、可选中、默认压缩发送在 0.3.20+
> 已实现并被单测覆盖；用户反馈的"完全不可用"大概率来自 0.3.16~0.3.19 旧
> 客户端（无该能力），验收须基于最新安装包。本轮真正的新增缺口是
> **R1 视频预览播放**与**R4 视频消息视觉**。

---

## R1 图片页：视频缩略图展示与点击播放 【P0 · 1.5 人日】

**用户反馈**：图片页视频文件无法正常加载/显示，点击后无法播放。

**现状（代码级）**
- 相册网格已显示视频条目（缩略图 + 时长角标 + 播放图标），缩略图解码失败
  时有占位底色兜底（`device_gallery_source.dart`）。
- **缺口**：点击视频条目进入的是 `_GalleryPreviewPage`（图片预览页），
  只显示静态缩略图，无播放按钮、无播放能力（工程未引入视频播放库）。

**需求描述**
1. 图片页网格中视频与图片混合按创建时间倒序展示（已实现，保持）。
2. 点击**视频**条目 → 进入**视频预览页**：
   - 黑色全屏背景，中央播放/暂停控制，底部显示时长与"发送原视频/压缩"
     说明文案；
   - 进入即加载该视频（压缩版优先，见 R2），加载中显示进度指示；
   - 支持播放/暂停与进度拖动，退出即停止播放。
3. 点击**图片**条目 → 维持现有图片预览页（R 已实现，不变）。

**技术要点**
- 新增依赖 `video_player`（官方插件，显式锁定版本）；iOS 需
  `NSAppTransportSecurity` 不涉及（本地文件播放）。
- 预览页优先播放**压缩临时文件**（R2 产物），发送时直接复用该文件，
  避免"预览一次、发送再压缩一次"的重复转码。

**验收标准**
- [ ] AC1 图片页中 MP4/MOV 视频显示缩略图+时长角标（已实现，回归）。
- [ ] AC2 点击视频 → 预览页可播放/暂停/拖动进度，无转卡顿白屏。
- [ ] AC3 点击图片 → 仍为图片预览（回归）。
- [ ] AC4 真机验证 MKV/AVI：至少可选中与发送（播放兼容性允许降级为
      "仅发送"，见 R2 兜底策略）。

## R2 视频压缩策略与"预览优先"发送 【P0 · 0.5 人日（补充明确+真机调优）】

**用户反馈**：应自动压缩并以预览形式优先发送，降低服务器负载与传输耗时；
需明确压缩策略。

**现状（代码级）**
- 默认发送路径已压缩：`video_compress`（H.264/AAC MP4，480p
  `Res640x480Quality`）；"原图"模式原样发送但单视频 >20MB 拦截；
  压缩失败回退原文件（同样 ≤20MB 兜底）。

**需求描述（将现状固化为明确策略）**
1. **自动转码**：所有相册视频默认转码为 MP4（H.264 + AAC）。
2. **分辨率/码率**：短边 ≤480p（`Res640x480Quality`），目标单文件 ≤20MB
   （480p 下一般数分钟内视频均可满足；超限继续压缩提示用户）。
3. **预览优先**：预览页播放与发送均使用**同一份压缩产物**；转码在
   进入预览页时后台启动，完成后预览与"发送"按钮就绪（转码中发送按钮
   显示进度，不阻塞用户取消）。
4. **原图模式**：勾选"原图"后按原始文件发送，单视频 >20MB 拦截提示
   （已实现，保持）。
5. 压缩失败兜底：若转码失败且原文件 ≤20MB，按原文件发送；否则提示失败。

**验收标准**
- [ ] AC1 发送 1 分钟 1080p 视频：默认通道产物为 480p MP4（真机验证
      体积显著小于原文件）。
- [ ] AC2 预览页播放的画面即压缩后效果；点发送直接复用，无二次转码。
- [ ] AC3 原图模式发送 >20MB 视频被拦截并提示。
- [ ] AC4 服务器与接收端收到的为 MP4 媒体（msgtype m.video）。

## R3 图片页直接选择并发送视频 【P1 · 0.5 人日（验证为主）】

**用户反馈**：当前仅能通过"文件"页面发送视频，路径不符合预期。

**现状（代码级）**
- 图片页已支持视频多选与发送（与图片同流程、受 9 项上限与"原图"开关
  约束），并发送 `m.video` 类型消息。用户"只能走文件页"的反馈与
  R1 同源（旧客户端无此能力，或真机上视频条目未显示导致用户改走文件页）。

**需求描述**
1. 图片页内视频与图片**同交互**：左上角圆圈选中（含序号）、底部"原图"
   开关与"发送(N)"按钮、发送顺序即勾选顺序（已实现，保持）。
2. 回归重点在**真机**：各品牌相册权限（READ_MEDIA_VIDEO）授权后视频
   条目完整可见、可选、可发。
3. "文件"入口保留不动（发送任意格式文件的独立路径）。

**验收标准**
- [ ] AC1 最新安装包上：不经过"文件"入口，纯图片页完成
      "选视频 → 发送 → 对方收到"全流程。
- [ ] AC2 视频+图片混合多选（如 2 视频 + 3 图片）一次发送全部成功，
      顺序与勾选一致。
- [ ] AC3 0.3.16~0.3.19 旧客户端不适用本条（需先升级，发布说明注明）。

## R4 视频消息视觉与播放（去绿色气泡） 【P1 · 1.5 人日】

**用户反馈**：视频消息不应使用绿色气泡，应使用白色/默认样式，统一视觉。

**现状（代码级）**
- 视频消息映射为 `RoomMessageKind.file` → `WeChatAttachmentTile`
  （文件名 + 进度条）并套在消息气泡里；**自己发送的视频为绿色气泡**
  （`bubbleOutgoing`），与微信"视频无气泡、缩略图即消息"的差异即用户
  所见问题。
- 接收端目前无视频播放能力（同 R1 依赖）。

**需求描述**
1. `RoomMessageKind` 新增 `video`；`MessageTypes.Video` 直接映射
   （不再降级为 file）。
2. 视频消息渲染为**无气泡媒体卡**：视频缩略图（首帧，圆角、固定尺寸
   与图片消息一致 200×150）+ 中央半透明播放按钮 + 右下角时长角标；
   自己与他人发的视频均**白底/默认样式**（即无绿色底衬）。
3. 布局沿用消息行体系：头像 + 昵称（群聊）+ 视频卡，与图片消息一致；
   长按弹出与图片相同的消息操作（转发/删除等）。
4. 点击视频卡 → 全屏播放页（`video_player`，播放/暂停/进度/声音），
   播放期间屏幕常亮，退出停止。
5. 发送方在上传完成前显示占位（缩略图 + 上传进度），完成后替换为
   可播放状态。

**验收标准**
- [ ] AC1 自己发送的视频消息：无绿色气泡，显示缩略图+播放按钮+时长。
- [ ] AC2 接收方看到的同一条视频消息样式一致（方向/头像按会话规则）。
- [ ] AC3 点击视频卡可全屏播放/暂停/拖动；退出后回到会话页。
- [ ] AC4 视频消息出现在会话列表时摘要为"[视频]"（已实现，回归）。
- [ ] AC5 消息搜索/转发入口对视频消息可用（沿用文件消息能力）。

**技术要点**
- `video_player` 依赖；`RoomMessageViewModel` 增加 `videoDuration`
  （取自 m.video content info.duration，秒转 mm:ss 展示）。
- 缩略图：发送方用压缩产物首帧（转码时生成）；接收端用
  m.video thumbnail（若携带）或本地解码首帧，无则占位播放按钮。

## 全局说明

- **旧客户端**：0.3.16~0.3.19 无相册视频能力，本需求验收一律基于
  最新安装包；发布说明需引导用户升级。
- **依赖新增**：`video_player`（官方、显式版本锁定）。
- **真机验证项**：视频转码耗时与发热（中端机 1 分钟 1080p 预计 5~15 秒）、
  各厂商 ROM 的视频解码兼容性（至少小米/华为/OPPO 各一台）。
- **服务端**：无需改动（m.video 走既有加密媒体上传通道）；大文件上传
  建议后续单独评估分片上传（非本轮）。

## 建议排期

R2（策略明确化）→ R1（预览播放）→ R4（消息视觉与播放）→ R3（真机
回归收口）；合计约 3.5~4 人日 + 真机联测。
