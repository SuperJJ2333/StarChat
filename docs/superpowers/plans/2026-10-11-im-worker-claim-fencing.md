# R9b step 1: explicit claim-generation interfaces

Approved scope: parent task's explicit 2026-10-11 instruction under R9/A7-4 in `2026-10-11-im-reliability-remediation.md`. Base `dc409a5e4652207f89b74eff2bf0b495c1795a6d`; isolated `im-worker-claim-fencing` tree. Own only `services/business-api/app/core/outbox.py`, `services/business-worker/app/worker.py`, related Consumer/Worker tests and this task's documentation/evidence.

1. RED: real Consumer tests prove that `(event_id, worker_id, attempt_count)` is mandatory on new APIs, stale attempts cannot renew/succeed/fail/dead after reclaim with the same worker ID, renewal fails at expiry and uses time sampled after the row lock. Real Worker tests must expose its currently unfenced completion. PostgreSQL tests exercise both orders of claim/completion, and NOWAIT renewal under a held lock.
2. GREEN: add `renew_claim`, `mark_claim_succeeded`, `mark_claim_failed`, `mark_claim_dead`, each requiring the original positive integer attempt. Validate and mutate within one transaction. Worker uses only these interfaces; reject a consumer missing them before dispatch. Existing `mark_*` entry points stay explicitly legacy for current direct callers; no optional token or implicit fallback in the new interfaces. No schema, handler, replay, configuration, or thread changes.
3. Verify: focused tests, existing Worker/Outbox/idempotency/handover invariants, bounded native PostgreSQL competition, applicable repository/type/contract gates after preflight; preserve and report existing strict active-handler XFAIL. Record actual commands/exits and input hashes. Freeze for non-author domain/SPEC then Quality/Security review; no deployment.

Decision: successful renewal updates only `locked_at`, with NOWAIT row acquisition; it must not resurrect a lease that expired while obtaining the lock. A DB exception propagates, never becomes a success or triggers automatic requeue. Network/pool timeouts remain caller/engine configuration, and this dormant public interface does not start a background lifecycle.

Decision: completion accepts an expired original generation that has not been reclaimed, preserving the existing completion contract; after a newer claim commits, old completion fails. Finalization uses row-lock generation predicates in the mutation transaction. The same-generation success/failure/dead behavior retains existing timestamps, retry scheduling and error truncation.

Limit: this fences queue state only, not an external effect from an already-running handler. Old public entry points remain weaker during compatibility; all deployable Worker code must use the new entry points. Both updated modules must ship together with role/protocol guards; a Worker-only overlay onto an old Consumer is not valid. No exactly-once claim, no financial transition/formula/authority change, no historical DEAD replay. Active handlers may still exceed five minutes and run concurrently until a separately reviewed renewal/fencing lifecycle is implemented. Existing ledger/audit/receipt/idempotency and handover checks remain unchanged.

Ruling: task artifacts/ledger live under `docs/verification/` as required by repository policy rather than the skill's generic `.superpowers/` scratch location. Financial handlers and schema are untouched, so this is a queue-ownership implementation note, not an ADR approving a protected financial or key-recovery change.
