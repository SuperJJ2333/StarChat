# Matrix 会话连续性、Megolm 在线备份与可信设备恢复设计

**状态：** 产品设计已批准；受保护变更评审待完成

**日期：** 2026-08-25

**适用范围：** Flutter 移动端会话启动、账号切换、本地 Matrix SQLCipher 数据库、Matrix 设备身份、SSSS、交叉签名、Megolm 在线密钥备份、可信设备秘密共享、消息解密状态和设备安全页面。

**受保护变更：** 本设计涉及 E2EE、密钥备份和密钥恢复。实施前必须完成 Domain Review 与 Quality/Security Review；任何实现不得让 Business API、Synapse、日志或验证材料取得恢复密钥、房间会话密钥或消息明文。

## 1. 背景与问题

当前普通退出只在当次进程中暂停 Matrix，但 APP 重启后，启动协调器发现 Business 会话不存在时会重置 Matrix 客户端，删除 SQLCipher 数据库及其安全存储密钥。用户随后以同一账号登录时会得到新的 Matrix 设备，旧的本地 Olm/Megolm 状态已丢失，因此历史密文可能显示为“消息尚未解密”。

当前“创建并缓存加密备份”只创建 SSSS 密钥并缓存秘密，没有完整创建在线 Megolm 备份版本、上传入站 Megolm 会话和恢复房间密钥。客户端也没有把在线备份与可信设备秘密请求组织为可观察恢复流程，因而无法区分暂时正在恢复与最终缺少会话密钥。

消息密文本身不会因缺少本地密钥自动消失；问题是客户端删除或无法取得对应 Megolm 会话后不能解密已有密文。

## 2. 目标

1. 主动退出后保留账号与 Matrix MXID 绑定、Matrix SQLCipher 数据库、数据库密钥、Matrix 设备 ID、Olm 账号及本地 Megolm 会话。
2. 只有确认切换到不同 Matrix 账号，或用户明确确认“清除本机聊天数据”时，才删除 Matrix 本地数据库和本机密钥。
3. 完整实现加密的 Megolm 在线备份、恢复密钥本机安全存储、在线恢复和可信设备秘密请求。
4. 新设备通过标准 Matrix 设备验证和 Olm 加密的秘密共享恢复备份私钥，服务器只中转密文。
5. 将消息状态明确区分为“正在解密”“缺少密钥，无法解密”和非缺钥型“消息解密失败”。
6. 建立“退出 → 关闭 APP → 重启 → 同账号登录 → 旧消息仍可解密”的自动化和模拟器端到端回归。

## 3. 明确不做

- 不把 SSSS 恢复密钥、Megolm 备份私钥、Olm/Megolm 会话密钥发送给 Business API。
- 不让 Synapse 保存任何上述秘密的明文。
- 不采用 Telegram Cloud Chat 式服务器可解密聊天。
- 不以业务密码、Refresh Token、邮箱验证码或密码找回流程派生恢复密钥。
- 不在普通退出、Business Token 失效、网络错误、数据库暂时打不开或账号封禁时自动删除 Matrix 数据。
- 不自定义一套绕过 Matrix 设备验证的业务服务器密钥信封协议。

## 4. 密钥和数据的权威边界

- Business API 负责业务账号认证、会话撤销、账号状态和一次性 Matrix Login Token，不负责聊天密钥。
- Synapse 负责 Matrix 账号、设备、公钥、加密事件、加密 to-device 事件和加密房间密钥备份。
- Android Keystore / iOS Keychain 保存 SQLCipher 数据库密钥、SSSS 恢复密钥和本机账号绑定元数据。
- Matrix SQLCipher 数据库保存 Matrix Access Token、设备 ID、同步游标、Olm 账号、交叉签名缓存、Megolm 会话及密文历史。
- 服务端可以保存使用备份公钥加密的 Megolm 会话，以及使用 SSSS 加密的 `m.megolm_backup.v1` 备份私钥；服务端不能取得解密这些内容的 SSSS 恢复密钥。
- 可信设备共享的是经过 Olm 端到端加密的 `m.megolm_backup.v1` 秘密。Synapse 可以暂存和转发 `m.secret.request` / `m.secret.send` 密文，但不能读取秘密。

## 5. 总体架构

### 5.1 本机账号绑定

新增独立于 Business 会话的版本化本机 Matrix 绑定记录，至少包含：

```text
version
matrix_user_id
matrix_device_id
homeserver
database_generation
```

绑定记录不包含业务密码、恢复密钥或消息正文。普通退出只清除 Business 会话，绑定记录继续存在。登录令牌返回 MXID 后，登录服务先比较绑定身份，再决定复用或清除。

### 5.2 同账号连续性

同账号登录必须复用原 SQLCipher 数据库和原设备 ID：

- Matrix Access Token 有效时直接恢复同步，不申请或消费新的 Matrix Login Token。
- Matrix 进入 soft logout 或 Token 明确失效时，使用 Business API 签发的一次性 Login Token和原设备 ID重新认证。
- 重新认证只更新 Matrix 凭证，不调用 SDK `logout()`、`clear()` 或本地数据库 reset。
- 重新认证前后必须验证 MXID、设备 ID及设备 Ed25519 指纹保持一致；不一致时失败关闭聊天入口，不静默创建新设备。

### 5.3 在线 Megolm 备份

首次配置通过 Matrix SDK Bootstrap/SSSS 流程完成：

1. 创建或安全打开 SSSS 默认密钥。
2. 配置交叉签名并验证本机设备。
3. 创建 `m.megolm_backup.v1.curve25519-aes-sha2` 在线备份版本。
4. 将备份私钥加密存入 SSSS。
5. 标记本地入站 Megolm 会话为待上传。
6. 上传加密后的房间会话；以后在同步后增量上传。
7. 将 SSSS 恢复密钥写入 Android Keystore / iOS Keychain，并提供可选的用户导出入口。

同一手机恢复时优先从系统安全存储打开 SSSS，再下载并恢复在线备份；日常退出和重启不要求用户抄录密钥。

### 5.4 可信设备恢复

新设备登录后生成标准 Matrix Olm 设备身份，不创建独立于 Matrix 的临时密码学协议。恢复步骤为：

1. 新设备与旧设备通过 SAS/二维码完成 Matrix 设备验证。
2. 新设备只向同一 MXID 下已验证、未封禁且不是自身的设备发送 `m.secret.request`。
3. 旧设备确认请求设备可信，并通过 Olm 加密的 `m.secret.send` 返回 `m.megolm_backup.v1` 秘密。
4. 新设备校验发送设备、公钥、请求 ID、有效期和备份公钥匹配关系。
5. 校验成功后缓存秘密并恢复在线 Megolm 备份。

没有可信旧设备时，只能使用用户以前主动导出的 SSSS 恢复密钥。两者都不存在时，业务账号和资金仍可恢复，但历史聊天永久无法恢复。

## 6. 账号与本机数据状态机

```text
未绑定
  └─ 登录账号 A → 已绑定并激活 A

已绑定并激活 A
  ├─ 主动退出 → 已绑定但未认证 A
  ├─ APP 关闭/重启 → 状态不变
  ├─ 同账号 A 登录 → 复用数据库、设备 ID 和密钥
  ├─ 登录账号 B → 确认切换 → 清除 A → 绑定并激活 B
  └─ 清除本机聊天数据 → 确认清除 → 未绑定
```

### 6.1 普通退出

- 尽力撤销 Business Refresh Token并清除 Business 本机会话。
- 停止 Matrix 同步并安全关闭数据库句柄。
- 保留 Matrix 本地授权状态、数据库、数据库密钥、绑定、设备 ID和全部加密状态。
- APP 的认证门必须阻止未通过 Business 登录的用户访问聊天 UI。
- 任一步骤失败都不得补偿为 Matrix reset。

### 6.2 启动与同账号登录

- Business 会话不存在而 Matrix 数据存在时进入登录页，Matrix 状态为“已保留”，不执行 reset。
- 同账号登录验证 Login Token返回的 MXID与本机绑定一致，然后复用或重新认证原设备。
- 临时网络故障保留当前数据和恢复进度。
- 数据库打不开时进入可重试错误页，不自动删除或重新生成数据库密钥。

### 6.3 不同账号与明确清除

- Login Token返回不同 MXID时，在打开聊天数据前提示将清除上一账号本机聊天数据。
- 用户取消后保留原账号数据，并终止本次账号切换。
- 用户确认后才删除上一账号 SQLCipher 数据库、数据库密钥、SSSS 恢复密钥缓存和绑定记录。
- “清除本机聊天数据”必须二次确认；执行前尽力撤销当前 Matrix 设备会话，离线时仍允许完成本地清除，并提示服务器设备列表可能暂时保留离线记录。

## 7. 备份与恢复状态机

```text
未配置
  → 正在创建 SSSS/交叉签名
  → 正在创建在线备份版本
  → 正在上传 Megolm 会话
  → 备份可用

备份可用
  ├─ 本机恢复密钥可用 → 自动解锁和恢复
  ├─ 本机密钥缺失 → 请求可信设备
  │                    ├─ 获得并验证秘密 → 恢复备份
  │                    └─ 无可信设备/超时 → 需要恢复密钥
  └─ 用户输入恢复密钥 → 校验公钥 → 恢复备份
```

恢复秘密必须对应当前 MXID和当前在线备份版本。密钥、公钥或版本不匹配时不得覆盖本地密钥、删除旧备份或自动创建替代版本。上传和下载失败保持可重试，已成功处理的会话不得重复破坏。

## 8. 消息解密状态

每个加密事件维护独立状态：

```text
等待解密
  → 本地数据库查找
  → 在线 Megolm 备份查找
  → 可信设备密钥请求
  → 解密成功 / 缺少密钥 / 密钥损坏
```

显示规则：

- `正在解密`：正在读取本地会话、访问在线备份、等待可信设备响应，或当前离线而恢复任务等待网络。
- `缺少密钥，无法解密`：本地没有会话，在线备份明确不存在或未配置，并且没有可请求的可信设备，或 30 秒内没有收到有效响应。
- `消息解密失败`：找到了密钥但完整性校验失败、算法不支持，或密文、会话索引、认证数据损坏。

“缺少密钥”不是永久锁死状态。手动重试、网络恢复、备份更新或可信设备迟到的有效响应均把状态重新置为“正在解密”；成功后立即用真实消息替换占位内容。消息列表与聊天详情必须消费同一个可观察解密状态源。

## 9. 错误处理

- 本地数据库打不开：不自动删除，提供重试和明确的手动清除入口。
- 账号绑定不一致：停止加载聊天并要求确认切换，不展示上一账号内容。
- Matrix soft logout：以原设备 ID重新认证；失败时保留数据库并允许重试。
- 在线备份暂时不可用：指数退避，不影响本地已有消息解密。
- 备份版本或恢复密钥不匹配：停止恢复，不覆盖现有备份和本机秘密。
- 未验证、已封禁、其他账号或请求过期的设备：拒绝秘密请求。
- 可信设备请求超时：进入可重试缺钥状态；迟到但仍在 Matrix 15 分钟请求有效期内的响应通过完整校验后仍可恢复。
- 普通退出部分失败：Business 会话仍从本机清除，Matrix 数据保持。
- 明确清除本机数据：即使服务器离线也完成本地清除，但必须提示可能存在待撤销服务器设备。

## 11. 测试设计

### 11.1 测试先行证据

每项行为先添加失败测试并确认因当前缺陷失败，再实现最小修改。红/绿输出、非 Git 验证摘要和模拟器证据写入 `docs/verification/`；临时材料只允许位于 `docs/verification/artifacts/2026-08-25/matrix-key-recovery/`。

### 11.2 会话生命周期单元测试

- 普通退出仅暂停 Matrix，`resetCalls == 0`。
- Business 会话缺失且 Matrix 已保留时，启动不 reset。
- 同账号登录前后设备 ID、Ed25519 指纹和数据库 generation 不变。
- soft logout 使用原设备 ID重新认证且不清库。
- 不同 MXID只有确认切换后 `resetCalls == 1`；取消时为零。
- 明确清除只有二次确认后删除。
- 数据库打开失败、网络错误、5xx、Business Token 失效和账号封禁均不自动删除 Matrix 数据。

### 11.3 备份与可信设备单元测试

- 创建 SSSS、交叉签名、在线备份版本并上传全部已有入站会话。
- 新入站会话在同步后增量上传；失败幂等重试且不重复创建版本。
- 恢复秘密不进入 Business API。
- 备份公钥不匹配时拒绝恢复且不覆盖现有版本。
- 仅向同 MXID、已验证、未封禁的其他设备发送秘密请求。
- 拒绝未验证、封禁、其他账号、请求 ID错误、超过 15 分钟、非 Olm 加密、发送设备公钥不匹配及秘密校验失败的响应。
- 有效秘密写入加密缓存后触发在线备份恢复，并取消其他未完成请求。

### 11.4 解密状态组件测试

- 本地、备份、可信设备恢复阶段均显示“正在解密”。
- 离线等待不得错误显示“缺少密钥”。
- 全部恢复路径不可用或注入时钟推进 30 秒后显示“缺少密钥，无法解密”。
- 密钥或密文损坏显示“消息解密失败”。
- 重试、网络恢复或迟到有效密钥使状态回到“正在解密”并最终显示真实消息。
- 消息列表和聊天详情同时更新，已解密内容不因一次网络错误倒退。

### 11.5 真实 Synapse 集成测试

在隔离 Docker Synapse 中使用测试账号与设备：

1. 设备 A接收并解密 Megolm 消息，创建在线备份并上传会话。
2. 全新数据库的设备 B使用测试恢复密钥下载备份并解密历史消息。
3. A、B 完成 SAS 验证；B通过 `m.secret.request` 请求，A通过 Olm 加密的 `m.secret.send` 返回备份秘密；B恢复历史消息。
4. 重复验证未验证、封禁、篡改、离线、超时和版本不匹配场景。
5. 使用测试专用一次性标记扫描 API 捕获、容器日志和 Synapse 存储，证明不存在秘密或消息明文；验证报告只记录 PASS 和脱敏摘要，不保存标记值。

### 11.6 必须通过的模拟器 E2E

```text
退出账号
→ adb force-stop 关闭 APP
→ 重启 APP
→ 同账号登录
→ 打开原会话
→ 旧消息仍可解密
```

测试账号 A、B先建立强制 E2EE 私聊并使 A成功解密 B发送的唯一测试消息。退出前记录 A的 MXID、设备 ID、设备 Ed25519 指纹和数据库 generation。重启后登录页不得泄露聊天内容；同账号登录后原消息直接显示或短暂显示“正在解密”后恢复。设备 ID、Ed25519 指纹和 generation 必须不变，且全过程没有 Matrix reset。

另行覆盖切换账号的取消/确认路径和“清除本机聊天数据”的取消/确认路径。数据库会因正常同步改变内容，不以文件哈希完全相同为判断条件。

### 11.7 日志安全测试

发布版和调试版日志均扫描并确认不存在消息正文、恢复密钥、Olm/Megolm 密钥、Token 和完整身份标识；错误日志必须包含稳定 `event_code`、阶段、结果和可关联的 `trace_id`。
