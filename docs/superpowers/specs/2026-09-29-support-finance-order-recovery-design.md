# 客服提现处理、链上核验与独占认领修复设计

状态：2026-09-29 用户批准会话内的分阶段方案；书面规格待用户审阅。实施前还须批准受保护 ADR 与逐项计划。

## 目标、基线与边界

本设计覆盖用户报告的四类问题：`WALLET_PAYOUT_CANNOT_CANCEL` 原始错误码与过早禁止取消；客服确认汇率后无法返回、无法查看并复制客户钱包地址、无法拒绝未开始出款的提现；无交易哈希时“查询链上核验结果”无法搜索；其他客服正在处理的提现或充值请求仍显示可点击的操作入口。后台沿用已发布的“墨夜银锋”钱包工作台样式，不另建资金系统。

已发布 Android `0.4.24+2193`、钱包工作台与业务 API 是基线。生产只读核对表明提现状态机和 TronGrid 核验的相关服务文件与本工作树 `fd9ab39d` 相同；线上提现和充值页面虽与本地文件字节不同，所述问题的代码仍在。执行前必须重新冻结实时 API 镜像、schema、静态 SHA 和部署层，不把本次调查快照当作发布基线。本轮只交付后台与 API：现有 Android 接收中文错误消息；客户端取消按钮在过期订单上的显示与失败后自动刷新留待后续 Android 版本，不能宣称已修复。

| ID | 期望行为 | 本轮验收 |
| --- | --- | --- |
| SFO-1 | 未真正开始出款时，用户可取消；客服可带原因拒绝；退款与原兑换冲正完整、一次性 | 认领和保存待执行汇率后均可取消或拒绝；与开始出款并发只允许一个结果；开始后保持冻结 |

## 调查结论与方案取舍

当前 `adjust-rate` 先独立提交 `begin_payment`，将 `execution_started_at` 写入并把提现变为 `CLAIMED`，然后才校验和调整汇率。即使汇率调整失败，先前的开始出款也已提交。用户取消只接受 `REQUESTED` 且尚未开始的订单；错误响应的 `message` 等于代码，而 Android 直接显示该消息。确认汇率返回的详情没有 `instructions`，客户地址因此消失，刷新后也不恢复。链上按钮只对已保存的候选 txid 调用 `transaction_evidence`；没有候选时会把订单置为 `UNKNOWN`，不会查 TronGrid 历史。提现与充值页面的外层“处理请求”始终可点击，但服务端拒绝第二位客服的有效认领。

只改按钮不能修正资金状态；把取消期限延至“到账前”无法排除已签名、已广播但尚未固化的付款，会造成付款与退款并存。因此采用“确认汇率与开始出款分离、只读发现候选、独占认领加受控管理员接管”的方案。保留 ADR-0013 的 TronGrid 单源、imToken 人工签名、固定 USDT 合约与固化收据要求；历史索引只用于发现，不能当结算证明。

## 提现状态和资金事务

客服认领只取得有时限的处理权，不启动出款。对于点钻来源的 `SUPPORT_MANUAL_V1`，`adjust-rate` 改为**准备汇率**：仅在 `REQUESTED` 且 `execution_started_at` 为空时，在同一事务内核对当前客服会话、实时角色和有效认领令牌，校验汇率格式、按 `Decimal` 六位精度计算待执行应付，保存独立的准备汇率、应付、摘要和递增版本，并写稳定原因、幂等收据、审计与 Outbox。可多次准备，每次留痕；当前 `row.final_rate/final_receive`、`HOLD`、原点钻兑换和用户可用余额**均不改变**。原有 USDT 来源订单仍不允许按点钻汇率重算。准备值是计划，不是付款成功或不可撤回的最终额；开始出款时必须重新核对限额、储备、用户余额和钱包状态。准备失败整笔回滚，不得先启动出款。开始出款后客服不能再调整汇率；既有 `OWNER_MANUAL_V1` 订单的原流程不受此兼容改动影响。

用户取消和客服拒绝共享同一受控释放应用接口，但分别使用用户身份与客服身份、独立的操作和原因。仅 `REQUESTED`、未开始、无候选付款凭证时可提交；在订单/预算/用户锁内与 `begin-payment`、其他取消/拒绝序列化。准备汇率未改变冻结，故释放原订单的全部 `HOLD`（初始 `row.amount`）；若申请由点钻兑换，则按原不可变兑换凭证的 source/target 金额做精确链接冲正。取消与拒绝必须同时使准备汇率失效，不能留下可执行草稿。所有分录保持资产内平衡；失败不得部分释放，重试不得重复退款。拒绝操作者须持有当前有效认领令牌，并在同一锁事务的提交前复核当前管理会话、钱包写权限，以及与现行客服订单授权一致的 `FINANCE_SUPPORT` **或配置的官方钱包所有者 `SUPER_ADMIN`** 资格；所有者管理员还须满足当次新鲜操作级证明。他人认领、租约过期或角色撤销均拒绝。拒绝必须从稳定原因菜单选择一项，例如收款地址无效、订单资料不符、受理规则不符；原因和实际操作者进入不可变拒绝记录、审计、Outbox。现有链接兑换冲正及账本证明把操作者固定为用户，并把原因固定为用户取消；本轮须在公开兑换/账本应用接口中拆开**受益用户账户**与**实际操作人**，以受益用户账户核验镜像分录、原 conversion ID、source/target 和唯一 reversal，同时使不可变账本事务、拒绝记录及审计准确指向实际操作者和 `MANUAL_PAYOUT_REJECTED`，不能只改一个调用参数或伪记为用户取消。核心终态沿用兼容的 `CANCELLED`，客服投影另显示 `REJECTED`，旧客户端仍安全识别为已终止。

`begin-payment` 保持唯一的不可逆操作入口。它在**一个事务**中核对当前认领、精确应付、目标地址快照、官方地址、储备、用户可用余额、钱包安全状态和未取消/未拒绝。点钻来源订单还须核对准备汇率的最新版本与**当前有效摘要**，按准备值调平用户 USDT 与 `HOLD`、记录最终汇率及金额；旧页面持原始摘要或旧准备版本调用必须 409，不得在新汇率下启动旧确认。USDT 来源订单没有准备汇率，沿用原报价金额、原摘要和初始 `HOLD`，不得要求准备版本或发生点钻汇率调平。两种分支都在各自校验和必要分录成功后，才把核心订单置为 `CLAIMED` 并设置开始时间，生成原有不可变付款指令与审计。任何一步失败都不启动、也不移动冻结；仍可取消/拒绝。成功后才开放完整客户地址与复制。重复 begin 只能读回同一不可变指令并提示“已开始，勿重复付款”，不能新增付款资格。开始后普通取消、拒绝、调汇率和第二次付款均不可用；已提交 txid、`UNKNOWN` 或链上结果不明继续保持冻结并走核对。已经由旧流程标为开始出款的历史订单不自动回拨 `REQUESTED`，须按单据、imToken 记录及链上证据单独核查，不能凭“未到账”或 TronGrid 暂无结果退款。

服务端保持错误 `code=WALLET_PAYOUT_CANNOT_CANCEL` 兼容，但将该错误的 `message` 改为明确中文，并针对开始出款、结果待核对等阶段给出可理解的原因；旧版 Android 可直接显示中文。客户端按钮显示及失败后刷新不属于本轮交付。

## 客服处理界面与地址

弹窗内增加明确“返回提现列表”按钮，关闭模态并保留订单筛选与当前服务器状态，不把返回解释为撤销已提交汇率。开始出款前显示待执行汇率、待执行应付与可再次调整的表单；“保存结算汇率”和“确认开始出款”分为两个操作，后者的确认窗显示**脱敏**地址、金额、网络和不可撤回提示，不提前提供完整地址或复制。确认成功后才从服务端取得完整地址，并突出提示须按该不可变付款指令操作。拒绝操作仅在开始前出现，选择原因、确认后刷新权威状态；写请求结果未知时不得自动重放。

新增受控的客户收款地址只读详情：从不可变报价快照取目标地址，**仅在订单已真正开始出款后**返回完整值；此前所有列表、详情、确认窗和接口仅显示脱敏地址。开始后只向持有有效付款证据处理资格的原认领者，或持有受控证据查看/接管资格的官方钱包所有者管理员返回，并对每次完整地址读取留审计。原认领者进入已开始状态后，其证据资格按服务端规则保留到证据权被撤销；不能仅因普通认领租约到期就丢失核对能力。普通队列、浏览器持久化、普通日志和错误消息不包含完整地址。开始后的付款详情以独立高对比区域和等宽换行文字突出“客户收款地址”，配有可键盘操作的复制 icon；只将完整地址写入剪贴板，成功/失败用 `role=status` 反馈。刷新或重新打开仍须重新鉴权；证据权撤销、退出或换账号立即清除 DOM 中的完整地址及草稿。地址复制不是付款确认，也不触发资金写入。

## TronGrid 无哈希发现与结算

把“查询链上核验结果”拆为“查找链上出款”和“核验已选交易”。仅在已开始出款、当前会话具备证据核对权时开放。新只读发现接口从服务端订单快照取官方付款地址、客户收款地址、固定 USDT 合约、精确六位应付额、开始时间和订单版本；前端不能传任意地址/金额来扩大搜索。TronGrid 的官方地址 TRC20 历史只用于获取 txid，固定主网、官方来源、确认状态、合约及有界时间窗，以固定固化头与明确扫描区间运行，完整处理分页、指纹循环、页数/条数/总时限与上游失败。查询不完整必须标记 `INCOMPLETE` 或 `UNAVAILABLE`，零候选不能写成“确定未付款”。较老订单超出安全分页预算时提示人工输入 txid 并继续核验，不以截断的搜索否定付款。链上观察器列表的水位不证明历史完整，也不能代替该查询。

每个发现的 txid 再走现有 `transaction_evidence` 固化收据，核对成功执行、固化头、新鲜度、官方来源、目标地址、整数金额、合约、出款时间及 `(txid, log_index)` 唯一事件。候选列表只展示缩略哈希、金额、**脱敏**收款地址、北京时间和证据状态；服务端用完整地址核对，前端不得从候选接口绕过地址读取权限。客服须对照 imToken 付款记录主动选择。选择命令在服务端重新核对订单版本、证据处理资格、完整发现结果、收据和事件未占用，并提前提示同时间窗内其他尚未终结、官方来源/目标/金额相同的出款订单；通过后把定位符作为不可变候选记入原订单，随后复用现有 reconcile。**真正的归属门禁放在所有路径共用的最终 reconcile 账本提交前**：手填 txid、候选选择、更正及重试都须在订单与同官方来源/目标归属锁内重验固化收据、事件占用及整个相交时间窗的未终结订单集合；开始新出款也遵循该锁协议，防止检查后出现竞争订单。若一条链上事件无法证明唯一归属，即使尚未被占用也不能结算，须进入人工调查。无候选、索引不完整、证据过期、重复匹配、与另一张订单无法区分或网络失败均保持冻结并提示待核对，不自动结算、不自动重付。已有手填 txid 和更正凭证路径保留，但无候选时直接点击核验不再把 `CLAIMED` 无故降为 `UNKNOWN`。

## 他人认领与管理员接管

提现与充值列表用服务端有效认领/能力投影决定入口。另一位客服持有有效租约时，普通客服按钮显示**“正被其他客服处理中”**且真实 `disabled`；不能仅靠 CSS 伪禁用。官方钱包所有者管理员可打开只读详情，并在单独确认窗填写稳定接管原因，调用独立受控命令。管理员资格在服务端重新核对当前 admin 会话、`SUPER_ADMIN` 与配置的 `wallet_manual_owner_admin_id`；真正接管还须当次新鲜的钱包操作级验证或 TOTP，并在持锁提交前复核授权，现有 48 小时后台会话不足以直接越过。前端角色或 `*` 权限本身不授予接管权。

未开始财务执行的订单，接管在订单锁内原子替换认领者和令牌、递增版本，写幂等收据、审计与 Outbox；旧客服令牌即时失效。已经开始出款的提现仅可走**证据核对接管**：产生独立的证据操作者、版本和令牌，撤销旧证据令牌，保留原付款认领者与其不可变开始记录；证据令牌只允许发现、提交或更正 txid、复核收据，不能调用付款指令、再次开始出款、改汇率或拒绝退款。接管前的原领取人在开始后即使普通租约届满，也可继续核对证据；证据接管提交后才失去该权。结果 `UNKNOWN` 或付款事实不明时只允许核对，不能跳过收据/唯一性门禁。充值在已有付款凭证、到账、调整绑定或下发不明时沿用其现有独立审批和安全恢复规则；管理员点击只读查看，并且仅在服务端证明未执行且当前处理资格可安全移交时开放相应证据/复核接管，绝不二次入账或普通拒绝。并发接管、旧令牌、身份/角色撤销和会话过期均失败关闭。

## 验证、发布与回退

先做失败用例，再逐项实现。业务 API 在隔离 PostgreSQL 验证准备汇率无余额或 `HOLD` 变动、调低汇率后用户另发申请仍能取消原单、准备失败无提前开始、调汇率/取消/拒绝与 begin 并发单赢家、旧摘要/旧版本拒绝、USDT 来源按原报价/原冻结开始、原点钻兑换及 USDT 差额完整冲正、真实客服拒绝身份与链接账本证明、同幂等键重放、跨进程认领与管理员旧令牌失效；TronGrid 测试覆盖零/一/多候选、循环/缺页/限流/超时、错误合约或地址或金额、失败/过期收据、事件已占用、重叠订单以及手填/更正路径的最终归属门禁。前端测试覆盖普通客服禁用、仅所有者管理员新鲜验证及受控入口、返回/重调汇率、开始前地址不可读/开始后授权复制与失权清理、证据令牌不能再开始出款、拒绝和链上候选所有等待/空/错误状态。更新 OpenAPI、迁移、运行手册与拒绝原因词典；先领域/规格审查，再独立质量/安全审查。

生产只发布精确的业务 API 与后台静态文件，不重打 Android 包，不修改 iOS、钱包签名器、托管服务或已发生的账本事实。部署前核对当前镜像、0092 后续 schema、Compose、静态 SHA、前一钱包工作台及 Android 2193 API 协议；expand 迁移须经隔离恢复/回退门禁。发布后核对最新接口、权限拒绝、真实静态 SHA、健康/重启、匿名 401 和未改变的其他服务。无真实授权账号时不伪造生产资金写或声称客服交互已验。回退静态与 API 时保留新增拒绝/接管/候选、账本、审计和 Outbox 记录；不做破坏性 downgrade，旧客户端继续读兼容核心状态。历史已开始订单的恢复单独取证，不由本次部署自动解锁。
