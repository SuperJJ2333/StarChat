# 管理员提现与充值一致性设计

状态：待用户审阅；本文件不是上线或资金操作授权。
日期：2026-09-30（北京时间）

## 1. 目标及授权

用户要求：充值与提现 UI 一致；提现仅管理员处理；自动展示兑换后金额并提供 -1%、-5%、+1%、+5%；提现流程与充值相反，允许取消。
用户随后明确确认取消边界：未签名、未广播可撤销退款；已签名、已广播或结果未知时停止后续付款操作并复核，不能凭 TronGrid 尚未发现到账直接退款。
用户本轮授权整理正式设计及实施计划；实现和发布等待文档批准及规定评审。

## 2. 当前代码事实与方案选择

- `frontend/src/admin-recharge-panel.js` 已支持基准汇率、最终汇率、金额预览及基准百分比按钮；按钮每次相对基准计算，不连续累乘。
- `admin-support-payout-panel.js` 仍使用客服处理文案，只有汇率输入，没有对应的快捷按钮与实时预览。
- `SupportOrderSessionAuthorizer` 同时服务充值和提现，允许 FINANCE_SUPPORT；不能直接收紧此公共类使充值客服权限受损。
- 出款已有 REQUESTED、CLAIMED、UNKNOWN、SETTLED、CANCELLED、VOIDED；已有确认未广播撤销接口及原子账本冲回。

选择：复用充值样式和既有出款领域接口，增加提现专属管理员鉴权。继续使用既有官方钱包负责人约束：SUPER_ADMIN 且账号 ID 等于配置的 `wallet_manual_owner_admin_id`。不把本任务解释为允许任意管理员操作官方钱包。
仅隐藏客服按钮不能满足权限要求；复制一套独立资金引擎会增加账本分叉，因此均不采用。

## 3. UI 与金额口径

后台充值、提现采用一致的标题、筛选、订单摘要、处理弹窗、字段间距、按钮层级、状态反馈与北京时间格式。充值保留客服处理权限。提现标题统一为“提现订单”，操作文案使用“管理员”。

提现展示：申请点钻、基准汇率（点钻/USDT）、基准更新时间及过期状态、最终汇率、原冻结 USDT、最终应付 USDT、锁定收款信息。保留历史原报价与调整记录。

公式：`最终应付 USDT = 申请点钻 / 最终汇率`，ROUND_HALF_UP 到 6 位小数。点钻 2 位小数；汇率最多 6 位小数且必须为正，沿用现有领域上限和最低出款限制。
快捷按钮顺序为 `-5% / -1% / 基准 / +1% / +5%`。与充值相同，相对本次有效基准汇率计算；不相对当前输入累乘。允许手工输入合法最终汇率。
例：申请 200.00 点钻，基准 7.000000，基准应付 28.571429 USDT；+5% 得到汇率 7.350000、应付 27.210884 USDT。提高汇率会减少提现 USDT，界面必须明确展示方向。

前端使用整数定点计算，服务端 Decimal 为最终权威。缺失或过期参考汇率不虚构基准，禁用快捷按钮；仍允许管理员核对后明确输入有效汇率。已保存结算使用服务端冻结的最终汇率，不被刷新后的参考值覆盖。
只在实际付款指令生成前允许调价；任何已签名、广播、候选哈希、UNKNOWN 或终态订单禁止调价。开始付款必须绑定最新订单版本、报价摘要和最终应付；不复用调价前指令。
现有 USDT 本金旧单保留原金额口径，不伪造点钻或提供无意义的 FX 调整。

## 4. 权限及迁移中的订单

前端不给 SUPPORT_AGENT、FINANCE_SUPPORT、SUPPORT_SUPERVISOR 提现处理入口；客服的充值入口继续可用。提现列表、详情及所有人工命令由提现专属鉴权保护。客户自身的申请、本人订单查询和既有未处理取消权不受本次后台权限变更影响。

服务端在每个入口、领域写入及提交前检查实时管理员角色、官方负责人 ID、有效管理会话、账户状态和既有资金保护。不能仅相信 Token 历史角色、界面传入角色或旧领取 token。
金融写操作保留钱包写入权限验证及独立操作密码/TOTP。同一次最终资金确认不得把查看权限、领取权当成操作证明。不弱化既有恢复冷却、余额检查、审核及幂等保护。

已被客服领取但未开始付款的旧订单：管理员可通过明确接管动作原子撤销旧租约、保留领取历史、审计原因，旧 token 立即失效；不能自动删除历史或冒充原处理人。
已开始付款的客服旧单：禁止自动重领或重新付款；由官方负责人进入复核，保留原付款证据及处理人。原客服的历史 token 不再授权写入。
自动链上监控及最终结算持续运行，不依赖原客服是否仍有处理权限。

## 5. 取消与链上核验

| 状态/证据 | 管理员操作 | 资金结果 |
| --- | --- | --- |
| REQUESTED，付款尚未开始 | 经独立验证取消，事务内再次核对无执行、无候选/结算证据 | CANCELLED，按既有账本接口冲回冻结和本单原兑换 |
| CLAIMED 或 UNKNOWN，但明确从未签名、从未广播 | 使用既有 VOIDED 流程；负责人声明、最新链上预检、版本及独立证明全部通过 | VOIDED，原子冲回，保留领取历史 |
| 已签名、已广播、无法确认是否广播或已有候选哈希 | “停止处理并复核”，禁止新付款及调价；保留核验和提交证据能力 | 不退款、不标记已取消；进入/维持 UNKNOWN 及复核 |
| 已核验到账或 SETTLED | 禁止取消及冲回 | 维持既有结算 |
| TronGrid 不可用、扫描过期、有疑似匹配或金额/地址不符 | 显示具体预检原因，禁止未广播退款操作 | 保持当前冻结 |

已签名但未广播同样不符合“从未签名”声明；不能允许其进入未广播退款捷径。链上交易不能由后台按钮保证撤回。
“停止处理并复核”只停止本单新付款和调价，持续后台链上扫描；后续合法到账仍可按原单准确结算，不重复付款。不新建全局暂停，不恢复其他历史暂停。

所有退款复用钱包/账本公开应用接口；不直接跨模块写表。冻结金额变动与原兑换冲回须保持每资产平衡、追加式账本、唯一关联、幂等、actor/reason/audit/Outbox。余额不足以冲回既有释放差额时原子拒绝。
取消与到账核验、领取、调价并发时锁定同一订单并重新验证版本：任一只能提交一次正确终态。失败时不出现半笔退款或已取消又结算。

## 6. API、兼容及上线

保留现有 URL 和响应基本字段，限制授权属于明确的安全策略变更。扩展管理动作采用可选字段/独立接口，不让旧客户端解析新必填字段；终态 VOIDED 沿用当前旧客户端兼容投影。
管理响应新增可选 `allowed_actions`（服务端实时能力）和 `cancellation_block_reason`；前端据此渲染，服务端仍独立验证，不能信任前端能力列表。
不旋转签名身份，不要求重新发布 Android/iOS；本轮以后台及 API 最小增量发布。若发现移动文案需要变动，单独记录并按移动交付门禁处理，不在本轮静默打包。
发布必须从当时生产镜像及静态基线提取差异，保留已上线 OTP worker、结算参考读取、下载测速、客户端续期和其他并行功能。回退保留账本/审计和新增安全约束，禁止恢复客服资金写权限作为默认回退。

## 7. 验收

- W1：充值/提现样式及弹窗状态一致；加载、空、失效、成功、失败和关闭返回均可用。
- W2：所有客服角色及旧 token 访问提现后台被拒；官方负责人管理员可处理，充值客服不回归。
- W3：汇率自动填充、五个快捷按钮、手工输入、正反换算、精度、大数及服务端金额绑定正确。
- W4：REQUESTED 取消、未广播 VOIDED、已广播停止复核三条路径行为明确；不可凭扫描暂无到账退款。
- W5：真实 PostgreSQL 并发、重复请求、失效权限、链上延迟、扫描不可用及冲回不足保持资金与审计不变量。
- W6：旧 Android/iOS 合同兼容；最小发布、生产权限拒绝、资源哈希及独立管理员操作结果可追溯。
