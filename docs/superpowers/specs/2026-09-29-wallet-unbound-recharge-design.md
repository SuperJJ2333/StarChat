# 钱包未绑定时封锁新充值申请：设计规格

日期：2026-09-29（Asia/Hong_Kong）。状态：产品规则已获用户确认；ADR-0077 补充、领域审查与质量/安全审查完成前，不实施受保护的服务端资金规则或发布。本文件只定义本次钱包范围，不授权生产资金操作。

## 目标与边界

没有 **ACTIVE** 私人钱包绑定的账号，不能从钱包首页进入新充值流程，也不能通过认证 API 创建新充值申请。已有申请、历史、付款证据和幂等重放仍可查询、恢复和核对；状态不因当前绑定变化而改写。提现既有绑定门禁保持。余额、汇率、客服结算、账本、审计和 Outbox 的金额及状态语义保持。

本轮不创建充值订单、不实际付款、不修改生产数据。修改资金写门禁属于受保护变更，须批准 ADR-0077 的本次补充，并完成领域与质量/安全审查。

## 已核对的基线与根因

Android Debug 0.4.22（2191）的钱包首页在 `apps/mobile_flutter/lib/features/wallet/manual_wallet_page.dart` 中使用 `canDeposit = cnyPricing || (activeBinding && depositEnabled)`。CNY 计价时，未绑定也能打开充值页；该页的人工充值按钮只检查页面就绪及能力配置，`submitManualRecharge()` 没有绑定检查。

当前生产 API 容器镜像为 `sha256:0bdf751c05015454781c24b66a0c5066ca08ce23436c232ff8aecd1ba5042993`（2026-09-29 经配置跳板只读核对）。镜像内 `app/api/recharge.py`、`app/modules/recharge/service.py`、`app/modules/recharge/workflow.py` 与本任务工作树对应文件的 SHA256 逐一一致。`POST /api/v1/recharge/requests` 核验登录、官方付款配置、金额、幂等键和到账凭证，却未查钱包绑定；`GET /api/v1/recharge/official-payment` 只检查结算能力与官方地址配置。故在结算能力开启且官方地址可用时，已登录的未绑定账号从代码路径上可以创建 `SUBMITTED` 申请。此次未向生产发送任何写请求，不能将其表述为生产账号实测。

相邻路径已有不同门禁：`POST /api/v1/wallet/manual/deposit-intents` 的钱包资金服务在同一事务中锁定绑定状态，要求当前 ACTIVE 绑定、匹配版本且没有待激活改绑；旧托管 `GET /api/v1/wallet/deposit-address` 在手工钱包运行时返回 `WALLET_LEGACY_FUNDING_DISABLED`。`GET /api/v1/wallet/official-deposit-address` 和 `GET /api/v1/recharge/official-payment` 是认证只读地址展示，不能创建订单。点钻页的“充值”仅是余额用途说明或账单类型，没有独立的新申请入口。

## 交互与视觉方案 A

钱包首页沿用现有导航、间距、品牌色、明暗主题和触控尺寸。浅色模式用现有 `WeChatColors.elevatedSurface` 呈现白色卡片；深色模式沿用对应 elevated surface，不写死白色。

1. 未绑定或绑定状态未确认时，充值和提现快捷按钮禁用；`openSection()` 仍二次检查，避免只靠按钮外观限制跳转。未取得可靠绑定状态时保持禁用，不把能力配置成功误作绑定成功。
2. “请先绑定你的钱包地址”放在地址区的独立警示背景框，配警告图标与可读说明。警示只反映当前绑定状态，不能遮住余额或已有申请。
3. “绑定钱包”作为独立可点的 elevated 卡片，明确箭头、边界及至少 44×44 的触控区域，进入既有绑定流程。服务不支持绑定、页面忙碌等状态沿用既有禁用规则，不提供假入口。
4. 点钻余额使用钱包现有余额 hero 的数字层级（`WeChatTypography.brand`、等宽数字和超长缩放），清晰区分标签、数值、单位；与点钻页大号余额风格一致。只改排版，不改余额来源、精度或数值。
5. 已有申请的通知栏、申请详情、取消/证据提交及历史入口仍可进入。`openSection(..., recover: true)` 只恢复现有申请，不允许创建另一笔；无绑定时不展示新的“下一步/再次充值”动作。缓存中的旧 ACTIVE 状态仅改善展示速度，不能代替服务端提交门禁。

HTML 设计演示在 `frontend/src/catalog/screens.js` 的钱包 `home/unbound` 页面与 `frontend/src/screens/wallet-binding.js` 保持相同状态和文案；Flutter 与演示共用已有颜色、字号及组件语义，不引入仅在一端存在的样式。

## 服务端权威规则

`POST /api/v1/recharge/requests` 保持现有登录、金额、官方付款能力、幂等、审计及 Outbox 机制。在创建**新**申请的同一数据库事务里，经钱包域公开的绑定读取/校验接口确认该账号的绑定仍为 ACTIVE，且绑定状态/版本有效；遵守现有钱包锁顺序，并使检查结果与订单提交保持一致。禁止从充值模块直接写钱包表，也不能在事务外先读缓存状态后直接创建订单。与既有手工充值意图相同，待激活改绑时应阻止新申请，具体错误码在接口契约中明确。

先识别同一账号、同一幂等键、同一载荷的**已完成**请求并返回原回执，再对真正的新申请施加绑定检查。因此旧申请在后续解绑或改绑后仍可安全重放，不生成第二笔申请，也不丢失恢复能力。无 ACTIVE 绑定的新请求复用 `WALLET_BINDING_REQUIRED`（409），待激活改绑用 `WALLET_BINDING_PENDING`（409），版本冲突用 `WALLET_BINDING_VERSION_CONFLICT`（409）；失败事务不留下新申请、成功审计或 Outbox。提交成功后既有 `SUBMITTED` 记录、审计及 Outbox 与现在一致。现有申请的查询、取消、付款核验、人工核对及最终结算不因新申请门禁被阻断。

本轮只在新申请创建瞬间检查有效绑定，不为申请新增绑定版本列，也不改变已有申请与付款证据的状态机；无需数据库迁移。特别要用 PostgreSQL 并发测试验证提交与改绑交错，不以一个独立 `binding.status()` 网络/数据库预检声称事务一致。

## 验收与测试先行

- Flutter RED：CNY 配置 + UNBOUND/PENDING/首次绑定加载中时，“充值”不可点，不产生新申请请求；ACTIVE 时可打开并提交；旧申请入口仍能查看和恢复，且无绑定时不能启动另一笔。GREEN 后检查 warning、绑定卡、余额文字层级、暗色主题和语义标签。
- 服务端 RED：UNBOUND/PENDING/绑定版本失效的新幂等键均拒绝且无订单/成功审计/Outbox；ACTIVE 创建一次；绑定随后变化时同键同载荷仍返回原回执，不同载荷仍冲突；现有待核对订单保持可读、可核对；未登录仍为 401，跨账号不能读取订单。
- 在 PostgreSQL 16 上验证提交与绑定激活/改绑并发，且不产生死锁、错配订单或重复订单。保留既有手工充值意图门禁及旧订单恢复用例。
- 先规格符合性审查，再做金融领域与质量/安全审查；适用的 Flutter、服务端、OpenAPI 和仓库门禁依移动交付手册运行并记录真实退出码。发布需另按生产工作流取得对应授权，重新读取当时运行镜像和 schema；本设计的只读基线不是发布基线。
