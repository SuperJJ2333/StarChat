# Android 2196 UI, media and push regression design

Status: authorized by the user's seven 2026-10-03 requirements and standing explicit autonomous plan/ADR authorization. Baseline main9abe0520, released Android0.4.27/2196; released iOS2194, not the unreturned2196 resign candidate.

Goal: responsive message/keyboard/navigation UI under incoming/outgoing bursts; immediate cached image display; repeat big-image views prefer previously downloaded original; gallery-like bottom horizontal actions; ordinary pushes alert without bringing the app foreground and remain usable without a foreground Dart channel; inspect both platform delivery paths; install a corrected debug candidate on emulator-5556 without losing data.

Acceptance:
- R1: instrument/trace the message processing and rebuild hot path. Pin the identified redundant work with observable failing tests, preserve ordering, receipt/typing correctness and pending/error messages. Coalesce refreshes and isolate composer/navigation from full timeline work as warranted. No increasing retention limits to conceal memory growth. Debug animation speed is not production frame performance evidence.
- R2: warm local thumbnail bytes render in the first frame on room reentry, without waiting a fresh Future/disk/network path; misses load asynchronously. Account/room/content identity and revocation remain enforced; bounded completed caches, no unbounded Futures/bytes.
- R3: after an authorized explicit original download, reopening the same image/account defaults to original. A cold durable original may load automatically; synchronous completed originals show immediately. Never auto-network-fetch a not-previously-downloaded original, or retain state across account changes/revocation. Flash/one-time media excluded.
- R4: edit/download/forward buttons at bottom in one horizontal row, each icon with small text inside the button, match existing album viewer style/tokens. Original action remains reachable and unobscured. Real actions, errors, progress, safe-area and accessibility preserved. Flutter/HTML demo/registry parity.
- R5: investigate memory-pressure/background policy and token/pusher/APNs/Getui lifecycles. No intentional process kill as memory optimization; cache clear alone must not unregister push or stop its delivery. Diagnose live server aggregate logs/status/config without emitting payloads, tokens or identifiers. Native compile/contracts and platform test coverage mandatory; emulator cannot prove Redmi/iPhone OEM lockscreen endurance.
- R6: ordinary message/friend push must not start an Activity or become a full-screen intent on receive; opening app occurs only on explicit notification tap. CallKit/Telecom call presentation unchanged. Cold engine delivery cannot be solved merely by removing launchApp and dropping notifications. Preserve dedup, sound/preferences/mute and generic-only E2EE push bodies.
- R7: freeze debug source/version/package/signature/ABI; preserve-data adb install on observed online emulator5556, verify installed identity, launch/crash/notification navigation checks. No silent uninstall, data clear or downgrade. No production release required for this debug request.

Observed initial evidence: Android NativePushBridge.notifyFlutter calls launchApp when channel==null; this is a confirmed R6 defect. RoomImagePreviewCache already has bounded completed session bytes, so R2 must trace UI/source token/async snapshot and invalidation rather than assume no cache. ImageViewerPage state currently stores originalBytes in page state only; R3 requires content/account scoped preference and cached authorization. Installed emulator is com.liuhetong.mobile.debug0.4.24/2193, firstInstallTime2026-09-26; not2196.

Approach selected: repair existing cache/render and native push boundaries with focused behavioral tests, not enlarge caches or introduce a perpetual UI keepalive. A notification-only native fallback or headless dispatcher must honor current preferences and Matrix server mute, and be chosen after delivery evidence. Any necessary opaque-ID routing contract keeps backward compatibility; no E2EE/auth change allowed without separate ADR/domain and security review.

Alternative considered: global original-byte retention increases memory/privacy risk and is rejected; forced Activity launch as background keepalive causes R6 and is rejected; merely deleting Activity launch without cold notification fallback loses R5 and is rejected.

Verification: focused red/green; scoped/full Flutter analysis/tests once final inputs frozen; Android native actual unit/compile; iOS affected contracts/native CI when feasible; UI contract/frontend when changed; root verify preflight/missing-environment evidence; independent specification/domain then quality/security reviews; actual emulator install. Record platform/device and server gaps explicitly, no claims of physical 30-minute background acceptance without measurement.
