## 1. 资金路径与边界

用户明确的新架构：每个账户绑定一个由用户自行掌管的TRON私人钱包；平台不生成用户地址，不收集用户私钥或助记词，不实施用户地址到官方地址的自动归集。

**资金路径已获用户确认：** 绑定钱包作为充值来源和唯一提现目标。用户主动从绑定钱包转入官方统一收款地址；平台确认后给App内部USDT账本入账；提现由官方钱包转回订单锁定的绑定钱包。私人钱包内尚未转入官方地址的余额不属于App内部余额。

下文按已确认的资金路径设计；真实入账或付款仍须完成实施和对应验收。

```text
用户私人TRON钱包（用户自行签名）
    │ 主动充值USDT
    ▼
官方统一收款/付款钱包
    │ TronGrid发现与固化收据核验
    ▼
充值归属核验 → USDT复式账本 → 点钻兑换（既有独立门禁）
    │ 提现申请、冻结、双审批、独立签名
    ▼
申请时绑定的钱包地址（不可被后续改绑修改）
```

官方钱包持有充值资金时，平台仍管理这些资产并负有内部账本兑付责任；“用户用私人钱包”不等于平台无需保管官方钱包或无需提现签名。现有独立签名条件尚未具备，生产充提继续关闭。TronGrid只能查询/广播已签名交易，不能代替用户或平台签名。

## 2. 绑定与改绑

### 2.1 钱包控制权

- 校验TRON主网Base58Check；首版只接受能按约定消息签名协议证明控制权的自托管账户。交易所充值地址、别人提供的地址不能仅凭填写或截图绑定。
- 后端签发一次性挑战：业务域名、网络、用户内部标识、会话、动作BIND/REBIND、规范地址、旧绑定版本、随机nonce、签发和到期时间。挑战有效期5分钟，验签成功与nonce消费在同一事务完成。
- 客户端调用钱包的消息签名能力，后端恢复签名地址并与挑战地址一致校验；优先采用TronWeb signMessageV2/verifyMessageV2协议及独立测试向量。签名消息明确写“仅证明绑定，不授权转账”。拒绝用approve授权代替绑定证明。
- 自定义TRON账户权限、多签或合约钱包不能直接套用普通单密钥地址恢复；首版不自动支持，需独立权限验证方案。
- 改绑需近期真实MFA、证明新钱包控制权；正常路径同时证明旧钱包控制权。旧钱包丢失走独立恢复案件、不同人员复核及资金限制，不通过客服直接改表。
- 一个用户最多一个ACTIVE绑定；同一地址不能绑定给不同用户，包括历史已使用地址，避免地址归属被转让后追认旧交易。同一用户可在满足间隔及重新验签后换回自己的历史地址。

### 2.2 滚动30天

- 使用服务端UTC、精确30×24小时，不按自然月或客户端时间计算。
- 首次绑定不计作“改绑”。第一次成功改绑后记录`last_rebind_at`；下一次允许时间为`last_rebind_at + 30 days`，恰好到达允许时间可操作。
- 即任何滚动30天区间内最多一次成功改绑。挑战请求、失败验证、重复请求和同地址幂等重试不消耗次数。
- 没有“先解绑再绑定”绕过入口；删号重建、清客户端缓存、换设备不重置审计历史。跨账户关联风险另走风控，不承诺仅凭地址限制解决所有关联账号问题。
- 同一用户并发改绑采用事务行锁/CAS，旧版本必须一致，只允许一个请求成功；绑定变更、审计、Outbox、nonce消费原子提交。
- 安全恢复不静默豁免30天限制；旧钥丢失可冻结处理，但不能靠恢复案件立即重置`last_rebind_at`。
- API返回`next_rebind_at`及固定错误码`WALLET_REBIND_TOO_SOON`，客户端显示准确下次时间。

### 2.3 改绑与在途资金

- 存在SUBMITTING、UNKNOWN、已签名/已广播提现时禁止改绑，直到确定终态。
- 改绑提交与提现取得SUBMITTING/签名提交资格必须锁定同一用户钱包控制行并校验同一binding_version/epoch；在一个事务内完成状态检查和CAS，不能把“查无在途”与“实际改绑”拆开。哪一方先获得资格，另一方必须拒绝并重新读取状态。
- 未提交的提现须先明确取消、释放原冻结，再改绑；不得把旧审批或原订单改成新目标。
- 所有充值意图和提现订单保存`binding_id/version`、原地址引用和规则版本。改绑追加历史记录，不覆盖旧记录。
- 改绑时原版本未完成充值意图原子关闭为`CLOSED_BY_REBIND`，停止接受新付款匹配，但保留其原始版本和已经发现的事件。新版本可新建意图，不受旧已关闭意图占用；旧意图迟到款进入核查，不能自动挂到新意图。
- 绑定区间按区块高度使用左闭右开`[effective_from_block, effective_to_block)`。切换屏障保存高度H及block_id；经认可固化与来源校验后，旧版本结束于H+1、新版本开始于H+1。尚未验证的切换保持PENDING，不展示新版本可充值；失败不计成功改绑次数，保留申请审计。
- 充值归属同时检查绑定区间与原充值意图的生效边界，不能仅检查地址；绑定区间不明确、屏障失效、旧地址在退役后转入、无有效意图等进入人工核查，不按扫描时间或当前绑定倒推历史归属。成功改绑冷却从激活事务的服务端时间开始计算。

## 3. 金额规则

| 项目 | 规则 |
|---|---|
| 最低充值 | 单条有效USDT Transfer实际进入官方地址的金额≥10.000000 |
| 最低提现 | 用户期望到账本金≥10.000000；网络费/服务费单独报价并加计冻结，不从这10USDT中悄悄扣减 |
| 计量 | 最小单位整数或Decimal，6位；接口金额为字符串 |
| 等于10 | 允许；9.999999拒绝正常充提处理 |
| 多笔小额 | 不自动拼成一笔达标充值；同笔交易多个日志逐条核验，不按交易总额冒充每笔达标 |

提现最小额不改变现有单笔上限、滚动限额、储备约束及手续费确认。新规则不追溯撤销旧版已入账记录，历史订单按快照规则处理。

充值无法从链上阻止小于10USDT的转账。小额已到账款记录为`BELOW_MINIMUM_REVIEW`并保留待处理义务，不记平台收入、不丢弃；人工处理或退款走既有审批和签名流程，不承诺自动退款。界面须在转账前说明小额无法正常自动入账。

## 4. 统一地址充值归属

1. 用户登录并具备有效绑定，创建充值意图，绑定用户、钱包版本、官方地址配置版本及规则快照；展示官方地址、二维码、USDT-TRC20、最低10及“必须从已绑定私人钱包转入”。真实地址由业务API受控下发，不硬编码源码。
2. 用户在自己的钱包里主动签名转账；App不掌握私钥，不接收助记词。二维码只编码目标地址，不证明收款方身份，显示文字必须与二维码一致。
3. TronGrid发现官方地址相关交易后，独立读取固化收据；解析固定USDT合约的Transfer日志。用日志`from`作为代币来源，不误用交易发起者或客户端申报地址。
4. 核对日志`to`为官方地址、`from`与有效绑定及意图一致、金额≥10、执行成功、区块/时间和确认阈值满足政策、事件未入账。没有匹配意图或绑定时进入悬账，用户提供txid仅帮助定位，不自动认领。
5. 同一来源地址匹配多个未完成意图时不得重复入账或按金额随意配单，进入`ATTRIBUTION_REVIEW`。允许一个用户最多一个有效充值意图以减少歧义；过期、少付、多付与迟到款保留原证据并审核，不覆盖订单金额。
6. `CONFIRMED→CREDITED`经公共账本接口在单事务内完成资金分录、事件唯一标识、充值订单、审计和Outbox。并发扫描及重试最多入账一次。

标准唯一键仍为`(network, contract, txid, log_index)`。事件归属在首次入账时固定，不能因改绑重新分配。充值截图、客服消息或单独知道txid都不是资金凭证。

## 5. 提现

- 用户只能选择当前已验证绑定钱包，不提供任意目标地址输入框。API不信任客户端target，服务端从绑定版本生成目标及不可变订单摘要。
- 本金≥10、费用有效、可用余额与限额/储备足够后冻结总额；双人审批不同身份，摘要覆盖目标、绑定版本、本金、费用上限、官方钱包配置和熔断epoch。
- 签名前重验绑定仍有效、审批未失效、暂停与限额。独立签名方再次核对摘要与策略，不能只信任API“已审批”标记。
- 未提交可撤销；提交/签名/广播后结果未知继续冻结和查询原意图，不重复支付、不超时退款。已完成链上付款不能撤回。
- 同一官方钱包不产生专属地址归集任务；资源/TRX费用预算仍由平台维护。公开钱包余额不得直接当作可用兑付储备，须证明平台控制权并扣除应付款等占用。

## 6. TronGrid监控与对账

TronGrid是指定发现/查询入口；复用已部署reader的官方合约校验、固化收据、真实日志索引、分页、重叠回扫、截止水位、限流/超时和错误脱敏。现有只读观察器仍保持单独数据库。

业务监控重点是“官方地址↔绑定地址”的充提，不把用户私人钱包向无关地址的支出当平台提现或扣减App余额；如展示私人钱包全部流水，应单独只读标记，不与内部余额混合。

新增监控指标：未绑定来源转入、小额/迟到款、绑定边界冲突、未匹配官方转出、重复事件冲突、索引落后/游标失败、长时间未固化、余额变化与业务凭证不符。报警包含内部事件引用，不输出完整地址或签名消息。

**保留最终性门禁：** “用TronGrid监控”不自动废除现有双独立来源入账要求。TronGrid的history与receipt接口属于同一来源；现有SOURCE_MATCHED只是观察级核对。若要改为单来源自动入账，须单独明确风险决策并审阅，不能在本次架构修改中默认放宽。第二来源未接入时仍可持续监控，但不开放自动入账。

对账取消“各用户地址归集”维度，改为官方受控钱包链上资产、内部USDT/可兑付点钻负债、已确认待入账款、提现占用及独立出款记录之间的核对。私有钱包链上余额属于用户外部资产，不计作平台储备或App可用余额。

## 7. 数据与API目标

- 新增绑定挑战、不可变绑定历史、当前绑定版本、last_rebind_at、nonce消费及充值意图记录。
- 当前绑定与地址历史有数据库唯一约束；所有地址只保存在受权限保护的配置/表，不写普通日志。
- `GET /wallet/binding`：当前掩码地址、版本、绑定状态、next_rebind_at。
- `POST /wallet/binding/challenges`、`POST /wallet/binding/confirm`：挑战与验签；确认要求幂等键、近期MFA及版本条件。
- `POST /wallet/deposit-intents`：创建绑定来源的充值意图；返回官方收款信息与最低10规则。
- `/wallet/config`新增`min_withdrawal`、`binding_required`、`rebind_interval_days=30`，`min_deposit`改为`10.000000`；前后端同源。
- 提现请求引用binding_version，目标由服务端确定。旧版任意地址提交不得悄悄接受；契约升级或客户端版本门禁先完成。
- 旧`/wallet/deposit-address`不再分配地址。兼容阶段明确返回官方统一地址、地址类型与绑定要求，不沿用“已生成专属地址”的文案。

上述是目标契约，OpenAPI及生成客户端随正式代码实施一起变更，本次不伪造为已上线接口。
