# iOS 换签后的 Matrix 历史恢复设计

**状态：待用户审阅书面规格；未实施。** 2026-09-28 用户批准“保留旧 App、为未来提供用户持有恢复码的加密备份与可信设备迁移、制作可并存测试包”的方向。本规格补充同账号新登录会删除旧 Matrix 设备的约束。

## 1. 目标与事实

- 畅聊业务账号由 Business API 的用户 ID、登录标识和 Matrix 用户 ID 确定，不以 Apple Team ID 为账号主键。新签名应用可以认证同一业务账号；服务端聊天事件仍是 Matrix 密文。
- 旧企业签名 Team 为 ZXB3TS7QD4，新签名 Team 为 A9HAF6NT6S。旧签名 iPhone 尚未覆盖，旧 App 仍能读历史。旧 Team 已不可用；用户没有 App 外保存的 Matrix 恢复密钥，也没有其他持钥设备。
- iOS 的普通 Keychain 访问组来自签名授权；现有 IOSSecureSession 没有显式共享组。新 Team 无权读取旧 Team 的默认组。旧 Matrix SQLCipher 数据库密钥在该组，重新登录不能自动打开旧库。参见 [Apple TN2311](https://developer.apple.com/library/archive/technotes/tn2311/_index.html)及 [Apple DTS 说明](https://developer.apple.com/forums/thread/706128)。
- 已发布旧 2189 没有可由用户进入的密钥导出或设备验证入口。当前 MatrixSecurityPage 的“加密备份”方法只创建 SSSS 密钥并缓存，不创建、上传及核验完整房间密钥备份；backupKeyMatchesCurrentVersion 只检测本地缓存。不能据此声称旧历史已备份。
- 当前 Business 新登录撤销旧 RefreshTokenFamily 和设备；Synapse 移动登录撤销其他令牌并删除其他 Matrix 设备。两个不同 Bundle ID 的 App 可以安装并存，**同账号同时在线不受支持**。在新包中登录真实旧账号可能使旧 App 失去在线传钥资格。参见 Business tokens.py、matrix_sessions.py 与 Synapse chatflow_mobile_login.py。
- 2026-09-28 官方下载及 OTA 入口已依用户授权切到新 Team 的 0.4.20/2189 包；同 build 不触发已安装用户的更新弹窗。该发布只验证分发元数据，未验证真机覆盖、旧聊天解密或 APNs。本规格不修改已发布入口。

本设计解决**以后**签名、重装或设备变化时的历史密钥恢复，并验证新 Team 独立 App 的安装行为。它不保证把当前旧 2189 的所有聊天迁入新 Team。若旧 App 无可用在线备份、第二持钥设备或外存恢复码，服务器不能从密文倒推出房间密钥。本机草稿和未同步缓存也不在 Matrix 房间密钥备份范围内。

## 2. 方案取舍与阶段

| 方案 | 能做什么 | 结论 |
| --- | --- | --- |
| 新 Team 直接覆盖旧 App，重新登录 | 恢复业务账号和服务端密文 | 无法读取旧 Team Keychain；可能留下打不开的旧 SQLCipher 库。不能作为历史恢复方案。 |
| 服务器持有恢复密钥 | 允许服务器代解密 | 破坏端到端加密边界；拒绝。 |
| 客户端加密房间密钥备份＋用户外存恢复码 | 新设备由用户输入密钥后恢复可解密历史；不依赖 Apple Team | 推荐先完成。必须证明 Matrix 备份覆盖及冷设备恢复。 |
| 已验证设备传钥 | 对未来两端都支持迁移的账号减少手输 | 现行单设备策略删除旧 Matrix 设备。需另做受保护的迁移认证设计；不能回填旧 2189。 |

阶段 A：真实加密备份与恢复实现，可先在 Android/同签名测试设备做功能验收。阶段 B：新 Bundle 测试包及跨新 Team 的真实设备验收；A 的跨 Team 验收依赖 B 签发，二者共同完成后才能宣称新流程通过。A、B 使用独立测试账号，不改变生产单设备政策。阶段 C：未来可信设备交接的认证与协议设计；C 不属于 A、B 的发布完成条件。批准总体方向不等于授权临时放宽单设备登录策略。

数据流：持钥客户端在本机加密 Megolm 房间密钥并上传 Matrix 加密备份；用户在 App 外保存恢复码；新设备下载密文，仅在本机用用户输入的恢复码解密，再验证早、中、近期历史。Business API 只负责账号与资金，Matrix homeserver 只保存规范的客户端加密备份及必要元数据。新设备生成自己的 Olm 身份和 SQLCipher 密钥，不复制旧设备数据库密钥。

Business API、Synapse 明文接口、日志、性能埋点、推送、验收记录不得取得恢复码、SSSS 私钥、备份私钥、Olm/Megolm 密钥、SQLCipher 密钥、消息或附件明文。服务端不得凭业务密码恢复历史。

## 3. A：用户持有恢复码的加密备份

1. 已登录且当前本机可读 Matrix 密钥时，先读取现有 SSSS 与 room-key backup version、算法、公钥和覆盖情况。可证明属于当前账号的已有备份可复用；未知、不匹配或部分配置不得自动覆盖、重置或轮换。
2. 需要新建时，仅在客户端安全随机生成高熵恢复码与备份私钥。经 Matrix SSSS 加密保存备份私钥，创建标准加密房间密钥备份版本，逐批上传现存与新增 Megolm inbound sessions。上传实现须处理 SDK 吞掉错误的路径；离线、超时、限流、中断、版本变化及部分上传不能报成功。
3. 客户端从 Matrix 读回备份版本、算法、公钥、计数与加密房间/会话清单，按 room_id、session_id 和 first_message_index 核对**本设备目前已持有**的 inbound sessions；必要时下载样本密文在本机解密。Matrix 备份不能包含本设备从未拿到的密钥，计数或抽样也不能证明全部历史可恢复。仅将最小脱敏状态写诊断，不上传会话 ID 清单或密钥。新增会话持续增量上传并重新校验覆盖。
4. 向用户显示恢复码，明确要求在 App 外保存。按 ADR-0007 仍可将恢复码安全缓存于本机 Keychain 供同机使用；经用户完整重输确认的 App 外副本是跨签名恢复的**额外条件**，仅有本机缓存不算独立恢复能力。关闭页面后不在通知、自动剪贴板、后台快照或日志回显。系统截图无法保证完全阻止，界面应提醒私密保存。
5. 生产界面显示“本设备已知密钥已备份 X/Y，恢复码已确认”及已知缺口；另行区分“已在新设备验证”。重输恢复码仅确认用户记录一致，不证明服务器备份可解。须拒绝缺失或无效 IV/MAC 的 SSSS 元数据，实际用该码解出备份私钥、推导公钥并与当前备份版本匹配；不能仅依赖 SDK 的 unlock/checkKey 返回或本机缓存。验收须在隔离测试或用户主动的可信新设备上，用全新 Matrix 设备和空本地库输入恢复码，逐个 room_id、session_id、first_message_index 对账导入清单并实际解密早、中、近期样本；抽样只证明密钥正确性，X/Y 也不是账号全部历史的覆盖率。
6. 状态至少有未配置、等待用户确认、上传中、待验证、已知密钥已备份、需要恢复码、恢复中、部分恢复、失败。状态由当前版本和本机已知密钥覆盖决定，不能由按钮点击或 SDK 返回直接置为成功。失败保留可重试状态；错账号或 homeserver 的材料不得混用。密钥重置、备份替换及跨签名身份旋转须显式确认及独立受保护评审。

## 4. A：新设备恢复与旧库保全

**顺序换机门禁：** 未来具备本功能的来源 App 应有“准备换机”入口。在来源设备仍有效且持钥时，先完成恢复码 App 外保存与重输、本设备已知入站会话 X/Y 全部持久化、待上传队列清空、当前版本/公钥和服务端库存逐会话读回；再以用户重输的恢复码、隔离的临时解密环境逐条下载并解开服务端读回的每个已知加密会话，核对 room_id、session_id 和 first_message_index，不能偷偷复用本机缓存密钥。全部逐项通过时才显示“本设备已知密钥可切换”；若仅能抽样、存在缺口或核对中断，只能显示“已上传，尚未逐项验证”与具体缺口，并提供“了解风险后继续”，不能标为受保护。同账号在独立设备上登录会撤销来源设备，不能把真实账号“先冷恢复测试”伪装成无副作用的预检；真正跨设备冷恢复在专用测试账号验收，真实账号仍有剩余风险。目标新设备在**提交账号密码、验证码或其他 Business 登录请求之前**明确提示：这次登录会撤销旧业务会话并删除旧 Matrix 设备；来源设备可能因此失去补传和在线传钥能力。用户可返回旧设备完成来源端步骤；若没有恢复码仍决定使用新 App，须单独确认历史可能无法解密后才提交登录。上述检查仅覆盖来源设备已持有的密钥，不能承诺未知历史均可解。

新 Team App 完成 Business 认证后校验 Matrix 用户 ID、homeserver 和备份所属账号。全新设备使用自己的 Olm 身份、SQLCipher 库和密钥。用户输入恢复码，仅在本机验证 SSSS 元数据必备的 IV/MAC 与完整性、实际解出备份私钥并推导公钥对上当前备份 version/算法；SDK unlock 返回本身不算验证。然后下载加密房间密钥，解密、校验并导入。对不可解的历史段明确报告覆盖缺口，不把“能登录”写成“历史已恢复”。恢复历史房间密钥与新设备交叉签名信任是两个独立状态：须单列“历史可读/设备已验证”，校验 cross-signing 身份并完成新设备签名或可信验证后才允许依赖受信任设备策略分享后续密钥；未验证时不显示完整恢复。成功后才开启增量备份。

设备上若已有旧加密库却拿不到对应 Keychain 密钥，保持 local_identity_preflight 的失败封闭行为。只有设备已解锁、Protected Data 可用，且原生查询明确返回 errSecItemNotFound，才可把对应 Keychain 项判为缺失；errSecInteractionNotAllowed、首次解锁前、锁屏暂不可读及其他 OSStatus 均应报暂不可用/错误并允许解锁后重试，**不得**进入新槽或登录恢复分支。现有 matrix_startup_client 会在 missingKey 时中止，现有归档入口也要求旧绑定和密钥可读；因此须新增受保护的安全登录壳，先只读检测旧加密文件，把归属视为**未验证**，不打开、不清除、不覆写、不把新随机密钥套到旧库，不能直接复用现有归档入口。用户完成 Business 认证后，界面说明旧加密文件仍保留、但新 Team 不保证能重新打开；可用外存恢复码尝试恢复服务器密文。只有用户明确确认“以新设备身份开始”后，才可在不改动旧文件、可回退的独立本地槽建立新库。原旧库清理仍依既有 ADR；本规格不授权静默清库。这个分支目前**不是现有能力**，必须另以同 Bundle 缺钥场景验证。

## 5. B：新 Team 并存测试 IPA

- 仅供内部验收，使用新 Team 下**单独注册且与签名匹配**的 Bundle ID、application-identifier、provisioning profile 和默认 Keychain 组；新 Bundle 对应独立 App Support 容器。不得沿用现有 (13) IPA 的 Bundle ID / application-identifier 不一致状态。旧 App 不覆盖、不卸载、不清数据。
- 测试版关闭正式更新入口；自定义 URL scheme、Universal Links、APNs/VoIP topic 和 Matrix pusher app_id 不复用旧生产身份。初次验收可不注册推送与来电，直到新 Bundle 的独立配置和凭证通过验证。测试包不切换官网或 OTA。
- 首轮先在可丢弃的测试 iPhone 上使用**两个不同的无余额测试账号**：旧签名 App 用账号 O 建立测试历史，新 Team 并存包只用账号 N 安装、启动、登录、聊天、备份、冷恢复、冷启动及锁屏/重启；卸载新包后确认旧 App 的账号 O 仍能打开其测试历史。O、N 均与真实旧账号分离；不能让新包以 O 登录，否则单设备策略会主动顶掉旧测试 App，使容器隔离验收失真。财务状态不参与。若尚无第二台可用 iPhone，真机验收保持未完成，不把唯一可读旧历史的设备当成首轮试验设备。
- **不得为“试一下能否恢复”而在唯一旧 iPhone 的新包中登录真实旧账号。** 现行 Business/Synapse 单设备策略会撤销旧会话、删除旧 Matrix 设备；安装并存不等于账号在线并存。真实账号切换须先做可恢复性审计、明确失去旧设备在线资格的影响，制定单独真机验收。即使回旧 App 重新登录，也不能事先保证原 Matrix 设备状态恢复。
- 新 Team 签名方须提供测试 Bundle 对应的 App ID 和 profile，签发最终 IPA 并确认 Bundle、Team、entitlements、期限与包内一致性。构建侧交付候选和验证清单，不在仓库保存签名密钥。Windows/模拟器检查不能代替真实 iPhone 企业安装反馈。

## 6. C：可信设备交接的后续门禁

对**未来有可达安全 UI 的两端客户端**，本 ADR 选择在新端替换登录**之前**完成由旧端主动确认的本地端到端交接方向：旧端确实持钥，双方通过近场/二维码配对并逐端确认临时身份和短时会话；新端只把恢复秘密暂存在隔离安全存储，完成受控登录后再核对稳定 MXID、备份版本及公钥，错配即销毁暂存秘密。具体配对、防重放、期限、撤销及错误处理须另写受保护规格和安全评审；不能把密码登录或配对动作本身视为已恢复，最终仍须逐会话对账与历史解密。现有 Matrix to-device 房间密钥分享仅适用于两端确实同时是有效、已验证设备的场景；直接分享房间密钥不要求有备份版本，分享 SSSS/备份私钥才核对版本与公钥。

现行同账号新登录会删除旧设备，并发 Matrix 传密在当前认证策略下不能交付。阶段 C 不开放限时双设备登录例外，也不修改现有 revoke_others/delete_device；如以后考虑并发迁移，须另立认证策略 ADR。登录前交接必须覆盖撤销、过期、设备绑定、审计及滥用测试，并经过认证与 E2EE 的批准 ADR、领域及质量/安全评审。旧 2189 没有可达发送端 UI，该阶段不能作为其历史的普遍补救。

## 7. 验收、回退与交付

| 场景 | 必须观察到的结果 |
| --- | --- |
| 新账号备份与冷恢复 | 使用独立测试账号先从可持钥的 Android 或新 Team iOS 建备份，再到空数据库的新 Team iOS 恢复；本机已知密钥逐会话清单与 first_message_index 对账，早、中、近期样本解密。旧 Team 2189 到新 Team 的真实历史恢复不在此项冒充通过，须逐账号判定。 |
| 已有备份与版本变化 | 正确复用；错误公钥、算法、账号、homeserver 或部分覆盖时暂停，不覆盖旧备份。 |
| 异常 | 错误码、离线、超时、429、SDK 吞错、上传中断、错码与备份缺段均可重试或报告缺口；旧库和 Keychain 不被清除。 |
| 恢复码与信任 | SSSS 元数据缺失 IV/MAC、错误 MAC、SDK 吞掉 unlock 后续错误、备份私钥与公钥不匹配均失败关闭；历史会话导入成功但设备未获可信签名时分别展示并限制后续受信任密钥分享。 |
| 并存包 | 新 Bundle、Team、entitlements、profile 匹配；在可丢弃测试设备上，旧 App 账号 O 与新包账号 N 分开，N 登录及卸载新包不影响 O 的本机测试历史；推送/来电仅在独立配置后验。 |
| 同 Bundle 旧库缺钥 | 分别注入 errSecItemNotFound、errSecInteractionNotAllowed、首次解锁前和其他 OSStatus；仅真实缺失进入安全登录壳，暂不可读只能解锁重试。非唯一持钥真机验证旧文件字节保全和明确新设备选择；独立 Bundle 测试不能代替此项。没有合适真机时该项保持未验证，不触碰唯一旧历史设备。 |
| 单设备政策 | 真实旧账号不用于首轮测试；另以专用账号 P 和可丢弃设备证明新登录撤销/删除旧设备，不将该测试混入 O/N 的并存隔离验收。 |

用户书面审阅后，先对 E2EE 与启动安全路径完成 ADR 的 Domain、Quality/Security 设计评审并标记批准，再进入受保护代码实现。实现遵守红/绿测试、focused tests、静态检查、适用完整门禁及真实 Synapse 集成测试；发布前再做规格符合性及 Domain、Quality/Security 代码审查。生产下载入口、更新弹窗、备份服务和单设备政策分别核对授权；测试 IPA 不自动进入正式分发。故障时保留旧设备、旧包、旧备份版本和加密库，只撤回新增入口，不删除历史密文或恢复材料。
