# Android 提现报价策略兼容修复设计

- 日期：2026-09-29。
- 范围：Android v0.4.21+2190 的人工钱包提现报价解析与下一版 Android 交付。
- 用户授权：用户确认“批准客户端兼容方案”；书面规格与实施计划按项目规则继续审阅。

## 问题与证据

Android v0.4.21+2190 的 ManualPayoutQuote.fromJson 只接受 approval_policy=OWNER_MANUAL_V1，遇到其他值时抛 FormatException("Invalid manual wallet response")。生产业务 API 已启用客服处理订单，成功的 POST /api/v1/wallet/manual/payout-quotes 响应含 SUPPORT_MANUAL_V1。用户按“获取提现报价”后，客户端把成功响应误报为无效。正式 2190 冻结清单和相应源文件 SHA 已核对；服务端当前镜像、源文件 SHA、开关和路由已只读核对。生产配置开启 PAYOUT_REQUESTS_ENABLED；当前容器安全聚合中有报价 HTTP 201，说明接口向已登录用户开放。聚合日志不按用户归因，不能据此判断某个用户的历史订单。

客户端在 POST 前保存报价操作的金额、绑定版本与幂等键；解析失败时没有保存报价 ID。再次点击沿用原键并取回同一报价，因此旧版会重复出现该提示。报价成功本身不冻结资金；用户确认并成功提交 POST /wallet/manual/payouts 后才可能产生冻结。历史账户状态仍以业务 API 记录为准。

## 决策

仅修复 Flutter 人工钱包报价模型的 approval_policy 解析：明确接受 OWNER_MANUAL_V1 与 SUPPORT_MANUAL_V1，保留原值供页面及后续逻辑使用；空值、未知值和其他字段格式错误继续拒绝。客户端仍在解析成功后保存报价 ID，之后按原有报价到期、支付授权、MFA、幂等键和钱包会话范围规则进入“确认提现”。此修改不改变业务 API 响应、真实客服审批路径、服务端状态机、账本、鉴权、限额、迁移或 OpenAPI。

下一 Android 版本从正式 2190 冻结输入构建，先核对全部移动端输入与冻结清单。不得把主工作区当前大量未提交改动或别的任务分支整体带入。候选版本号/build 取实时未占用的递增值；用户已安装 2190 的固定签名身份必须连续。构建先走源码 APK，再按固定 Apktool/zipalign/签名/包体门禁产生最终 ARM64 正式包。生产发布前读取实时 Android/iOS 设置与渠道状态，按既有不可变文件和轻量发布门禁验收；iOS 及其他平台设置保持其当时真实值。

## 验收

1. 用正式 2190 报价样本先证明 SUPPORT_MANUAL_V1 在旧解析器失败；修复后两个已知策略均成功，未知策略仍失败。
2. 模拟 HTTP 201 客服报价：客户端展示金额、费用、收款地址和报价到期信息，保存报价 ID；同键重试或恢复不会重复创造资金申请。
3. 保留支付确认门禁：仅获取报价不调用 POST /wallet/manual/payouts；用户确认仍需现有支付授权/MFA，失败及结果未知按原键恢复。
4. 对受影响 Flutter 专项、共享相关门禁及 Android 包体/签名/升级路径给出实际退出码与 SHA；发布后核对 HTTPS、版本设置、不可变 APK、官方入口与旧包回退可用。没有真实用户凭证时，真实账户提现交互单列待验收，不用匿名探针或合成数据冒充。

## 边界与回退

不把服务端 SUPPORT_MANUAL_V1 伪装成旧策略，不仅隐藏报错，不自动重试财务写入，不清理用户本地待恢复操作。发布失败保留 2190 正式包及设置备份；已形成的服务端报价、申请、审计和账本不能通过客户端回退删除。监控和用户订单查询仍走业务 API 权威数据。
