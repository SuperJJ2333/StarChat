# Scoped native message notification fallback

Date: 2026-10-03. User has explicitly approved autonomous ADR/plan decisions; this decision requires independent domain and quality/security design review before implementation. Implementation and device acceptance are separate gates. Scope: ordinary Android message push; existing call signaling, iOS APNs transport and business authorization remain separate.

## Problem and evidence

NativePushBridge starts MainActivity when no Flutter channel exists. Removing that call alone would lose the only cold wake path: the current Dart fallback requires a running coordinator and is silent. AppHome also acknowledges wakes before the coordinator is ready. The existing type-only push cannot identify a room for local mute policy or an event for deduplication. Memory-pressure handlers clear caches; they do not intentionally kill the app or unregister pushers. Production Getui transient retry defects have already been repaired under a separately reviewed deployment.

## Decision

1. Ordinary receive may enqueue bounded wake state and show a generic system notification through the account's current policy. It must not start an Activity, use a message full-screen intent or request UI focus. Only a valid, explicit notification tap may enter the existing router. Native calls keep their existing authorized caller flow.
2. A new Android Matrix pusher opts into `chatflow_push_v=1` with `chatflow_push_scope`: a securely random, fixed64-hex nonce persisted for the current authenticated account session. Cold restart reuses it. Logout/account change disables native message delivery and clears pending notifications/taps first, then rotates scope before network deregistration/reconciliation. Registration occurs only after the current local policy mirror is installed. The nonce is an association token, never a bearer credential or authorization grant.
3. Only valid v1 ordinary-message push may add `scope`, `room_key`, and `event_key` to the existing type field. Association keys are SHA256 of UTF8 `scope + NUL + raw Matrix identifier`, represented as fixed64 lowercase hex. Raw room/event IDs are discarded before provider transmission. A truly legacy pusher without opt-in retains type-only compatibility; calls retain their existing shape. An opted-in malformed/unsupported v1 pusher never downgrades to a legacy vendor alert. Message plaintext, sender/room names, attachments, financial state, E2EE/recovery keys and authentication tokens remain forbidden.
4. Native storage mirrors only notification policy and account/session association: global enabled/sound/DND choices, locally effective room mute state and bounded dedup/wake state. No message content or raw room/event identifier is needed. A received association must match the currently enabled scope; stale scopes and stale-account taps are rejected. Keys select existing local policy and dedup state; they do not grant room membership or decrypted-media access.
5. The Dart/native handoff is acknowledged only after a ready consumer assumes responsibility. Native fallback and later Matrix handling share event association and suppress duplicate alerts without dropping the Matrix message itself. State is bounded and expires; disposal/revocation clears ownership and cannot publish late work into a new account.
6. Policy mirroring and pusher reconciliation happen on actual account/policy/room-mute changes, not by rebuilding every room on each message sync. Offline/failed reconciliation remains pending and retries through the existing lifecycle. v1 currently uses transmission only and omits vendor OS-rendered notifications, because that direct-display path bypasses local policy and scope validation. Truly legacy/call vendor output is unchanged. Enabling v1 vendor output requires a separate official-provider policy/scope review and actual configuration evidence; a server snapshot cannot revoke an already queued alert or enforce a preference changed while offline. This explicitly leaves process-killed/vendor-only OEM delivery unaccepted; native fixes and debug delivery are not proof of full R5 completion.

## Conditions incorporated from independent design review

Review: `docs/verification/artifacts/2026-10-03/mobile-ui-push-2196/push-metadata-design-review.md`, domain first then quality/security, D1–D4/Q1–Q3. The following are implementation requirements, not claims of passing implementation tests.

- v1 target association is per Matrix pusher device. Never select one device's scope for all CIDs or spread untrusted pusher data into provider JSON. Conflicting duplicate-CID scopes fail closed. Strict integer version excludes bool; scope/keys require64 lowercase hex. Gateway body256KiB/devices100/raw identifier1024 UTF8 bytes/native JSON4096 bytes are engineering caps. Invalid or oversized values are rejected without emitting them in logs.
- Scope uses32 cryptographically secure random bytes, bound to account and authenticated session epoch in app-private durable storage. Startup starts native delivery disabled until authenticated preparation; engine teardown releases consumer ownership without revoking the current background account. True logout/auth revocation/account change revokes native eligibility, notifications and pending taps before network awaits. Late policy/registration/tap callbacks recheck scope/generation.
- Native policy installation is atomic and versioned; ACK means validated durable storage for the captured scope/revision. A restrictive update invalidates/silences current native fallback eligibility before the setting is applied/acknowledged, including an already registered v1 pusher. Failed storage/ACK is not reported as an applied setting, keeps delivery non-disruptive and registration/policy retry pending, and cannot leave the prior audible snapshot active. Eligible presentation resumes only after the current safe snapshot is durably installed. Locally pending room mute overrides remote state. Global off produces no ordinary alert; muted/DND messages go to silent notification center; sound/vibration choices apply independently. DND is evaluated at display time in local timezone, including crossing-midnight/equal-endpoint semantics of the existing engine. Unknown/overflow/incomplete room state is non-disruptive; no cold inferred mention/attention exception. Current-room/foreground/call-active live suppression remains effective. The current Dart sound-disabled channel defect must also be fixed.
- Authenticated preparation on startup means initial/unbound policy setup and genuine account/session transitions. A cold SDK callback may use a still valid, durably prepared current scope/policy without booting Flutter or resetting eligibility; this is necessary for the actual cold fallback. Restrictive pending/invalid policy state cannot become eligible by cold bootstrap alone.
- Desired/acknowledged pusher identity includes token, scope and relevant policy/contract revision. Same-token changes reconcile. In-flight updates coalesce and send the newest revision after old completion; old compensating deletes cannot remove a new shared-token registration. Cold process restart reuses current scope; true re-login rotates it.
- Native is one serialized event-claim owner for Dart and fallback. Coordinator-not-ready, false/no ACK and stale channel retain fallback eligibility. Handoff timeout is bounded (at most5seconds); late ACK invalidates its old owner epoch. Matrix-first/native-first/simultaneous/retry transitions allow at most one disruptive alert while preserving sync/store/badge handling. Permission/presenter failure does not count as successful display; retry is bounded. Subsequent detailed Matrix presentation replaces/cancels generic center content without re-alerting.
- Foreground presentation uses a scoped, expiring lease rather than permanent ownership on a method-channel ACK. A known abort before any presentation restores ordinary policy-eligible fallback, even if a same-scope policy update invalidated readiness. If the engine disappears or an active-presentation ACK is lost, whether a local banner/sound already occurred is unknowable: recover within the bounded handoff through a silent notification-center item, not a second disruptive alert. This preserves visible fallback and sync/store/badge; it cannot promise sound for that uncertain crash/interruption case. Lease expiry must fence stale Dart work before every disruptive effect. Expiry/restart must not retain a permanent active claim, and recovered pending entries share the existing finite budgets. This refinement requires ordered independent design and implementation review.
- Claims budget4096 with10minute expiry covers the reported5messages/second through the5minute provider retry window while retaining a finite cap. Pending wakes32 with5minute expiry, one pending tap with5minute expiry, room-policy entries2048, displayed generic aggregation bounded. Prune load/insertion, reject future timestamps, and make overflow non-disruptive. Persist small transactions/coalesced snapshots in a serialized owner off the UI thread; do not write an entire maximum map per message or per eviction. The application-process GTIntentService owns policy/claims; the separate SDK push process cannot treat multiprocess SharedPreferences as a lock.
- Notification taps use explicit immutable PendingIntent, no raw ID and scoped identity. Validate at native entry and immediately before Dart route resolution. Only current authenticated local membership can resolve the digest; unresolved current-scope tap may open home, while stale-scope tap does nothing. No digest grants content access.
- Preserve revision-owned limiter reservation/release, bounded provider offload,503 retry, permanent-only CID rejection, single401 token refresh with identical request body, call whitelist and unchanged APNs behavior. Changed-path logs remove existing raw-room debug output; use only stable codes/counts. Both old-client and v1 negative whitelist tests remain mandatory.

## Privacy boundary and compatibility

This is a narrow extension of the prior Getui type-only whitelist. The provider can correlate scoped digests within one authenticated session; scope rotation limits cross-session correlation. The gateway already receives Matrix event_id_only metadata; it receives no new message plaintext or key material. Transport remains HTTPS with certificate verification. No association value appears in logs, analytics or user-facing diagnostics; diagnostics use stable reasons/counts only. The existing generic vendor text remains generic.

The old client/pusher behavior stays compatible. v1 schema validation rejects oversized/malformed fields before hashing or provider use. Registration metadata is input to notification presentation only and cannot mutate identity, wallet, ledger or other business state. On a new v1 client, legacy/versionless payloads can provide bounded sync hints but cannot independently prove current account or eligibility for disruptive native presentation. Rollback to type-only server transmission is therefore a degraded cold-notification path on new clients; it remains safe and never auto-launches the app. Old installed clients keep their legacy provider compatibility.

## Required review and verification

Domain review checks mute/global/DND, stale account and tap semantics, old-client and call compatibility, normal/cold/coordinator-not-ready ownership, expiry, registration/reconciliation and vendor policy limits. Quality/security review checks exact outbound whitelist, scope generation/storage/rotation, no plaintext/raw-ID logging, input caps, bounded memory/work, race-safe dedup and revocation, TLS and no new privilege. Behavioral RED/GREEN must cover cold receive without Activity, native notification/sound eligibility, explicit tap only, late/duplicate delivery, account change and temporary provider failure. Android native compile/tests and emulator acceptance cannot substitute for Redmi OEM half-hour delivery or iPhone APNs device verification.
