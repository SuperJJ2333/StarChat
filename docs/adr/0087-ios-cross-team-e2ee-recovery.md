# ADR-0087：跨 iOS 签名团队的 Matrix 加密密钥恢复

**状态：草案，待用户批准及 Domain、Quality/Security 设计评审；不授权实施或发布。**

**日期：2026-09-28。**

**关联：** [ADR-0003](0003-mobile-dual-session-persistence.md)、[ADR-0007](0007-mobile-matrix-session-continuity-and-key-recovery.md)、[ADR-0062](0062-mobile-single-device-session.md)、[ADR-0063](0063-preserve-account-local-chat-stores.md)、[ADR-0068](0068-installation-generation-reset.md)、[迁移可行性核查](../verification/2026-09-28-ios13-migration-feasibility.md)。

## 背景与现状

业务账号、稳定 Matrix 用户 ID 和服务器保存的密文不以 Apple Team ID 为主键。iOS 本机 SQLCipher 数据库密钥、会话等存在当前签名授权的 Keychain 组中。旧企业包的 Team 为 `ZXB3TS7QD4`，新包为 `A9HAF6NT6S`；改变签名团队不会赋予新包读取旧组的权限。新包即使重新登录同一业务账号和 Matrix 用户，也不能仅凭服务器身份解开旧本地数据库或过去的房间密钥。参见 [Apple TN2311](https://developer.apple.com/library/archive/technotes/tn2311/_index.html) 及 [Apple DTS 的跨团队迁移说明](https://developer.apple.com/forums/thread/706128)。

原团队已不可用，旧签名 iPhone 尚能读旧聊天，用户没有外存恢复码，也没有另一台持钥设备；新团队包尚未装到这台 iPhone。冻结的旧版 0.4.20/2189 没有可达的恢复密钥导出或可信设备迁移入口。因而当前**没有经验证的旧 2189 历史无损迁移路径**；不能把“同账号登录”“SAS 验证成功”或网站已分发新包说成已找回历史。旧手机须保持原状，不能为了测试覆盖安装、卸载或清除其数据。

既有客户端的 `backupKeysToEncryptedStore()` 仅创建 SSSS key 并缓存秘密，没有创建 Matrix `/room_keys/version` 或证明房间密钥上传；`backupKeyMatchesCurrentVersion()` 只查本地缓存。SDK 上传方法还会捕获并记录错误，调用返回不能当作服务器备份完成。ADR-0007 的“真实在线 Megolm 备份”决策仍有效，本 ADR 补足跨团队恢复的完成条件和与现行单设备策略的关系。

## 决策

1. **身份与本地存储分离。** 新签名团队登录同一业务账号时继续使用既有稳定 Matrix 用户 ID；新安装或独立 Bundle ID 测试包创建自己的 Keychain 项、SQLCipher 库和 Matrix 设备。不得把 Apple Team ID 加入业务账号或 Matrix 身份，也不得尝试通过复制旧 Keychain 组名、降低 Keychain 权限、覆盖旧库的密钥或服务端明文导出绕过系统权限。检测到旧加密库存在而密钥不可读时失败关闭，保留原文件；仅在已认证用户明确选择后才允许建立独立的新本地槽，不能将新密钥写入旧库。
2. **用户持有恢复码。** 在能读取现有 E2EE 状态的客户端本地生成高熵恢复秘密，以 Matrix SSSS、交叉签名和 `m.megolm_backup.v1.curve25519-aes-sha2` 创建真正的加密房间密钥备份。只向 Matrix homeserver 上传按协议加密的备份、SSSS 密文及密文设备事件。向用户展示可离线保存的恢复码并要求确认已保存；业务 API、管理端、通知网关、诊断/日志、分析埋点均不得接收恢复码、SQLCipher 密钥、Megolm/Olm 明文密钥、消息正文或明文附件。任何“忘记恢复码”路径均不得把业务身份认证等同于解密授权。
3. **可验证的备份状态。** 客户端须取得当前 `/room_keys/version` 并校验算法、公钥和版本与本地恢复秘密对应；上传本机已持有的入站房间会话后读取服务端版本及条目数等非秘密元数据，确认所有待上传会话已获持久化确认。上传异常、网络未知结果、版本轮换或计数不符时保持“待完成/需重试”，不得显示“已保护”。用户文案只承诺“本设备已持有且确认上传的房间密钥”，不承诺本来就缺失的旧会话可恢复。发布前必须以干净客户端、用户保存的恢复码从服务器恢复并解密代表性的旧密文，不能仅以 SDK 返回、SSSS 缓存或元数据读回代替端到端证明。
4. **按现行单设备策略恢复。** 新团队客户端先以正常业务认证和受控 Matrix broker 建立新设备，再使用用户输入的恢复码在本地解开备份并恢复入站房间会话；恢复失败保留新旧各自本地数据和服务器密文，提供明确重试。业务登录、钱包和支持数据仍由业务 API 判定；恢复不能改变或补写金融状态。
5. **可信设备交接必须在旧设备被撤销前完成。** ADR-0062 的业务登录与 Synapse broker 会在新设备登录时撤销旧会话、删除旧 Matrix device。故常规“先在新 App 登录、再让旧 App 经 Matrix SAS/`m.secret.send` 实时传密钥”在现行策略下不成立。本轮不开放并发双设备例外、不绕过 broker、不复活旧 token。未来持钥客户端若提供设备交接，须在新设备触发替换登录**之前**，由旧设备在本地确认用户操作、建立端到端保护的离线/近场交接，将恢复秘密传给新设备的临时隔离存储；新设备登录后必须核对稳定 MXID、备份版本/公钥，再恢复，错配即销毁暂存秘密。其具体配对、身份确认、重放防护、暂存期限和撤销语义要由单独规格与安全评审确定，并在真实单设备 broker 下证明有效。旧 2189 没有此入口，不能追溯为现有用户提供这条路径。
6. **并装测试与正式发布隔离。** 新团队并装测试包必须使用与旧包不同的 Bundle ID、匹配的显式 App ID/企业描述文件、`application-identifier` 和 Keychain entitlement；其沙盒、推送 topic、Universal Link/URL scheme 与正式包隔离。现有 `(13).ipa` 的 Bundle ID 与签名 `application-identifier` 记录存在差异，不能直接作为并装验收包。并装只验证新流程和保全旧设备，不证明新团队能读旧组，也不改变现网 iOS 下载、OTA 或更新弹窗。
7. **旧库缺钥的安全入口需新增。** 现有启动路径在 missingKey 时会中止，现有归档入口要求旧绑定及密钥可读，不能直接当作换签恢复入口。受保护实现须先提供不打开旧库的安全登录壳，将旧文件归属视为未验证；Business 认证及用户明确选择后，只能在独立本地槽建立新库，旧加密文件原样保全。保全文件不代表新 Team 可重新打开。

备份核对必须逐个本设备已知 room_id、session_id 与 first_message_index 对账源库存、服务器读回的密文库存、干净客户端导入库存；版本计数或早中晚抽样只能提供部分证据，不能证明从未在源设备持有的旧会话也已备份。UI 应写“本设备已知密钥已备份 X/Y”，列明已知缺口，不用“所有历史均可恢复”。跨 Team 冷恢复可用独立测试账号由 Android 或新 Team 测试版建立备份，再在新 Team iOS 空库验证；冻结旧 Team 2189 的真实历史恢复仍是逐账号条件判断，不能充作该验收通过。

并装隔离测试用两个不同的无余额账号：旧签名测试 App 的 O 保留测试历史，新包只登录 N，避免单设备顶号掩盖容器隔离结果。单设备替换行为另用账号 P 和可丢弃设备验证；绝不用唯一持钥的真实旧账号做这三项测试。

在当前单设备策略下，未来来源 App 须在新端登录前展示“准备换机”：确认用户已在 App 外保存并重输恢复码、待上传队列已清空、本机已知会话逐项从 Matrix 读回、用该码在隔离临时解密环境逐条下载解开每个已知会话并核对 room_id、session_id、first_message_index，才标示已知密钥可切换；若仅抽样或中断，只能显示“已上传，尚未逐项验证”。ADR-0007 允许本机 Keychain 安全缓存恢复码供同机使用；外存副本是跨 Team 的额外必要条件。若用户在已知缺口下仍继续，应明确选择“了解风险后继续”，不能称历史受保护。同账号在新设备先做真实冷恢复测试会立即撤销来源设备，故不能作为无副作用的换机预检。新端须在提交 Business 登录请求之前告知旧业务会话和 Matrix 设备会被撤销/删除，并提供返回旧设备的选择；无恢复码仍要登录者须单独确认旧历史可能无法解密。

恢复码验证不得仅依赖 SDK 的 checkKey/unlock 返回或本机缓存：SSSS 元数据缺失 IV/MAC 或 MAC 不匹配时必须拒绝，实际用用户输入码解出备份私钥、推导公钥与当前备份 version/算法核对，再以干净客户端导入和解密验证。恢复历史房间密钥与交叉签名设备信任分别记录；新设备未完成可信签名/验证时不得显示“完整恢复”，受信任设备密钥分享仍受现有 E2EE 规则限制。只有在设备解锁且 Protected Data 可用时查询明确返回 errSecItemNotFound，旧库缺钥分支才能启动；锁屏、首次解锁前、errSecInteractionNotAllowed 或其他 OSStatus 一律保留旧数据并等待解锁/重试，不能视为密钥丢失。

## 对既有 ADR 的影响

保留 ADR-0003 的双域持久化、ADR-0007 的真实加密备份及无秘密服务端托管要求、ADR-0063 的按账号隔离存储和 ADR-0068 的安装世代判定。ADR-0062 的受控登录与精确设备撤销优先适用；因此 ADR-0007 所述经 Matrix `m.secret.request` / `m.secret.send` 向旧设备取密钥，只能在旧设备仍是有效、已验证设备时使用，不能作为新登录之后的跨设备恢复路径。离线、登录前交接是本 ADR 提议的未来补充路径，不修改现行 broker。

## 取舍与明确不采用的方案

| 方案 | 判定 |
| --- | --- |
| 仅改业务账号字段、迁移服务器用户记录或强行设旧 Keychain 组 | 无法改变 iOS 签名授权；拒绝。 |
| 让业务 API 托管恢复码或明文房间密钥，凭登录自动取回 | 破坏 E2EE 信任边界；拒绝。 |
| 直接覆盖旧 iPhone 安装新 Team IPA 后观察是否还读得到历史 | 唯一可读副本可能丢失；拒绝作为首轮验证。 |
| 新旧 App 同账号同时登录，依靠 Matrix to-device 在线传密 | 现行 broker 会撤销旧设备；不做临时单设备策略例外。 |
| 真实加密备份加用户持有码，顺序切换设备 | 与单设备策略兼容；选为可交付的主要恢复路径。 |
| 经本机用户确认的登录前设备交接 | 仅限未来两端都支持该功能，需独立规格和安全审查；不能用于冻结 2189。 |

## 兼容、失败处理与回退

- 已发布的旧 2189 不会因新代码自动获得备份能力。若其旧房间密钥既无真实在线备份、又无外存恢复码或其他持钥设备，平台不得承诺历史可恢复。保留旧签名手机和不可变旧包；旧 profile 有到期日，旧设备继续可用的时间不作保证。
- 新版缺恢复码、备份版本不匹配、校验失败、网络中断、Keychain 错误或 SQLCipher 库打不开，均不得自动清库、生成替代密钥来“修复”旧库、把密钥交给业务服务端或静默将不可解密密文标为已恢复。区分“备份未完成”“待输入恢复码”“缺少某段历史密钥”和“本地存储异常”。
- 支持重新生成/轮换恢复码时，必须先确保新备份和已持有密钥可由新码恢复，旧码失效及回滚语义经专门评审；不能在新备份未知结果时删除旧版本或本地状态。
- 若新备份功能出错，回退 UI/自动操作并保留旧设备、本地 SQLCipher、已创建的服务器加密备份和用户已保存的恢复码；不回退到无条件清库，不重开公开 Matrix 登录旁路。发布回退不得假定已撤销的旧 Matrix 设备可重新上线。

## 证据与评审门禁

**实施前：** 用户审阅书面设计与本 ADR 后批准；Domain Review 覆盖稳定身份、单设备 broker、旧客户端无法迁移的边界、失败和回退语义；Quality/Security Review 覆盖密钥生成/存放、备份版本及公钥验证、离线码展示、日志/诊断脱敏、错误时保留数据、交接威胁模型。上述签署完成后方可将本 ADR 改为“已批准”并编制实施计划。可信设备交接的具体协议若超出本 ADR，另行书面批准。

**实现及发布前：** 测试先证明现有 SSSS-only 路径不构成完整备份，再验证版本创建、加密上传、失败重试、版本不匹配、旧房间和新房间会话、干净客户端恢复和逐会话对账、账号隔离、无秘密泄漏；以真实 Synapse 和 broker 在专用测试账号/设备上测试“新登录撤销旧设备”，不能用模拟双端长期在线作验收。并装签名必须检查 Bundle ID、Team/App ID、entitlements、安装和旧签名测试 App 仍可读；同 Bundle 缺钥启动壳另以注入和非唯一持钥真机测试，缺真机时明确未验。先用可丢弃测试设备/账号，唯一可读旧历史的手机保持原状。按仓库流程先规格符合性审查，再 Domain 与 Quality/Security 代码复核。任何服务端变更或正式包分发另循部署授权与平台发布门禁，本草案不构成发布许可。
