# ADR: bounded encrypted startup projection

Date: 2026-10-17. Status: APPROVED for implementation under explicit user four-point authorization. Independent DOMAIN/SPEC then QUALITY/SECURITY reviews passed after B1 correction (task-4-design-review.md and task-4-design-fix1-review.md). Root admitted the exact frozen Task4 implementation scope; code, executable tests and device acceptance are still required. Baseline product: 02c76dcce63b449d463d7a02cf188ebc12ec3089.

Related: [diagnosis](../verification/artifacts/2026-10-17/startup-local-projection/task-3-diagnosis.md), [task brief](../verification/artifacts/2026-10-17/startup-local-projection/task-4-brief.md), [original design](../superpowers/specs/2026-10-17-startup-local-projection-design.md).

## Decision and authority

Maintain a derived account-isolated AEAD projection from an already fully restored, identity-checked, business-authenticated session. It contains already admitted application conversation rows and bounded visible canonical message heads. Read it after installation and secure account admission, before touching the large historical Matrix database. Preserve the complete existing original-DB preflight, SQLCipher parameters, retained Olm checks, business restore and dispatch authority in background. A cache proof grants local display and durable pending-text enqueue only. It grants no SDK login, access token, network request, room-key operation, money action or transport authority.

This explicitly separates local display from full-store admission: a corrupt/mismatched original Matrix store may coexist briefly with a valid previously committed projection owned by the current secure account. Full validation failure immediately revokes that projection and routes through existing safe Retry/recovery. We do not claim the original store was validated by validating the projection. This new read-only display authority is the item requiring domain/security review.

Same Client and Room instances, current AppHome/RoomPage/timeline controllers and existing outbox remain. The existing SqliteOutboxStore is local metadata storage, not asserted encrypted by this change. This ADR encrypts the new projection only; it does not migrate or change outbox storage/security policy.

## Exact cryptographic context

Use pinned `cryptography: 2.9.0`, `AesGcm.with256bits()`, 96-bit fresh cryptographic-random nonce and 128-bit tag. Existing patterns: emoji_preview_cache.dart and video_poster_disk_store.dart. Do not copy their weaker replacement/quota semantics; use the commit protocol below. No new dependency, stored secret, token or change to Matrix/SQLCipher keys/KDF.

IKM = strict base64url-decoded existing matrixDatabaseKey (exactly 32 bytes). Read-only admission must not call a key-creating API. K = HKDF-SHA256, outputLength=32; salt = UTF8("ChatFlow/startup-projection/HKDF-SHA256/v1"); info = C. Use package Hkdf(hmac:Hmac.sha256(),outputLength:32), not a hand-rolled KDF. Derived key is transient and never persisted.

C is deterministic UTF8(jsonEncode(JSON array)), in this exact order and types:
`["ChatFlow/startup-projection",1,scope,homeserver,matrixUserId,deviceId,ed25519Fingerprint,databaseGeneration,installationId,cacheEpoch]`.
All identity strings use the exact validated secure binding values, not independently normalized URI spellings. scope may be empty for the valid legacy slot. installationId and cacheEpoch are 32 random bytes encoded unpadded base64url. No floats/maps in C. Reject missing dimensions/invalid encoding; never substitute empty values. Homeserver must equal configured/authorized binding. The locally stored Business MXID must equal matrixUserId.

Envelope header H = ASCII `CFSP` (4 bytes), version=1 (u8), flags=0 (u8), ciphertext length (u32 big endian), nonce (12 bytes). AAD = H || C. File = H || ciphertext || tag(16). C is reconstructed from secure admission, not trusted from file. SHA256(file) is pinned in the secure commit head. Nonce fresh for every attempted write; a failed retry creates another nonce. Keys and plaintext exist only in memory and are dropped when owner is revoked; Dart GC is not claimed to guarantee zeroization.

## Boundaries and encoding

User ceiling: 4MiB total cache footprint, 40 rooms, 40 events per cached room. To include crash-safe old+new files, each committed/encrypting envelope is capped at **2MiB** and only one active account projection is retained. Old committed + one candidate <=4MiB; clean orphan candidates before starting another write, and refuse writing if cleanup/quota cannot be confirmed. Switching accounts invalidates the old projection; old account DB/history are untouched. Ciphertext limit is checked with stat and bounded read before allocating/decrypting, then exact header length is checked. No decompression.

Payload is a versioned allowlisted JSON object with explicit `kind:"valid"`, `rooms:[]`, identity-free per-room display fields, and per-room `head:[]`. A valid empty projection is distinct from missing/corrupt. Reject unknown schema versions, duplicate room/event IDs, invalid types, out-of-range timestamps/counts, or payload limits. Max serialized conversation record 16KiB, event record 64KiB, singleton state value 16KiB, <=16 singleton state types per room; identifiers <=2KiB, display strings <=4KiB. No arbitrary SDK account-data/room maps, member fan-out, tokens, Olm pickles, recovery/session keys, financial authority, media bytes or disk plaintext. Event allowlist includes stable ID/txid if already synced, sender display, timestamp/type, exact cacheable body/media metadata and relation/redaction representation required by existing canonical timeline; unsent messages remain solely in existing outbox.

Budget selection: take at most 40 currently admitted rows in displayed order; encode their bounded required metadata first. Add visible, non-hidden canonical events newest-first round-robin across included rooms, at most 40 each, until 2MiB envelope budget. Never truncate a message into a false complete body. Omit an oversize event and mark head partial; do not label a partial head as complete history. Every row carries headCoverage (empty/partial/complete_cached), permission snapshot and history-generation identity. Full SDK history can expand the same timeline later. This does not promise that arbitrary oversized historical content is cached.

## Secure head, admission and commit protocol

Add account-scoped secure key `liuhetong.startup_projection_head.v1[.<scope>]`. Value has bounded version, installationId, random epoch, state invalid/committed, committed ciphertext SHA256 and envelope byte length (no message content). Add it to SecureSessionStore scoped keys and installation/identity cleanup. No independent cache encryption key.

Add `SecureSessionStore.readStartupProjectionAdmission(installationId)` under `_runMatrixIdentityOperation`: one coherent operation reads existing journal, scope/registry, binding, existing database secret, clear tombstone, existing Business session/MXID, fresh-device/archive restrictions and projection head. It is inspection-only: no key generation, no archive replay, no legacy Business session migration. Require completed installation reconciliation and all binding dimensions. Cache miss/locked store/pending journal/tombstone/unbound scope/expired-invalid local session/identity mismatch yields no local display capability. Existing network validity still belongs to business restore.

InstallationId is a new public random marker in application-support startup projection directory, created only after installation reconciliation and only on verified full-session priming if absent. Missing marker with existing cache is a miss, never implicit adoption. Its value must match secure head and authenticated context. Existing InstallationReconciler remains authoritative and runs first; clearInstallation removes secure heads, and stale container files cannot be admitted against a different marker/head.

`StartupProjectionAdmission` is immutable attempt metadata, not raw public key material. Its owner tracks in-memory account/session/installation generation and retired state. After bounded read/decrypt, recheck secure commit head and current identity snapshot under the identity serializer before publishing (never trust a cached read across an await that permits account switch). This second check is necessary; optimize repetition inside each snapshot, not away.

Writer: acquire a zero-active-mutation capture permit and capture a verified full-session generation and eligible canonical snapshot through public app APIs. Recheck the permit after capture; prepare/encrypt outside the identity lock, write/flush/rename a unique candidate to an immutable digest-named final file outside that lock. Under the short identity serializer, recheck identity/epoch/history generation AND the unchanged mutation revision/zero active tickets. Commit secure head with exact digest/length last. The operation-spanning ticket protocol below is mandatory; an epoch check alone is insufficient. Until that succeeds the candidate is invisible. Delete old file only after commit. Missing file/head mismatch/torn write/candidate after crash -> miss, never fall back to a previous generation. Parent-directory fsync durability is not assumed; lost rename can only produce miss. Startup cleanup considers only cache-owned hash filenames, never DBs.

`beginStartupProjectionMutation(reason)` synchronously registers an active mutation ticket, revokes in-memory readers/writers, and changes the secure head to invalid with a new random epoch BEFORE allowing the privacy/lifecycle mutation. The ticket remains active through actual apply/transaction completion as specified below; it is not a prehook-only notification. File removal is scheduled separately. File deletion alone is insufficient. If invalidation cannot be persisted, fail the privacy operation before acknowledging success; keep the current projection unavailable in memory. Do not acknowledge clear/delete with an old committed cache still admissible. If logout/revocation cannot persist cleanup, access remains denied in memory and existing secure logout failure handling must surface failure; do not silently claim durable logout.

## Review correction B1: operation-scoped mutation and writer fencing

This section refines all invalidation rows above. A pre-mutation epoch change alone is NOT sufficient. An operation remains fenced until its real effects have settled; onSync/onEvent notifications are not completion receipts.

Exact public contracts (names may retain SDK namespace conventions, semantics fixed):

```dart
// begin is synchronous: increments revision, adds ticket, revokes readers/writers.
StartupProjectionMutationTicket beginMutation(StartupProjectionMutationReason reason);
// beforeApply completes only after durable invalid head is written; failure means no apply.
abstract interface class StartupProjectionMutationTicket {
  Future<void> get beforeApply;
  Future<void> finish({required bool applied}); // owner-scoped, idempotent exactly-once
}
// convenience wraps begin -> await beforeApply -> await apply -> finish in finally
Future<T> runMutation<T>(StartupProjectionMutationReason reason, Future<T> Function() apply);
// returns null while any ticket active, owner revoked, or current owner poisoned
StartupProjectionCapturePermit? beginCapture();
Future<void> commit(StartupProjectionCapturePermit permit, PreparedProjection projection);
```

Coordinator state: immutable owner token, monotonic in-memory mutationRevision, active ticket IDs, durable invalidation flight, `requiresVerifiedReopen` after uncertain/failed apply. Every begin increments revision and synchronously marks active BEFORE its first await. Every finish increments revision and removes only that ticket; it cannot authorize another owner. A nested operation owns a separate ticket, or explicitly receives the existing parent ticket for the same awaited operation. No optional guards. Coalescing durable invalid-head writes is allowed only if every nested ticket awaits the same completed invalidation for that owner/epoch. Outer completion does not remove inner tickets.

Writer capture and final commit both require current verified owner, zero active tickets, unchanged mutationRevision, exact secure epoch/head and full binding/generation. Capture permit tags a **new canonical snapshot requested after the last successful mutation completion**; a previously stored UI snapshot cannot be relabeled with the new revision. Capture is asynchronous outside the identity lock and rechecks the permit after its awaits. A ticket starting during capture/encryption/file write invalidates the permit; discard candidate. A new writer under the just-rotated epoch is still denied while the mutation is active, closing B1.

At final secure-head commit, perform checks inside the short identity serializer immediately before write and again after its await. If begin fires while the secure write is pending, writer reports no publication and leaves/rewrites the head invalid before releasing the short serializer; queued mutation beforeApply cannot complete until its own durable invalidation has settled. Crash before that invalidation is safe because mutation apply has not been allowed to start. Never wait for mutation completion while holding the identity serializer. No secure lock across network, long polls, snapshot capture, SDK apply, file encryption, or lifecycle drain.

`finish(applied:true)` runs only after the real persistence/transaction/awaited operation succeeds, including nested work whose success the operation acknowledges. Head remains invalid; it does not republish by itself. When the last ticket finishes, a new post-apply canonical capture may run. Crash after apply but before capture/commit is a cache miss. `finish(applied:false)` leaves head invalid and poisons cache writing for that owner (`requiresVerifiedReopen=true`), because SDK in-memory state may differ from rolled-back disk. A normal stale UI snapshot or a later onSync event cannot clear this flag. Only a newly fully restored/identity-checked/business-authenticated owner after safe reopen can prime again. This conservative cache availability cost avoids inventing rollback reconciliation. If invalidation itself fails, apply is not invoked and the ticket still fails/poisons until verified reopen; no successful privacy acknowledgement. The prior durable head may remain valid when the secure write fails, but no privacy mutation has been applied in that case; do not falsely claim a failed secure write made disk invalid.

Suspend/account-switch synchronously revokes owner before awaiting existing drains. Ticket finish from the old owner may release its own resources but cannot remove new-owner tickets, update head, clear poison or schedule new-owner capture. Durable mutation tickets need no separate journal: BEFORE apply the persisted head is invalid; a process restart cannot admit it. New process must complete normal full validation and fresh capture to re-prime. Revision/ticket memory is not used as crash-persistent authority.

### Exact apply boundaries

- Local history/preference mutation guard wraps the actual `preferences.set*` / preference persistence Future, including success checks; facade-level network/read-marker/leave/redact operations use an outer ticket spanning their awaited operation. Lower-level nested tickets remain active until their own persistence completes. A prehook callback alone is forbidden.
- Secure session/identity methods serialize only the head/key/pointer write steps. `saveSession`/`clearBusinessSession` must join the same identity serializer for relevant Business identity/head changes while retaining their synchronous in-memory authorization revocation; no network call under that serializer.
- Production Client sync: after HTTP long-poll response and required local-load readiness, but BEFORE `prepareSyncTimelineStorage`, begin ticket and await beforeApply; recheck current loop/owner/generation after await. Hold ticket across preparation and the whole `database.transaction` Future, including storePrevBatch, and finish in finally after that Future succeeds/fails. An aborted skipped transaction is not successful applied work. The database-null path spans `_handleSync` completion. Do not acquire a ticket while awaiting the long poll.
- Test `handleSync`: begin before prepareSyncTimelineStorage; finish after preparation + `_handleSync` actually settle (or after any transaction it gains). Both paths call the same helper; no duplicated incomplete prehook. `_handleSync` emits onSync inside production transaction, so onSync can schedule capture but capture remains rejected until the outer ticket ends.
- Nonempty room/account-data batches conservatively receive a ticket. Empty long polls do not. Callbacks must not call `_withClient`, await lifecycle drain, or recursively wait for the SDK operation they guard.

### Admission parsing bounds and native read path

Check UTF-8 encoded value length before any admission JSON decoding: registry <=64KiB and <=256 entries; binding <=8KiB; Business session <=16KiB; head <=4KiB; archive index/journal <=64KiB and <=128 entries where parsed; scalar scope/identity fields <=2KiB; existing key string <=128 bytes with exact decoded IKM=32; registration key <=256 bytes; installation marker exact 43 ASCII base64url characters decoding to 32 bytes. Excess/malformed/unknown values -> fast-cache miss and unchanged normal admission, never truncate or alter registry. Platform secure-storage retrieval itself returns a string and is not claimed bounded by this parser; only subsequent decode/materialization is bounded. Fixed envelope/payload limits still apply.

Declare ownership extension `apps/mobile_flutter/ios/Runner/IOSSecureSession.swift`: add ONLY inspection allowlist entries for `liuhetong.registration_device_key.v1`, `liuhetong.startup_projection_head.v1` and strict scoped head pattern. Update Dart `FlutterSecureKeyValueStore._nativePreflightKey` to route these to native `peek`; not mutating `read`. Existing iOS `peek` performs SecItemCopyMatching only, preserves genuine locked errors and does not migrate accessibility/create items. Head writes remain explicit normal secure writes outside inspection, not new native write authorization. Bridge file requires no change because it already exposes peek.

Tests must verify native allowlist rejects unrelated keys/scoped malformed names and peek makes no update/add/delete calls even for old accessibility. Dart channel routing tests cover both new keys. Actual iOS Swift/runtime validation requires Apple tooling; Android or mocked Dart passing cannot be reported as iOS validated. Proposed native test file: `apps/mobile_flutter/ios/RunnerTests/IOSStartupProjectionPeekTests.swift`; existing project test-target registration must be checked before adding it (any pbxproj change needs separate root ownership declaration).

### Required failing interleavings

1. Pause hide after beforeApply durable invalidation but before its persistence; attempt NEW-epoch capture/commit -> rejected. Resume apply; kill before republish -> next launch cache miss.
2. Same race with production sync: pause inside DB transaction after onSync fires but before commit; capture/commit still rejected. Verify completion only after commit Future, and preparation failure/transaction rollback poison writer.
3. Capture under revision R; begin mutation while encrypt/write/head-write is held; release writer -> no committed stale projection may survive into applied mutation. Old digest rollback remains miss.
4. Nested outer+inner tickets: ending outer cannot permit capture until inner completes. Failure of either keeps invalid/poisoned state. Duplicate finish is idempotent, stale-owner finish cannot release new owner.
5. Pause network response before arrival -> no ticket/no writer starvation; empty poll -> no ticket. Ticket begin's await owner switch -> no prepare/apply for old owner.
6. Failed persistence/invalidation -> no success acknowledgement and no re-prime from old snapshot; verified reopen + new canonical capture can re-prime. Include local account-data hide, event hide, history clear, SDK redaction/leave, and Business identity transitions.
