# ADR 0009：同设备 60 天登录缓存与并发刷新竞态修复

日期：2026-08-30　状态：已批准（产品所有者明确要求“同个设备保存账号的 60 天登录缓存”）

## 背景

生产数据显示 73 个设备令牌族中 14 个（19%）因 `TOKEN_REUSE` 被服务端重用检测强制撤销，用户表现为：离开 App 约 15 分钟（业务 access token 有效期）后回来即被踢到登录页（用户感知为“2 小时”），以及更新安装冷启动后要求重新登录。

根因是**客户端并发刷新竞态**：`BusinessApiClient._authorized` 对每个 401 各自调用 `refreshSession()`，无 single-flight 锁。多个并发请求（首页聚合加载）同时用同一个 refresh token 换新，第一个成功消费，其余命中服务端单次使用检测 `rotate()` → `TOKEN_REUSE` → 撤销整个设备令牌族。服务端令牌本身工作正常。

## 决定

1. **服务端**：refresh token 生命周期 30 天 → **60 天**（滑动续期：每次 rotate 后新记录 `expires_at = now + 60d`）。语义：同一设备 60 天内至少活跃一次即持续在线；连续 60 天不活跃则过期，需重新登录。
2. **客户端**：`refreshSession()` 增加 **single-flight**——并发 401 共享同一次网络刷新，其余调用方 await 同一 Future。刷新成功后各请求以新 access token 重放。
3. **保留不变（不弱化安全）**：
   - refresh token 单次使用 + `TOKEN_REUSE` 重用检测撤族机制完整保留；
   - 设备绑定（`identity_devices`）、登出撤销、密码重置撤族、access token 15 分钟短生命周期均不变；
   - Matrix 侧非过期凭据与本地加密库不动。

## 后果

- 修复后并发刷新不再误触重用检测，设备会话在活跃使用下保持 60 天滑动有效。
- 剩余的 `TOKEN_REUSE` 撤族仅对应真实重放攻击或客户端实现缺陷，作为入侵检测信号保留价值。
- access token 仍为 15 分钟，泄露窗口不随本变更扩大；refresh token 泄露窗口由 30 天增至 60 天，由设备绑定与单次使用检测补偿，风险可接受（移动端单设备场景）。
