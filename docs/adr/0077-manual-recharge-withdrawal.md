# ADR-0077：人工充值与人工提现（客服结算、汇率调整、快照）

日期：2026-09-21。状态：**已批准（用户 2026-09-21 需求书确认全部规则）**。授权范围：实现与隔离测试；不含生产发布、实际出款或生产数据修改。细化 ADR-0076 的出入款边界，替代 ADR-0070 的充值自动衔接为默认关闭。

## 背景

取消原在线自动充值；APP 从后台授权的官方客服目录推荐充值客服；用户向客服支付 USDT，客服核实后处理点钻充值；提现最终支付 USDT；客服可调整结算汇率，**汇率调整本身不需要用户再次确认、第二人复核或金额审批**。边界：该豁免仅限"汇率调整"这一个动作，不删除支付密码/TOTP、审批、幂等、审计、出款安全等既有约束。

## 决策

### 充值（人工）

1. **申请单**：`POST /recharge/requests`（用户，支付密码不涉及——只生成订单）创建 `RechargeRequest`：user_id、`amount_usdt NUMERIC(30,6)`、可选 `evidence_txid`（链上凭证）、用户备注、状态 `SUBMITTED`、参考汇率快照 id。**只生成待处理订单，不增加任何余额**。
2. **凭证防重**：`evidence_txid` 非空时部分唯一索引——同一到账凭证不得重复用于充值；重复提交返回 409 `RECHARGE_EVIDENCE_REUSED`。
3. **客服目录**：`cs_directory_entries` 表（cs 业务 user_id、展示名、收款地址、说明、enabled、排序），仅管理员可增删改（审计）。`GET /support/recharge-directory` 返回启用条目（业务身份+收款地址），APP 据此推荐。
4. **入账**：客服核实实际付款后，通过**既有公开财务服务**执行（财务调整/执行链路及既有审批状态机不变，不新增直改余额通道）；执行成功原子地把申请单置 `CREDITED`，记录最终点钻金额、执行者、关联调整/账本交易 id、最终汇率快照。审计 + Outbox（`recharge.credited`/`recharge.rejected`）。拒绝需原因，状态 `REJECTED`。
5. **关闭自动充值**：`wallet_auto_deposit_enabled` 默认 False：托管充值回调入口对新事件返回业务错误 `AUTO_DEPOSIT_CLOSED`；观察者自动入账任务停止推进新入账；历史 CREDITED、对账、修复/补录能力保留。配置校验器：manual_liquidity 运行时必须显式声明该值。
6. **后台展示**：充值案件页显示用户、原始金额/币种、参考汇率（快照）、客服最终汇率、最终点钻金额、处理记录（时间线）。

### 提现（人工 USDT 出款）

7. **状态机不变，金额口径改变**：沿用 manual payout（REQUESTED→CLAIMED→SETTLED / CANCELLED / UNKNOWN）与双审批、支付密码、绑定版本、限额、储备门禁。`funding_asset=CAIBI` 的报价改为：`receive`（最终 USDT 应付）= 点钻金额 ÷ 结算汇率（快照汇率，6 位 HALF_UP），快照记录 `fx_snapshot_id`、`conversion_rate`；`conversion_rate` 不再写死 '1'。**原 10 USDT 最低门槛继续按 USDT 应付额执行**。
8. **内部兑换按率**：新增 `convert_for_payout`（source X 点钻 → target Y USDT，Y=X/率），两账本各自平衡；取消时按原转换镜像冲正（退回 X 点钻、收回 Y USDT），`require_conversion_release` 按 source/target 精确校验。旧 1:1 订单的校验与冲正路径保持不变（按订单自身快照）。
9. **汇率调整**：管理员（owner_admin）在 CLAIMED 且未提交 txid 前可调用 `adjust-rate`（幂等、审计记录处理人/时间/调整原因/前后值）：更新该订单最终汇率与最终 USDT 应付额并重算冻结差额（多余冻结退回用户 USDT/点钻账本，不足则拒绝调整）。**无用户二次确认、无第二人复核、无金额审批**；其余全部安全约束不变。SETTLED 后不可调整。
10. **不确定结果**：UNKNOWN/多匹配/证据不可用一律进 `UNKNOWN`（待核对），绝不自动重复付款、绝不自动改状态掩盖资金事实——沿用现有 reconcile 纪律。人工付款确认以链上证据匹配（txid/log_index 唯一、金额=最终应付、收款地址=绑定地址）为唯一 SETTLED 依据。
11. **结算快照**：SETTLED 时订单持久保存最终汇率、最终应付、调整历史（JSON 快照）；后续汇率刷新不改变已批准/已结算订单。

## 迁移与回退

- `0077_recharge_requests`（新表 + 目录表 + 部分唯一索引）、`0076_payout_settlement`（manual payout 报价/订单增加最终汇率、应付额、快照列）expand-only。
- 回退：关闭充值申请入口/恢复自动充值各自独立开关；汇率调整端点关闭不影响既有订单结算；已结算订单与账本不可回滚，纠错走关联冲正。


## 实施补充（2026-09-21，复审缺口闭环）

**案件-财务执行持久绑定**（`recharge_credit_bindings`，迁移 0079）：一个案件同时至多一个 `BOUND` 绑定、一条财务调整至多绑定一个案件（扁平 `state_active` 判别的部分唯一约束）。绑定校验：调整归属同一用户、未冲正、仍在审批中。执行仍走既有公开财务链路；执行后由 `complete_bound`（worker `recharge_registration` 兜底扫描 + 人工入口）幂等登记——完整复用 `mark_credited` 的凭证核验（已执行、用户/金额/分录/冲正状态一致），执行后宕机自动恢复登记；调整被拒或凭证不符 → 绑定 `FAILED`（原因入档，案件保留 SUBMITTED 供人工以准确结算完成），绝不伪造 CREDITED、绝不二次入账。后台不得以"重建财务调整"补登记。

## 第二轮复审修正（2026-09-22，覆盖上文失败释放口径）

1. 已执行且未冲正的调整发生登记失败时，绑定进入 **NEEDS_REVIEW 并继续占用唯一绑定**；禁止取消案件、拒绝案件或更换财务调整补登记。只有确定被拒或已冲正等可释放情况落 FAILED。已绑定案件的直接登记必须使用同一调整，不能消费其他案件凭证。
2. 迁移 **0081** 保留全部绑定历史：非活动 `state_active` 改为 NULL，活动为 `1`，避免旧唯一键只容纳一条 `0` 历史。增加最终汇率和点钻金额快照；绑定时检查金额按原舍入规则一致。旧绑定只能推导可精确复算的六位汇率，否则待核对；不篡改既成金额。
3. 账本提供公开的原交易行锁接口；登记与冲正序列化，账本写路径锁顺序统一。已登记后发生合法冲正仍保留历史登记事实，不抹除账本历史。状态转换记录审计与 Outbox；恢复扫描优先处理已执行/已拒绝命令，避免审批队列饥饿。
4. 此修正不新增客服调价审批或用户确认。金融执行仍沿用既有权限、审批、幂等及审计；登记成功与账本执行是不同状态，UI 必须区分。
5. 发布先升级到 0081，再部署匹配的服务与 worker。回退先暂停相关写入口与恢复 worker，保留新增列、状态和历史；禁止 destructive downgrade 或直接删除绑定恢复旧代码。0081 的逆向降级明确拒绝删除历史。

## 第三轮处置接口复审（2026-09-22）

- `release` 只接受**拒绝且没有执行交易**或**已存在可核对冲正**的证据。调整缺失、状态与交易矛盾、交易指针缺失但幂等账本交易仍存在均不能证明未付款，保留 NEEDS_REVIEW。`complete_bound` 对矛盾 REJECTED 也执行同样约束。
- 案件→绑定→调整→原交易的锁顺序与登记一致；释放有幂等记录、原样 actor、审计及 Outbox。复核不再给 actor 拼接前缀，避免错误身份和 PostgreSQL VARCHAR(36) 溢出。
- 新增且未发布的 `POST /recharge/admin/requests/{id}/review` 必须带 `Idempotency-Key` 和 `binding_id`。在案件锁内验证预期绑定，旧页面动作不得作用于新绑定。释放的旧幂等请求可重放原回执，但不能释放后续绑定。客户端按 binding_id 生成稳定操作键。
- 待核对队列按不可变 created_at/id 分页；历史展示最近活动/终态绑定，最终汇率/金额来自绑定快照，不用未登记案件的空值覆盖。时间线保留 actor 与状态转换事实。
- 只修改复核一致性与未发布契约，不改变点钻计价、客服调价免新增审批、金融执行授权、舍入或余额数字。本轮无新数据库迁移。
# 2026-09-22 补充：取消旧充值意图

用户明确授权新增旧充值申请取消功能；本补充仅授权本地实现与隔离验证，不授予生产迁移/部署或真实资金操作权限，领域和质量安全审查由主任务独立完成。

本人尚未过期的 OPEN 充值意图可经真实 API 进入 CANCELLED。该动作只关闭意图，不表示链上转账被撤销或退款。保留原金额、地址、绑定和有效期快照；使用原钱包 reserve/control/binding 锁序与回执处理串行化，追加幂等取消记录、审计和事务 Outbox。已入账或其他终态不可取消；相同用户与键只能重放同一意图取消响应。

取消后真实链上回执仍完整保存，进入人工核验并计入未解决资金义务；不得因 CANCELLED 忽略、删除、退款或自动挪给新意图。Flutter 仅在服务器确认 CANCELLED 后移除付款信息；未知响应保留申请，通过同键重试/权威查询恢复。

扩展迁移为 `0082_deposit_intent_cancel`，依赖本地 `0081_recharge_binding_history`；它不能直接用于尚在其他分支迁移版本的生产环境。回退保留历史与新状态，采用前向修复，不执行破坏性 downgrade。
