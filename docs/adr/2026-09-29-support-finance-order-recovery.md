# 客服提现取消边界、链上发现与独占订单接管 ADR

- 日期：2026-09-29。
- 状态：**用户已批准实施及受控生产发布**。用户先批准[书面规格](../superpowers/specs/2026-09-29-support-finance-order-recovery-design.md)及其汇率暂存、地址分阶段安全修订，随后于 2026-09-30 明确要求“修改产品代码和生产环境”，按[逐项实施计划](../superpowers/plans/2026-09-29-support-finance-order-recovery.md)执行；发布仍受该计划的测试、审查、现网基线与回退门禁约束。
- 适用：`SUPPORT_MANUAL_V1` 提现及客服充值订单的管理入口、提现资金状态、TronGrid 只读发现、订单处理资格。旧 `OWNER_MANUAL_V1` 的付款策略和既成订单记录不追溯改写。

## 现象及既有决策

当前 `support_payout.adjust_rate` 先在独立事务执行 `begin_payment`，把尚未在 imToken 签名的订单写成 `CLAIMED` 并记录 `execution_started_at`，随后才尝试调汇率。因此即便调价失败，用户取消也会得到 `WALLET_PAYOUT_CANNOT_CANCEL`。服务端把错误码原样作为 `message`，已发行 Android 将它直接呈现。完整收款地址只存在于开始出款的瞬时返回；后台回到详情后没有重新读取和复制入口。无已存 txid 的 reconcile 不发现链上交易，且会把出款标为 `UNKNOWN`。另一个客服已持有有效租约时，提现与充值列表仍显示可点击的“处理请求”。

[ADR-0013](0013-trongrid-single-source-manual-payout.md)规定 imToken 人工签名、TronGrid 历史仅发现、固化收据和精确 Transfer 才可结算；[ADR-0077](0077-manual-recharge-withdrawal.md)规定点钻来源提现汇率、账本镜像冲正及用户无需二次确认汇率；[ADR-0081](0081-support-order-settlement-and-staff-activation.md)规定客服独占认领、开始付款后不自动接管/解冻；[ADR-0084](0084-verified-recharge-direct-settlement.md)规定已核验充值的专用下发门禁。本 ADR 仅在以下明确冲突处细化这些决策，不解除其他财务与身份门槛。

## 决策

### 1. 真正开始出款是取消和拒绝的截止点

客服认领和确认结算汇率均保持核心订单 `REQUESTED`。对点钻来源的 `SUPPORT_MANUAL_V1`，现有 `adjust-rate` 请求转为保存**待执行**汇率、应付、摘要和版本；在持锁事务中校验格式、精度、认领、角色、会话与幂等，记录实际操作者、原因、审计和 Outbox。多次更改逐次留痕。保存草稿不改最终汇率字段、`HOLD`、原点钻兑换或用户可用资产；USDT 来源不得借点钻汇率重算。此条替代 ADR-0077 在客服策略下要求 `CLAIMED` 后调汇率和调价即释放冻结差额的时点；原 `OWNER_MANUAL_V1` 与既成调价历史不变。

`begin-payment` 是唯一开始付款的事务边界。它必须在同一事务中重验当前认领/操作授权、订单与汇率版本、**当前有效摘要**、原报价、钱包安全、限额、储备、目标地址快照与精确金额。点钻来源按最新准备值原子调平 USDT 可用额和 `HOLD`、记录最终率与应付；USDT 来源继续使用原报价摘要和初始冻结，不需要准备版本。校验或余额/储备失败时整笔回滚，仍允许取消或拒绝；成功时才变为 `CLAIMED`、写开始时间与不可变付款指令。持原始摘要或旧准备版本的页面不得在新汇率下开始付款。重复 begin 只读回同一指令，不能授予第二次签名资格。开始后即使用户尚未到账，也不得普通取消、拒绝、改汇率或重付；结果不明继续冻结核查。

开始前用户可取消，持有有效处理令牌的财务客服或配置的官方钱包所有者管理员可选择稳定原因拒绝。两者共享受控释放应用接口，但使用不同操作、实际操作者和原因；与 begin 在资金预算、订单和用户锁内序列化，提交前再验实时会话、角色、处理令牌及操作级授权。由于汇率草稿不改 `HOLD`，终止时释放原冻结额，并按原兑换凭证精确链接冲正点钻来源。账本应用接口与证明要把**受益用户账户**和**实际操作人**拆开：前者核对原兑换及镜像分录，后者记录在不可变冲正事务、拒绝记录、审计与 Outbox；不得把客服拒绝冒记为用户取消。退款、终态、草稿失效、审计和 Outbox 必须原子提交且幂等。对旧客户端保持兼容的核心 `CANCELLED`，在客服投影单独呈现 `REJECTED`。已由旧流程开始的订单不自动回拨或退款。

### 2. 完整客户地址只在出款开始后可取得

在 `REQUESTED`、认领、汇率准备和最终确认弹窗阶段，后台和接口仅显示脱敏目标地址。开始付款提交后，具有当前付款证据资格的原处理人或受控查看/接管资格的官方钱包所有者管理员才可读取不可变快照中的完整地址；每次读取留审计，失权、登出或换账号时清除 DOM。详情突出显示地址并提供完整值复制图标。原处理人开始后普通租约到期仍保留证据核对权，直到其证据权被正式撤销。完整地址不得进入普通列表、浏览器持久化、错误消息或日志。复制是只读辅助，不表示付款已执行。

### 3. TronGrid 发现只产生候选，最终结算共用归属门禁

仅在真正开始付款后，由服务端不可变订单快照构造官方来源、目标、金额、USDT 合约、时间窗及版本，查询 TronGrid 官方地址 TRC20 历史。采用有界分页、固定固化头/扫描区间、指纹循环和总时间预算；上游错误、超预算或不完整明确报告 `INCOMPLETE`/`UNAVAILABLE`，零候选不等于未付款。老订单可继续手填 txid。候选只显示缩略哈希、脱敏地址、精确金额、时间和收据状态，由处理人对照 imToken 记录主动选择。

每个候选仍通过 ADR-0013 的 `transaction_evidence` 校验固化、成功执行、固定合约、官方来源、目标、精确整数金额、时间和唯一 `(txid, log_index)`。选择、手填、更正和重试一律进入同一个最终 reconcile：在对应订单及官方来源/目标归属锁内重新检查新鲜收据、事件占用和相交时窗的未终结订单；开始新出款也遵守相同锁协议。现有资金全局预算行锁可充当覆盖所有官方来源/目标的更强归属序列化锁，但要用隔离 PostgreSQL 并发测试证明请求、开始与结算均持有它。若两个订单无法明确区分，即使事件尚未被占用也保持冻结待调查，不挑第一笔、不入账、不自动重付。无候选时的“核验”不应仅因未填哈希就把 `CLAIMED` 写成 `UNKNOWN`；已有证据不明或明确矛盾仍按原核对状态处理。TronGrid 是唯一现有供应方，发现增强不宣称第二数据源或独立验证。

### 4. 有效租约对客服独占，管理员接管为另一个受控命令

提现和充值列表由服务端当前有效认领投影决定普通客服能否操作；他人有效处理中的按钮必须真实禁用并显示“正被其他客服处理中”。客户端禁用不代替服务端锁和令牌校验。

仅同时满足当前 `SUPER_ADMIN`、配置的 `wallet_manual_owner_admin_id`、当前管理会话以及**当次新鲜的钱包操作级验证/TOTP**的官方钱包所有者管理员，可以在只读查看后、填写稳定原因并单独确认，调用接管命令。选定认证模式的证明随**本次订单和接管命令**提交并在同一请求内验证，不能把可复用的 60 分钟 grant 或 48 小时管理会话当成新鲜证明；凭证原文不持久化。服务端持锁提交前复核授权。未开始的提现订单可原子轮换处理人、令牌和版本，撤销旧令牌并写幂等收据、审计、Outbox。已开始的提现只能接管**证据资格**：独立证据操作者/令牌/版本，旧共用 `claim_token` 对开始出款、重读付款指令和证据写均失效，原付款认领记录不变；新令牌不能开始付款、取得新的付款指令、调价或退款，只能发现、提交/更正证据和复核。充值已有付款凭证、已核验到账、已绑定、已入账或下发结果不明时不得按普通空白认领轮换，须遵守原核验与恢复状态机；仅在服务端证明未执行且能安全移交时才允许相应证据/复核接管，不以管理员身份绕过凭证唯一性或再下发点钻。

### 5. 错误提示与后台操作闭环

`WALLET_PAYOUT_CANNOT_CANCEL` 保持兼容错误 `code`，但其 `message` 为明确中文；服务端按真正开始/结果待核对原因区分提示。已发行 Android 可显示中文，客户端过期订单取消按钮的显示和失败后刷新需后续 Android 版本，不能记作本轮完成。后台弹窗有显式返回列表；汇率可在真正开始前反复保存；拒绝有原因菜单和操作结果查询。任何写响应未知时先查询权威状态，不静默生成新幂等键重放。

## 替代方案与后果

把取消期限放宽到“用户到账前”无法证明 imToken 尚未签名或广播，会产生付款与退款并存，因此拒绝。保留确认汇率即开始付款会继续错误锁死取消；调价时立即释放冻结差额会让用户把差额用于第二张提现，之后原点钻兑换可能无法精确冲正，因此拒绝。用 TronGrid 历史直接结算、把无搜索结果当作未付款、只在候选选择时检查重复或只放开前端按钮，都无法提供最终资金/权限证明，因此拒绝。

本方案增加客服状态字段、精确一次的证据处理令牌、有限的只读 TronGrid 调用、跨订单归属锁和受益账户/操作人分离。需 expand-only 迁移和旧客户端兼容投影；旧订单和不可变账本不重写。人工签名误付或重复付款仍无法自动撤回；歧义订单保持冻结并走审计调查。

## 验证与发布门槛

按获批计划先做红灯测试，再完成隔离 PostgreSQL 的取消/begin/拒绝并发、降低汇率后新订单、余额不足回滚、精确镜像冲正、真实操作者、USDT 来源兼容、旧摘要拒绝、接管令牌撤销、重复付款限制和充值不二次入账；以替身与隔离链源测试 TronGrid 分页、异常、固化收据、歧义以及手填/更正最终门禁。后台验证真实 disabled、只读与写权限、地址复制/清理和操作结果恢复。更新 OpenAPI、迁移与恢复手册；先领域/规格审查，再独立质量/安全审查。

发布前重新冻结生产 API/静态/Worker 镜像、schema 与 Compose，核对其他任务的后继版本及回退相容性；迁移仅扩展，先验证隔离恢复。只发布本轮后台和业务 API，不重建 Android/iOS，不在生产制造资金写或自动处理历史已开始订单。回退保留新增状态、证据、账本、审计和 Outbox，禁止破坏性 downgrade；若旧 API 无法理解新在途状态，先关受影响写入口，再以兼容镜像或前向修复恢复。发布验收以实际静态 SHA、结构化健康、401/403 权限拒绝、真实订单状态和审计为证据；没有真实授权测试账号时明确保留人工交互验收缺口。
