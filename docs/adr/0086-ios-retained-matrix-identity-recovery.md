# ADR-0086：iOS 保留旧库后显式建立新的 Matrix 设备

日期：2026-09-24。状态：**设计已批准**（产品选择、Domain 与 Quality/Security 设计评审）；实现、原生门禁、真机覆盖升级和发布仍须分别验收。产品选择：用户已明确接受保留旧库、建立新设备，并承担部分旧消息可能无法解密的结果。

## 背景

iOS 0.3.102/2144 的旧账号登录在 `account_storage` 阶段出现 L07。真机脱敏事件码证明，旧绑定的 Olm Ed25519 指纹与当前打开的本机客户端指纹不一致。另有 0.4.7/2172 在启动前出现“本地聊天身份校验未通过”，但尚未取得该错误的独立事件码；不能假定两者根因相同。当前 `Client.init` 先于应用的连续性检查运行，缺失 Olm pickle 的已登录库可能在检查前被 SDK 创建新身份并上传设备公钥。

ADR-0007 要求普通退出保留 Matrix 身份；原身份的私钥不可从账号密码重建。ADR-0072 仍为提案，但当前源码对真实指纹不符仍失败关闭。用户已接受在确实不能继续使用原身份时，保留旧库并显式建立新设备。此决策扩充恢复路径，不把不匹配的公钥当作原身份。

## 决策

1. 在打开已有 Matrix SQLCipher 库或调用 SDK `Client.init` 之前，只读检查目标槽的库、现存数据库密钥、绑定、`box_client` 账号及 Olm pickle。iOS 现有 Keychain `read` 会对旧 accessibility 执行 `SecItemUpdate`，因此预检必须新增只调用 `SecItemCopyMatching` 的原生 `peek`，不能复用迁移式 `read`。解封 pickle 只在设备内存进行，仅比较公钥指纹；不得写库、创建缺失密钥、迁移数据库或上传设备密钥。不可读、模糊、多候选状态失败关闭，不能当作全新安装。
2. 当前已认证 Business 会话的 Matrix 登录授权返回的 MXID 和 homeserver 是恢复目标的唯一权威来源。选择或描述旧槽前先与其逐字核对；登录新设备后还须核对服务端返回的 `user_id`。任一不符均拒绝切换、拒绝展示旧数据。对已绑定身份，只有同账号、同 homeserver 且 Olm 指纹吻合才复用原设备。真实不匹配、Olm pickle 缺失或库已明确不存在时，不改写旧绑定指纹，不把旧 device ID 用于新设备登录。
3. 将“保留旧库并建立新设备”作为**单独、明确的用户确认**。界面先说明旧加密聊天可能无法解密、现有旧设备可能受单设备策略吊销，再提供取消与确认；不得借用现有“清除本机聊天数据”或账号切换提示。网络、数据库、Keychain 暂时不可读时不提供建立新设备按钮。启动时若尚未完成 Business 认证，只能提示登录或重试，不得提前切换槽。
4. 确认后先关闭旧 Matrix 客户端、数据库句柄及同步任务，再在同账号及 homeserver 的本机存储中分配新的随机槽和 SQLCipher 密钥。旧数据库文件及 WAL/SHM、旧数据库密钥、旧绑定、旧恢复密钥均保持原样；持久归档索引保存旧 scope、旧数据库路径及其 WAL/SHM 路径、旧 Keychain 密钥与绑定的引用，普通同账号登录及清理流程不得删除或覆盖它们。旧库不作为新设备的解密库，新绑定只能由新设备登录后创建。
5. 槽注册表与活动槽位是分开的安全存储项。先写持久恢复日志和含旧 scope 的归档索引，读回校验成功后才写新 key、registry 与 active pointer；确认提交后最后清除 journal。崩溃后按日志及实际存储状态重放完成或恢复旧指针；任何未知状态阻止启动。若归档索引写入、提交或清除 journal 失败，不得丢掉旧 scope 枚举入口。重复确认须幂等，不得无意间再创建第二个新槽。新库只在切换完整提交后才能由 SDK 初始化。归档索引和日志采用固定版本的持久 Keychain schema，记录全部归档 scope 供清理枚举。安装世代探测器必须识别独立存在的 `.sqlite`、`.sqlite.encrypted`、`-wal` 与 `-shm`；任一旧库或 sidecar 存在时不得误作全新安装清理。只有真正新安装且全部旧库与 sidecar 均不存在时，`clearInstallation` 才清理归档 scope 的旧 Keychain 项、归档索引和日志。部分删除失败保持枚举入口，供下次安全重试。
6. 业务登录权不等同于旧 E2EE 密钥恢复。新设备只用新的、短时的 Matrix broker 登录令牌，且不传旧 `deviceId`；最终服务端 `user_id` 必须等于授权 MXID。恢复密钥或已验证旧设备若可用，可按 ADR-0007 的标准 Matrix 机制恢复有备份的 Megolm 会话；没有该材料时，如实显示旧消息可能无法解密。服务器不得取得旧库、Olm pickle、SSSS 恢复密钥或消息明文。
7. 启动路径及登录/重登录路径共享预检与恢复判定。恢复所需的异常使用稳定枚举码；日志不得包含完整用户 ID、公钥指纹、SQLCipher 密钥、pickle 或消息内容。`L07` 原阶段码保留为诊断上下文，但用户可看到可操作的本机恢复说明。
8. 此机制仅解决应用源码可控的身份连续性问题。旧版已签 App ID 与新版签名身份若不能被 iOS 接受为覆盖升级，客户端代码无法保证旧容器数据保留；公开分发须另过真机覆盖、签名、APNs 与包体一致性门禁。

现有 2144 的已签 App ID 异常地与 Bundle ID 不对应。为满足用户在开发阶段沿用相同企业签名且必须保留旧数据的选择，发布检查器只允许显式声明这一已取证的精确旧 App ID（`ZXB3TS7QD4.cn.edu.buaa.wxwork.notifyext`）；默认新包仍按 `Team.Bundle` 检查。这个例外只承认签名元数据，不能证明 iOS 接受安装。只有最终同一 SHA 企业 IPA 在另一台健康 2144 真机上不卸载覆盖后，确认登录、原聊天、Keychain 与后台提醒均可用，并通过生产 APNs、旧 Team/Keychain 和非签名包体检查，才允许公开入口。不得把此例外说成已修正历史 App ID；任何失败继续停发。

## 拒绝的替代方案

- 把旧绑定指纹改为现有公钥：会把新 Olm 身份伪装成原设备，掩盖旧密钥丢失。
- 自动删除旧数据库或 Keychain：会破坏可能尚存的房间密钥和取证材料。
- 仅重签 0.3.102/2144 或 0.4.7/2172：不改变已证实的源码连续性路径。
- 在预检暂时不可读时直接创建新设备：可能覆盖可恢复状态，故保持失败关闭并允许重试。

## 验证与回滚

先写失败用例，再实施只读预检、崩溃可恢复槽切换、登录/启动 UI。测试须覆盖预检前零写入/零上传、每个异常状态、取消不变更、确认后旧字节和旧 Keychain 项不变、新 `deviceId`、崩溃注入与幂等；再用 iOS 真机验证 SQLCipher 只读与旧版不卸载覆盖。若恢复实现出现问题，可关闭**新的确认入口**并保留全部旧库和新库，不得以清库或指纹覆写回滚。公开发布还需独立的最终 IPA 签名与分发验收。
