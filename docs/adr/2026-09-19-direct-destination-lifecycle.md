# Direct destination lifecycle and durable recovery generations

Status: accepted under explicit user authorization for ADR and production repairs; implementation/domain review and independent quality/security review passed against the recorded final hashes. Full repository and deployment gates remain separate. This supersedes the physical-destination immutability restriction for the bounded verified recovery cases, not the stable logical conversation identity or encryption invariants. [Specification](../superpowers/specs/2026-09-19-direct-conversation-auto-recovery.md), [plan](../superpowers/plans/2026-09-19-direct-conversation-auto-recovery.md), [verification](../verification/2026-09-19-direct-conversation-auto-recovery.md).

The user confirmed the manually repaired pair now sends successfully and requested system-wide prevention. Current metadata proves additional active unblocked friendships with a retired canonical, including one without a healthy registered replacement. An incident-only operations command cannot satisfy that requirement; neither can exposing null to old clients or assigning a new random room on timeouts.

## Decision

Separate the stable business conversation/history from the currently authorized sending room. Prefer a healthy current room. When strict metadata proves retirement, choose a verified usable registered alternative deterministically; preserve every old source. When none exists, only an explicit new-client resolver may reserve a durable recovery generation. One generation has one fixed alias and marker identity across users, devices, response loss and process restart. Creation remains on participant devices; the server does not join users, decrypt messages, receive room keys or manufacture user sessions.

Add resolve and publish-recovery endpoints. Resolve returns ready/join_required/create_required/unavailable and generation/alias/marker evidence. Generation0 uses existing V2 first-creation protocol. Later generations retain the original reservation and old canonical until a valid current-generation publication commits. Publication checks Matrix pair/encryption/alias/marker and expected-old/generation fencing under the pair lock. Late old-generation publication never overwrites a newer sending destination. All state changes preserve logical ID and audit/Outbox evidence.

Publication must revalidate old-room retirement under lock: if the old destination became healthy or acquired invitations, its unchanged room ID is insufficient permission to replace it. An old-generation replay must return the current authoritative destination/revision or a stale conflict, never an obsolete sending destination. Alias collision or invalid marker does not allocate a newer generation to evade verification. A monotonic canonical revision fences stale directory responses independently of creation generation.

Resolve, publication and compatibility corrections require both users currently ACTIVE, an existing friendship and no block in either direction; recheck after Matrix I/O. A separate pair mutex serializes block/unblock/delete with coordination without accidentally creating a room reservation. Lock ordering is mutex then creation reservation then relationship row.

Decision amendment: invitation-only rooms cannot be repaired solely by asking the departed actor to join when the joined peer is absent. An explicit new-client POST from the strictly verified departed actor may therefore recover an exact encrypted pair where that actor is leave and the peer is JOIN, with all existing send-power/member/relationship checks. Prefer a freshly verified registered source with both users JOIN; otherwise allocate the same durable generation protocol. Persist the recovery reason and original departed business user ID. Subsequent resolve/publication validates that original actor, regardless of who publishes: actor must remain leave; peer may remain JOIN or become leave (same alias, no extra generation). Actor becoming JOIN, invite, ban or unknown blocks replacement. The joined peer cannot initiate this exception on behalf of the departed actor. Old GETs retain their fully-retired-only policy. No administrator forced join is introduced.

Synapse retirement nuance: after the peer also leaves, strict state can successfully return an empty list. An existing requester-left generation may continue using the already-approved fully-retired proof (strict successful state with no active/invited/banned/knocking members plus matching successful room details with integer joined_members=0), including that empty-state form. Initial partial-exit authorization still requires the explicit member/encryption/permission evidence above. Visible rejoin/invitation/ban rejects replacement; failed or malformed metadata never equals retirement. This continues the same alias, does not advance a generation, and does not relax new-target verification.

Compatibility directory GETs may perform bounded idempotent maintenance of a strictly retired destination to an already verified source; this is an explicit documented maintenance side effect for deployed clients. GETs cannot allocate generations, claim new rooms or return false absence. Both endpoints share the policy. Throttling bounds probe load; it never supplies proof for a mutation. A healthy canonical does not move merely because multiple sources exist. An unavailable homeserver, malformed state or a blocked/deleted friendship cannot trigger failover or generation allocation.

Probe bounds: legacy GET examines at most four sources; explicit POST may examine up to32 within the same four-second metadata budget. Rotate the starting source even for short lists so a slow first source cannot starve a healthy later source. Creation requires all enumerated candidates freshly excluded in the current request; no negative proof is accumulated across requests. More than32 sources without a found healthy target, unresolved evidence or budget exhaustion returns unavailable. This is an explicit resource/evidence limit, not a guarantee of delivery for every possible history size. The last blocking read may overrun by at most its0.5-second phase timeout; expired evidence cannot commit a mutation.

Normal invitations may converge through the participant client. Bans, lack of sending power, absent keys and network failures remain distinct failures; this protocol does not bypass them. For candidate targets, both expected members and their send permission must be verified. The business database cannot atomically freeze Matrix state; final client permission/encryption guards remain mandatory.

## Sending and user experience

New clients use the lifecycle resolver before binding a new text row or starting an attachment/forward. The currently visible logical conversation follows the confirmed new primary without showing another friend conversation. Only null-room durable text rows are known undispatched in the existing contract. Bound rows keep their original room and transaction ID regardless of failed/queued/retry state; no ambiguous message is copied to another room. New resolver responses are guarded against stale account/page generations. Group rooms and financial business operations retain their existing semantics.

Unbound conversation resolution has per-peer bounded retries after 2, 5 and 15 seconds, so an online device does not depend solely on a new network edge. Exhaustion leaves durable unbound rows in a visible manually retryable failed state; it never changes a bound row's destination. Network recovery may resume sooner, and account disposal cancels scheduled retries. A newly published room with an invited peer is not evidence that the peer has joined or received a message.

Old2136 benefits from server source failover on its existing GETs, but cannot drive no-source generations or reliably refresh an already open attachment lease. Shipping the new client is a separate acceptance requirement. No claim of universal successful delivery is made without connectivity, room permissions and usable encryption keys.

## Verification and rollback

Expand-only generation schema, focused red/green cases, protocol contract tests, actual PostgreSQL concurrent/lost-response/fenced-publication proof, spec then independent security review, and final source/build identity are release gates. Preserve production-only patches. Application rollback keeps expanded state, history and audits; no destructive downgrade, original reservation replacement, canonical deletion or whole-database restore to undo one mapping. Explicitly report unavailable cases and unshipped client behavior.
