## 最重要的定位缺口

最近 10 万行内，Android 2190 的 **110 份已接收批次均没有 `network_requests` 逐请求明细**；另一个相邻切片的 109 份中，108 份已由 `events + operations` 占满每批 20 条名额。[批次容量统计](artifacts/2026-09-28/uploaded-diagnostics-followup/network/batch-capacity-count.json)和[字段统计](artifacts/2026-09-28/uploaded-diagnostics-followup/network/batch-field-count.json)均只含闭合计数。2190 正式构建的冻结源码哈希与当前 [装箱代码](../../apps/mobile_flutter/lib/core/chat_diagnostics.dart) 和[有界队列](../../apps/mobile_flutter/lib/core/network_diagnostics.dart)一致，见[源码归属核验](artifacts/2026-09-28/uploaded-diagnostics-followup/source-attribution.json)：代码先装事件和操作，再尝试装请求明细；满 20 条的批次确定没有请求明细槽位。接收端允许该字段，旧 Android 2188 / iOS 2189 批次在同一窗口分别上传了 100 / 5 条，所以不是服务器全面不支持。服务端已接收批次无法证明客户端当时确有待发请求，也不能排除客户端先因 422 降级关闭该扩展；这两个可能性对满额和未满额批次都要在端上核查。容量问题是确定的阻塞条件，尚不是全部缺失的唯一已证根因。

2190 在较早的滚动窗口还上报 `network_request/incomplete` 的聚合 `reported_count=3505`，源码语义是丢失的网络摘要尝试与逐请求记录的增量，**不是 3,505 次线路超时**。截至 19:24:10+08 的全容器窗口有 83 个不重复的 `diagnostic_loss.sample_id`，共报告 21 条事件、3,612 条操作记录和 198,259 个帧诊断记录丢失；没有跨分段重复或冲突。这是遥测缺失，198,259 不是屏幕实际掉帧数。因而当前日志不能兑现“每次网络超时都带完整请求阶段并远端留存”。

## 处理顺序

先修复 Android 诊断装箱的容量阻塞：在 20 条、客户端默认 15KiB 与服务端 16KiB 上限内给失败请求保留可证明的容量，并用“事件/操作持续满额、请求队列积压、上传失败/422 降级”测试验证；同时在端上确认请求是否确实排队及扩展是否被关闭。发布新客户端后，以真实后续版本批次出现 `network_requests` 且丢失计数受控作为验收。再按同一请求 ID 对齐客户端阶段与服务端完成时间，分开调查 Matrix 的 `unknown` 等待、两次媒体失败及消息页最差帧窗口。iOS 应在包含同等诊断的新 build 到达真实设备后复查。现有记录没有地区/运营商/实际入口或双区同栈测点，不足以据此把新加坡改为主服务器。

本次没有修改代码、DNS、数据库、镜像或客户端分发；所有原始用户日志留在服务器，最终证据文件没有用户标识、IP、URL、请求 UUID、正文或凭据。
