# Durable media independent SPEC/domain review

Candidate: 850710bd52d5763e8a3831e0665cb1eb5dbe44fd in im-media-outbox/StarChat. Parent assigned this review under approved remediation R8; this reviewer owns only this separate artifact directory and did not edit candidate production or tests. Baseline source was checked clean before probes; after the final probe HEAD remained 850710bd and both core production files still had no diff (the implementer had begun a new, untracked regression file).

Outcome: CHANGES REQUIRED. Specification/domain review was performed first, followed by review-quality.md. The four independently demonstrated findings below prevent approval of this frozen candidate.

1. **P1 — A suspended resolver blocks all later intent persistence.** media_outbox_store.dart:373-550 puts the entire persistence operation in the instance _serial chain, including loadFile/loadBytes and file copy. With A's resolver held open, B.persistBytes cannot even create its preparing row: byTxid(B) is null after 300 ms, and B proceeds only after A settles. Normal slow platform resolution/export/forward download can therefore block unrelated-room preparation and leave later selected work without durable intent. Keep atomic metadata/count/space admission short, and bound actual preparation separately without holding the intent queue.
2. **P2 — An existing later retry timer suppresses a newly due earlier task.** media_outbox_recovery_service.dart:431-439 uses _retry ??= Timer(delay) without comparing deadlines. A stored five-second deadline is scheduled first; B then fails with the normal two-second network backoff. After three seconds, B has still sent only once. Schedule the earliest due scan while continuing to check every task's persisted server deadline; this must not shorten a 429 deadline.
3. **P1 — Preparation ownership is instance-local, so replacement cancellation touches a live source.** Store _writingSources (line 167), releaseTerminalSource (608-617), and service cancel (416-429) do not share source-copy lifetime across replacement instances. An old same-owner service holds a foreground token and pauses during an open .part write; after suspension, a new same-owner service cancels it and attempts to delete that still-open file. Windows reports errno 32 instead of safely deferring cleanup. Shared preparation pins must survive service replacement until real settlement; terminal accounting must stay charged until safe deletion.
4. **P2 — A flight skipped at initial recovery becomes an unrecoverable automatic orphan after it settles.** media_outbox_recovery_service.dart:364-405 reconciles sending only once. A replacement service first sees the old live flight and skips it, then sets _reconciled=true. The old suspended service rejects its late ACK and leaves sending; the replacement's next scan cannot claim sending and changes it to failed/not-admitted. The independent fixture observes zero replacement sends, where the same transaction should be retried as ACK-unknown once no real flight/foreground owner remains. Explicit user retry currently works around this, but automatic recovery does not.

## Requirements that were traced

- Separate pending-media-v1/owner namespace is derived from account, homeserver and database generation. Metadata contains routing, txid, digest and whitelisted presentation fields, not tokens, room keys, captions or arbitrary event content. No Matrix/text-outbox tables are written.
- Intent precedes resolver/export/file copy within an admitted persistence operation; source copy uses bounded chunks, digest, flush and private rename. Source/cache domains are separate. Low space and source integrity failure retain an actionable row. The first finding concerns operations waiting before that intent, not the ordering inside the current operation.
- The 512 MiB byte reservation is a SQLite transaction counting charged partial/terminal sources; failed deletion does not release charge. The 128 pending check is currently outside that transaction and only instance-serialized. Its replacement-instance atomicity should be included in the short-transaction fix, not claimed proven by the existing single-instance byte-cap test. Native 16 MiB free-space is sampled at admission; it is not an OS reservation against external writers.
- Transport has two distinct-room slots, one real flight per (owner, txid), ordered same-room requests, no UI-timeout release, and a discovery lock that no longer spans Future.wait of transports. Existing fairness/scan-lock tests cover those corrected cases. The new findings cover preparation, deadline ordering and replacement lifetimes that those tests missed.
- Recovery authorizes before source verification. SDK/lease checks account/client/room identity, E2EE and current send permission again around asynchronous preparation. Prepared/asFile, dimensions and duration fields persist; the real SDK mock-HTTP test exercises the same transaction URL after ACK loss and m.file preservation.
- Current gallery factory always supplies localVideoFile for videos. The unused-by-default fallback branch no longer passes photo.duration; preserve that compatibility field if editing it. No group-size bypass finding remains: the final _sendMedia group video check is present. The old gallery preparation already ignored its original argument, so this is not attributed to the candidate.
