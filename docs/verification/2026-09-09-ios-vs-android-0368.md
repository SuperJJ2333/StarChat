## Consequences for rollout

The candidate should not be described as “Android 2072 functionality, adapted for iPhone.” To reach that result, integrate the Android business/UI additions into iOS while preserving the new coordination/context fixes and resolving the competing cache implementations with regression tests. This comparison does not itself authorize changing Android or silently merging every branch.

The new iOS acceptance and both profile “send message” entry points use the same coordinated controller. Once a canonical room is established, they open it. Creation/sync is network-dependent, not atomic with the business acceptance click. Existing duplicate rooms/history are not deleted or merged.

Mixed with unmodified Android 2072, server-only deployment plus iOS upgrade cannot guarantee that every obsolete Android creation path avoids an additional physical Matrix room. The server can preserve its first canonical mapping and deny registration into a pending reservation, but the old Android client may already have created another room directly in Matrix. Likewise, an offline requester cannot instantly send an ordinary message; the selected new iOS behavior is a labeled acceptor-authored request explanation, not impersonation of the requester. These limits must remain visible in the release report.
