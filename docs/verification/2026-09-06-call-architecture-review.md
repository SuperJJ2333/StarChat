# 通话实现与本次修复说明

## 判断

问题包含实际的集成架构缺陷和测试覆盖缺口，不是仅靠扩容带宽即可修复，也不能笼统归因于 Flutter 或 Matrix 不支持通话。

已确认：Matrix 0.34.0 在 initWithInvite 中先打开本地媒体，再将新来电交给应用；权限失败便中止来电展示。应用的拒绝授权分支还会拒绝来电并触发原生通知清理。推送泛化通知、解密后的消息通知和通话通知没有统一取消关系。先前验证未覆盖“从未授权的来电”和这几条通知路径的交叉时序，导致问题延续。

## 成熟应用公开做法

- Telegram 官方文档明确区分 Telegram API 信令通道与基于 WebRTC 的传输通道，呼叫协商和密钥协商有专门协议。来源：https://core.telegram.org/api/end-to-end/video-calls 。
- WhatsApp 官方工程说明：来电信令分发到接收者各设备，某设备接听后使用对应的加密媒体密钥建立通话。这表明来电分发/设备状态与实际媒体建立分开。来源：https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/ 。
- WhatsApp 还公开了简化的静默来电通知协议和中继保护 IP 的实现，反映其针对不同来电状态专门设计路径；这不是对全部闭源 Android 实现的描述。来源：https://engineering.fb.com/2023/11/08/security/whatsapp-calls-enhancing-security/ 。
- Android 提供 CallStyle 来电通知、接听/拒接动作和通话优先级；媒体前台服务另有相机/麦克风权限及启动限制。来源：https://developer.android.com/develop/ui/compose/notifications/call-style 和 https://developer.android.com/develop/background-work/services/fgs/service-types 。

由此得到的本项目设计建议（推论）：把推送唤醒、本地同步解密、来电状态/通知、接听授权、媒体采集、网络连接分开；由一套通话状态协调呈现，不能让一个阶段失败时无条件清理另一个阶段的通知。

## 本次落实

1. SDK 入站呼叫不再提前采集；用户接听后才采集。版本固定为本地 Matrix 0.34.0 源码副本，只修改 call_session.dart，保留许可证与上游哈希，避免 pub-cache 修补在换机或 CI 时丢失。没有修改加密协议或服务端密钥边界。
2. 应用层权限拒绝保留 ringing，可重新授权/接听、拒接或进入权限设置。原生 answering 可恢复 ringing，协调器不再把刚恢复的来电通知取消。
3. 本地泛化唤醒先尝试同步，给解密五秒机会；明确为来电或真实消息时取消泛化通知，且取消覆盖异步展示竞态。通话授权/连接阶段也保持 callActive，防止泛化通知重新出现。
4. 已本地解密为通话信令的事件不再作为聊天通知展示。语音来电标题为“语音通话”，视频为“畅聊视频来电”。
5. 接听媒体采集期间发生结束，kEnding/kEnded 均阻止迟到接听；迟到媒体释放，重复点击共享同一次采集。

## 仍存在的架构边界

当前 event_id_only 推送与服务端内容最小化设计不能在服务端识别加密来电。Getui 厂商离线通用通知使用随机 ID，不能安全关联本地解密事件；本次本地修复不保证彻底消除“进程已死、厂商先显示泛化提示”的情况。不能为隐藏它而关闭所有真实消息的离线提示。

彻底解决该离线路径需要：配置厂商离线通道、持久化不透明事件/通知关联、可可靠启动的同步解密入口，以及通知与通话的一致状态协调。应按 E2EE 元数据边界审查后实施，不泄露正文、SDP、发送者姓名、密钥或明文音视频。

增加 TURN 节点用于媒体网络绕行/跨运营商链路优化；带宽用于已确定的并发吞吐瓶颈。它们解决不了权限时序、通知覆盖、推送登记或进程唤醒问题。是否改用商业 RTC 服务应在这些基础路径稳定后再评估，不承诺换 SDK 就自动获得可靠后台来电。

## 后续验收矩阵

每次通话改动至少覆盖：前台/后台/锁屏/进程被回收；麦克风和相机未授予/拒绝/永久拒绝；语音不请求相机；来电时同时有真实消息；立即接听/拒接；授权时对方挂断；多设备同账号接听；跨网络连接和超时；最小化、返回、结束清理。自动化覆盖状态与时序，实际厂商后台行为必须配合真机双端测试。
