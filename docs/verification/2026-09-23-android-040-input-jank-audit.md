# Android 0.4.0 输入卡顿：源码调查与建议

日期：2026-09-23。范围：解释原因并提出方案；未改代码、未构建、未发布，未进行真机性能采样。

## 证据身份

正式发布记录对应 0.4.0+2157，源码 28bdfc48；用户仅报告 v0.4.0，尚未核实其设备 build、型号及输入法。发布证据见 [正式包报告](2026-09-22-android-040-release.md)。本次使用 git show 读取该提交，避免把当前未发布优化当作旧包行为。

## 源码事实（以下行号均属于 28bdfc48）

- room_page.dart:854–900：输入监听只进行提及差分、草稿保存与必要的提及面板切换，没有直接历史搜索调用。room_draft_store.dart 中保存已有 300ms 去抖，预览逐房间通知。
- room_page.dart:1113–1116、1607–1632：同步通知经 scheduleRefresh 合并；变化后执行提及摄取、搜索索引维护、撤回处理和时间线局部通知。
- room_timeline_controller.dart:924 起：已有帧级通知合并及 50ms 兜底。不是每个 SDK 事件都直接重建整个聊天页。
- room_page.dart:4646–4706：每次维护索引仍同步遍历 timeline.allMessages（已加载消息，不等于整个数据库历史），分配集合；400ms Timer 位于遍历之后，只延后提交，不把计算移出 UI isolate。
- 同一路径存在待提交批次覆盖风险：observe 先登记 seen，随后取消旧 Timer，而新闭包只保留本次 fresh。400ms 内新批次可能取消前批次尚未提交的索引；这是静态逻辑缺陷，尚未执行复现测试，不代表已证实它是输入卡顿主因。
- logical_conversation_timeline.dart:83–105：合并 snapshot 遍历各来源，内容变化后排序。窗口化渲染不能自动保证所有上游计算都局限在可视消息。
- room_page.dart:1578–1603：每次合并后的 metadata 刷新读取 roomInfo 并比较成员列表；大群额外成本待采样。

## 判断与方案

首要假设是同步恢复/消息洪峰带来的 UI isolate 计算竞争。网络等待本身不应阻塞本地输入；数据到达后的投影、索引、状态通知及绘制可能延迟文本编辑事件。未采样，不能量化各项贡献，也不能排除输入法/设备/图片绘制和 SDK 解密存储开销。

1. 先在实际受影响设备记录输入事件处理到下一帧、UI/raster 帧耗时、snapshot/index/member/mention 的计数和耗时。不记录正文、输入文本或密钥。
2. 索引改为按事件新增/变更/撤回的持久待处理队列；累计后分批消费，成功才确认，失败可重试，去抖不能丢批。空闲调度必须有最大等待时间，撤回优先从可搜索结果排除。
3. 时间线按来源 revision 复用快照并增量合并；成员和提及仅按相关变化更新，补同步分片让出事件循环。保证去重、顺序、本地回显和撤回语义。
4. 保留既有输入控制器/FocusNode/局部刷新；检查外层重建和 IME composing，不在组合输入时回写 text/selection。不把单纯 RepaintBoundary 当作 CPU 计算隔离。
5. 对确认为 CPU 热点且可分离的纯计算考虑后台 isolate；不直接移动 SDK/数据库对象，不把明文上传服务端索引。

## 验收建议（目标，不是已测结果）

同一设备用 profile 包采样、release 包复验；正常网络、丢包/延迟、断线补同步；10/50条每秒与短时突发；短/长已加载历史；连续中文拼音、选词、删除和光标移动。观察 P95/P99 输入延迟和慢帧，并验证无丢字、组合串重置、重复消息、索引漏批或撤回残留。建议先以 P95 输入到显示 <50ms、P99 <100ms 为目标，结合设备基线调整；帧预算按刷新率，60Hz 为约16.7ms。

本次仅静态调查；没有运行性能测试，不承诺提升倍数。此前服务端诊断接收部署不会改变已安装 0.4.0 的输入性能，最终修复须交付新 Android 包。
