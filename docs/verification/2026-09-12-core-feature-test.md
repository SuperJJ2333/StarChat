### 关键发现 F1（P0）：断网恢复后消息同步不恢复

- **步骤**：①App 前台正常收消息（服务端确认持续 /sync 流量）→ ②断网 10–12s（run1 飞行模式导致 WiFi 重连、网络重建；run3 `svc wifi disable`）→ ③网络恢复（run1 WiFi 回来 / run3 切蜂窝，OS 层 ping 服务器正常）→ ④观测。
- **实际**：恢复后 **run1 ≥6 分钟、run3（含切前台）≥2 分钟**，账号在服务端**零请求**（Synapse 按 user 过滤计数 0），客户端仅打印 2 次 `Syncloop failed: Client has not connection`；`chatflow/syncwatchdog` 看门狗**全程无日志**（软阈值 2.5min 应触发）。期间 UI 仍可渲染本地库消息（AvatarFirstPaint 持续）。**强制重启 App 后 1.0s 内重连**（02:13:47→48，服务端当分钟 7 请求）。
- **复现概率**：2/2（有效断网样本；另 1 次因 MIUI 飞行模式未真正断网判无效）。
- **证据**：reconnect-log*.txt、watchdog-recovery.txt、repro3-recovery.txt、服务端 docker logs 时间线。
- **根因假设（待代码修复确认）**：网络切换后长轮询 socket 死亡，SDK sync 循环抛错后未重试；`MatrixSyncWatchdog` 未介入——审计点：`app_home.dart:451/1020` 的启动条件（capability 门控）与心跳口径；缺"连接性恢复事件→立即 resync"。
- **建议**：接入 ConnectivityResult 监听，网络可用沿变化即 `client.restartSyncLoop()`；修复看门狗装配条件并补"断网→恢复"集成测试（现有 `matrix_sync_watchdog_test.dart` 单测绿但未覆盖真机网络切换路径）。

## 2. 多媒体消息文件缓存与加载

### 架构核对（代码证据，已验证）

| 项 | 结论 | 证据 |

### 与消息模块一致性结论（用户关注点）

**不一致（M3）**：朋友圈与消息媒体是**两套独立缓存**（chat-media 内容寻址对象+引用 vs moments flutter_cache_manager 键值缓存）。同一图片若同时出现在聊天与朋友圈会**各存一份**（两模块重复，非模块内重复）。建议：朋友圈对大图/视频复用 `objects/<sha256>` 存储（服务端已回传内容哈希时可零成本接入）。

### 未验证 / 阻塞

- 长视频/多图深滚动流量、预加载策略、跨用户同图复用统计：需样本与打点（附录 A 用例；阈值：滑动 jank ≤5%、单次会话流量 ≤30MB、同图跨用户磁盘仅 1 份）。

## 附录 A：未执行项的可执行用例与数据构造

1. **规模数据**（预发环境）：注册 101 个 bot 账号；1 主账号入 100 群；每群用 `matrix-bot` 以脚本发 1000 条混合消息（文本 70%/图 15%/视频 5%/语音 5%/文件 5%，大小分档 100KB/3MB/40MB/150MB 各占比 4:3:2:1）。验收：全部入库且客户端 30 分钟内全量可加载。
2. **接收延迟/丢失/重复/乱序**：服务端发送侧打点（event_id, ts）与客户端接收侧打点对齐写 ES；1 小时 10 msg/s/群；按 event_id 幂等核对。阈值见 §1 表。
3. **弱网/抖动**：Linux 网关 `tc netem delay 200ms 50ms loss 2%` 或 Charles Throttle；用例：发送中断网→恢复续传；收图中断→重试；同步中断→F1 修复后应自动恢复。
4. **推送唤醒**：设备 Doze + 杀进程，另一端发消息；验收 个推到达≤10s、点击进会话定位正确。
5. **多媒体去重/秒传**：同一 3MB 图分别发给用户 A/B/群 G/收藏；断言 chat-media objects 计数 +1 而非 +3；跨设备同账号登录后二次查看 0 网络回源（命中本地）。
6. **朋友圈一致性改造后回归**：同一图发朋友圈+聊天，断言单一存储。
